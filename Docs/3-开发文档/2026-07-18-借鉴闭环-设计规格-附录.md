# Borrowing Lifecycle: Design Specification Appendix

> Main specification: [Design Specification](2026-07-18-借鉴闭环-设计规格.md).

## A. Identifier and path contracts

- `source_id`: a stable lowercase identifier containing only ASCII lowercase letters, digits, periods, underscores, and hyphens; the first character must be a letter or digit.
- `capture_id`: source type + date + short fingerprint prefix, such as `git-20260718-a1b2c3d4e5f6`. The card still stores the complete fingerprint.
- `borrow_id`: `borrow-YYYYMMDD-<slug>`. Append a stable sequence number on collision; never overwrite an older directory.
- Every relative path must remain inside `借鉴区/` after normalization. Cards prohibit absolute local paths and credentials. All tracked text sinks—identifiers, locators, authorization descriptions, Git/Local/Web facts, and Web `charset / etag / last_modified` fields—must reuse the same credential detector at normalized input and final rendering. Reject whitespace-delimited sensitive keys, JSON Unicode-escaped keys, and explicit nonempty values beginning with punctuation. Malformed Unicode escapes fail closed as credentials.
- Git/web use sanitized public locators. Local-source `canonical_locator` uses `local:<display-name>`. `capture.local.json/v1` stores exactly five fixed keys, three of whose values are normalized local paths. The borrowing area must not persist actual credentials; keep them outside this area in operating-system or tool credential storage. Prefetch private Git/Web content outside the borrowing area, then pass only sanitized public locators or local input paths for prefetched content to capture. Any future support for secret-based access requires a new schema, separate Class B authorization, and dedicated secret storage; do not extend v1 for that purpose.

## B. Source-version card contract

Cards use Markdown with restricted YAML frontmatter. Frontmatter contains only fixed scalars, avoiding a YAML-module dependency. Type-specific details go into fixed body tables.

Common fields include at least:

```yaml
schema: borrowing-source/v1
source_id: example
capture_id: git-20260718-a1b2c3d4e5f6
source_type: git
capture_status: ready
canonical_locator: https://example.invalid/owner/repo.git
fingerprint_algorithm: git-object
fingerprint: <complete-value>
captured_at: 2026-07-18T00:00:00.000Z
rights_status: unverified
access_policy: source-read-only
reuse_scope: inspect-and-analyze-only
execution_policy: deny
network_policy: source-read-only
storage_policy: local-only
distribution_policy: deny
upstream_write_policy: deny
auto_refresh: false
```

The Git table records ref, ref type, object format, commit, tree, and submodule/LFS status. The local table records manifest algorithm, file count, byte count, and exclusions/failures. The web table records original/final URLs, redirects, status code, MIME, charset, ETag, Last-Modified, and response hash.

Git LFS and submodules may be detected and recorded read-only; initialization, downloading, and execution are prohibited.

Allowed values are fixed: `rights_status=unverified|verified|restricted`; `access_policy=local-read-only|source-read-only`; `reuse_scope=inspect-and-analyze-only|copy-internal-approved|adapt-internal-approved|redistribute-approved`; `execution_policy=deny|sandbox-approved`; `network_policy=deny|source-read-only`; `storage_policy=local-only|tracked-metadata-only|tracked-content-approved`; `distribution_policy=deny|internal-approved|external-approved`; `upstream_write_policy=deny`; `auto_refresh=false`. Capture and P4t provide no source-execution, automatic-refresh, or upstream-write capability.

The body also contains a fixed permissions table: `Permission dimension / Effective value / Authorization time / Authorization source / Applicable scope`. Default permissions cite `default-policy`. Any departure from defaults requires a per-dimension ISO 8601 authorization time, auditable authorization source, and bounded scope, without credentials. Ready Git/Web captures require `access=source-read-only + network=source-read-only + execution=deny + upstream-write=deny`; local captures require `network=deny + upstream-write=deny`. Running trusted Git/PowerShell capture tools does not change source-content `execution_policy`.

Official cards allow only `ready / retired`. Failed staging creates no official card, although ignored candidate cards and staging may remain. After ready, identity and fingerprint fields cannot be rewritten. Retirement only appends to the fixed management-history table: `Time / Previous state / New state / Reason / Confirmation`. Before ready→retired, confirm all referring items are `closed/cancelled`. P4t requires no active item to reference a retired capture; retain historical references from terminal items. Missing `local-only` caches produce warnings; existing caches with incorrect fingerprints fail hard.

## C. Borrowing-card contract

Frontmatter includes at least:

```yaml
schema: borrowing-item/v1
borrow_id: borrow-20260718-example
title: <item-title>
lifecycle_status: draft
decision: pending
impact_level: L1
owner_pm: project-pm
blocked: false
created_at: 2026-07-18T00:00:00+08:00
updated_at: 2026-07-18T00:00:00+08:00
supersedes: ""
closure_seal_sha256: ""
```

Required body sections:

1. Problem to solve and success criteria.
2. Source-binding table: `source_id / capture_id / fingerprint / Evidence locator`; supports multiple sources.
3. Candidate matrix: existing capabilities, reusable ideas, conflicts, conclusions, and reasons.
4. Explicitly adopted and explicitly excluded material.
5. Target files, responsible PM, L1-L4, and PROP/ADR links.
6. Acceptance criteria, implementation records, and fresh verification evidence.
7. State history: time, previous state, new state, decision, reason, and confirmation.

## D. Valid state combinations

| lifecycle_status | Allowed decision | Requirements |
|---|---|---|
| draft | pending | Problem and initial source locator |
| assessing | pending / adopt / adapt / reject / defer | At least one ready capture and a candidate matrix |
| implementation_ready | adopt / adapt | Q1-Q7, L1-L4, and required approvals passed |
| implementing | adopt / adapt | Target scope and responsible roles established |
| verifying | adopt / adapt | Implementation record exists |
| closed | adopt / adapt | Target files, adaptation differences, and fresh verification evidence |
| closed | reject | Assessment evidence and rejection reasons |
| parked | defer | Resumption condition or review date |
| cancelled | Any | Cancellation reason; must not masquerade as reject |

After entering `implementation_ready`, `implementing`, `verifying`, or `closed`, each source binding for `adopt` requires `reuse_scope=copy-internal-approved`; `adapt` requires `reuse_scope=adapt-internal-approved`. Neither `inspect-and-analyze-only`, a mismatched internal scope, nor `redistribute-approved` implies permission for the current internal implementation.

Valid adjacent transitions are fixed: initial `none → draft`; `draft → assessing`; `assessing → implementation_ready / parked / closed(reject)`; `parked → assessing`; `implementation_ready → implementing`; `implementing → verifying`; `verifying → closed(adopt|adapt)`; any active state may become `cancelled`. `closed/cancelled` are terminal. Same-state evidence additions are allowed only in active states and must not fabricate a transition.

`blocked=true` is allowed only in active states and requires `blocked_from`, `reason`, and `resume_condition`. Unblocking returns to the original state. P4t validates each adjacent transition, nondecreasing timestamps, and decision conditions. The last history row must match current frontmatter values.

For `closed`, `closure_seal_sha256` is mandatory: normalize the entire card to UTF-8, LF, and one trailing newline; blank the seal-line value, then calculate SHA-256. The seal must be empty in every other state. It detects accidental or noncompliant edits. Recalculating the seal is not a valid revision; legitimate changes require a new `supersedes` item.

## E. Minimum P4t contracts

### Template mode

- `.czxt-template-root` exists and `.czxt-project-root` does not. Both or neither fails hard.
- `借鉴区/` contains only README, ignore rules, templates, and empty directory skeletons.
- `实例化项目.ps1` copies neither the borrowing area recursively nor the template marker.
- Template-card fields and state enums match the rule document.

### Instance mode

- `.czxt-project-root` exists and the template marker does not. Both or neither fails hard.
- Source/capture/borrow IDs are unique and match their directories.
- Source-card schemas, type fields, and fingerprint formats are valid.
- Referenced captures exist. Active items reference only ready captures. Only terminal `closed/cancelled` items may retain historical references to retired captures. Prove the absence of active references before source retirement.
- State/decision combinations, every adjacent transition, the last history row, conditional closure, and closure seals are valid. `borrowing-evidence/v1` precisely binds the evidence bullet's time, command, exit, and target-inventory digest. Arbitrary nonempty files and `.staging-*` members cannot serve as fresh evidence.
- All paths remain within the root, with no reparse points, symlinks, junctions, or hardlinks. Every regular file requires `NumberOfLinks=1`. Unavailable link-count APIs fail hard.
- Ignore rules isolate raw caches. If the root is in a Git repository, any cache tracked by `git ls-files` fails hard. Lightweight evidence must not become a disguised second source.
- `{{APP_REPO_DIR}}` must not depend on the borrowing area through import, require, `file:`, workspace/build configuration, script invocation, symbolic links, or runtime reads.

Application isolation performs three actual-read passes: tree baseline, application scan, and final tree review. For files `≤8 MiB`, each pass binds identity, length, complete bytes, and SHA-256. For files `>8 MiB`, each pass binds only identity, length, and the first `64 KiB`; detection of tail changes outside that observation range with unchanged identity and length is not promised. Text accepts only strict UTF-8 or BOM-marked UTF-16LE / UTF-16BE. Large-file prefixes use a non-finalizing decoder; malformed encoding within the observed range still fails hard.

The three read passes share one fail-closed budget: at most `20000` files, `100000` directory entries, and `512 MiB` of digest reads. Project-card reads allow `1 MiB` each and `2 MiB` across initial/final reads. Tree baseline, application scan, and final review are charged for actual reads and enumeration; no subphase may reset the budget.

P4t exit codes: `0` pass, `5` nonblocking warning, `10` hard failure. The checker must not connect to the network, refresh sources, or execute external content.

## F. Contract-test matrix

Positive cases: empty template, empty instance, Git capture, local capture, web capture, multiple-source item, reject closure, defer/resume, verified adopt/adapt closure, and source refresh preserving older references.

Negative cases: conflicting mode markers, recursive-copy leaks, duplicate IDs, directory/ID mismatch, missing fingerprints, nonexistent references, invalid state transitions, inconsistent history, closure without evidence, path traversal, symlink/junction, accidentally tracked caches, direct application dependencies, and execution triggered by external content.

All tests use temporary fixtures: local temporary repositories for Git, temporary directories for local sources, and offline response bytes for web sources. No network dependency.

## G. Failure recovery

- Capture failure: register no official ready capture. Ignored candidate cards and staging may remain; report the staging path and failed phase.
- Refresh must not rewrite older captures. Return REUSED only when the complete fingerprint is unchanged and matches the stable facts of the sole valid ready capture. Changed fingerprints create new captures. Older items retain `source_id + capture_id + fingerprint` and never follow updates automatically.
- Snapshot corruption or fingerprint mismatch: P4t fails hard; implementation and closure are prohibited.
- Verification failure: remain in `verifying` and append failure evidence. Do not reset, delete user changes, or roll back silently.
- Refresh failure: older captures and items remain unaffected.
- Closure failure: candidate installation and seal commit both use no-overwrite behavior and must not overwrite later objects. Restore the original active card only if ownership is proven and `content-deleted` has not been entered. Evidence bound to the current official object with only a `borrow_id` mismatch still supports safe restoration from the complete snapshot. Other `seal-ownership-unproven` cases retain the current official card and staging. `content-deleted` is an irreversible completion point; do not roll back the official card afterward.
- The staging ownership chain is fixed: atomically create the staging directory relative to a trusted parent-directory handle. Create the first `原活动卡.bin` with handle-relative CreateNew; write, flush, and bind it on that same handle. Hold the file lease throughout the transaction so the directory remains nonempty. Create candidate `借鉴卡.md` with handle-relative CreateNew as well.
- Cleanup order is fixed: `Candidate→retained Original→content-deleted→directory`. Validate Candidate through one opened, bound handle and set delete-pending on that same handle. Set delete-pending for retained Original through its retained lease on the same handle. Immediately enter `content-deleted`, then delete the directory through its creation handle. Leave no gap between validation and path opening. Creation failures delete only objects bound to this transaction's handles.
- After P4t exit 0, acquire the final official-card lock through one OPEN_REPARSE_POINT open. Recheck canonical path, regular non-reparse type, link count=1, identity, length, and bytes from that same handle. Hold this exclusive lease until staging cleanup finishes. Never validate a safe path and then reopen by path.
- Staging-candidate updates after sealing follow a two-state contract: the official-card ownership snapshot and current staging-candidate snapshot are independent states. Rollback validates each separately. Do not prematurely change the staging expectation to sealed bytes. After the Set operation in `Set-BctCandidateBytes` commits, update the state object before later checks that may fail, so exception branches see the actual committed candidate.
- Instantiation failure: use no-overwrite `target→backup` and `prepared→target` transactions. Bind project root, source, and target through handles and `GetFinalPathNameByHandleW`, rejecting physical aliases such as `subst`. Register each output immediately in the output manifest and retain read-only shared leases. Failed multi-file installation promises no global atomic rollback. Preserve auditable remnants when ownership is unclear.
- Before cleanup, deletion, moving, or retirement, inspect references and obtain separate confirmation under existing B/C boundaries.
