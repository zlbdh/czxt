# 借鉴闭环 · 设计规格附录

> 主规格：[2026-07-18-借鉴闭环-设计规格.md](2026-07-18-借鉴闭环-设计规格.md)

## A. 标识与路径合同

- `source_id`：稳定小写标识，只允许 ASCII 小写字母、数字、点、下划线、连字符；首字符为字母或数字。
- `capture_id`：来源类型 + 日期 + 指纹短前缀，例如 `git-20260718-a1b2c3d4e5f6`；完整指纹仍写入卡片。
- `borrow_id`：`borrow-YYYYMMDD-<slug>`；重复时追加稳定序号，不覆盖旧目录。
- 所有相对路径必须规范化后仍位于 `借鉴区/`；卡片禁止绝对本机路径和凭据。标识、locator、授权说明、Git/Local/Web facts 与 Web `charset / etag / last_modified` 等所有 tracked 文本 sink 均须在规范化入口和最终 renderer 复用同一凭据检测器；空白分隔敏感键、JSON Unicode 转义键、标点开头的非空显式值都必须拒绝，畸形 Unicode 转义按凭据 fail closed。
- Git/网页使用净化后的公开定位；本地来源的 `canonical_locator` 使用 `local:<display-name>`。`capture.local.json/v1` 只保存固定 5 键，其中 3 个值是规范化本机路径；真实凭据不由借鉴区持久化，必须留在借鉴区之外的操作系统或工具的凭据存储。私有 Git / Web 内容先在借鉴区外预取，只把净化后的公开定位或已预取内容的本机输入路径交给 capture；未来若支持秘密接入，必须采用新 schema、独立 B 类授权与专用秘密存储方案，不得扩写 v1。

## B. 来源版本卡合同

卡片为 Markdown + 受限 YAML frontmatter。frontmatter 只使用固定标量，避免引入 YAML 模块；类型专属细节进入固定正文表。

公共字段至少包含：

```yaml
schema: borrowing-source/v1
source_id: example
capture_id: git-20260718-a1b2c3d4e5f6
source_type: git
capture_status: ready
canonical_locator: https://example.invalid/owner/repo.git
fingerprint_algorithm: git-object
fingerprint: <完整值>
captured_at: 2026-07-18T00:00:00.000Z
rights_status: unverified
access_policy: source-read-only
reuse_scope: inspect-and-analyze-only
execution_policy: deny
network_policy: source-read-only
storage_policy: local-only
distribution_policy: deny
upstream_write_policy: deny
auto_refresh: false
```

Git 表记录 ref、ref 类型、object format、commit、tree、submodule/LFS 状态；本地表记录 manifest 算法、文件数、字节数和排除/失败项；网页表记录原始/最终 URL、重定向、状态码、MIME、charset、ETag、Last-Modified 与响应哈希。

Git 的 LFS 与 submodule 允许只读检测并记录，禁止初始化/下载/执行。

允许值固定为：`rights_status=unverified|verified|restricted`；`access_policy=local-read-only|source-read-only`；`reuse_scope=inspect-and-analyze-only|copy-internal-approved|adapt-internal-approved|redistribute-approved`；`execution_policy=deny|sandbox-approved`；`network_policy=deny|source-read-only`；`storage_policy=local-only|tracked-metadata-only|tracked-content-approved`；`distribution_policy=deny|internal-approved|external-approved`；`upstream_write_policy=deny`；`auto_refresh=false`。捕获器和 P4t 不提供来源执行、自动刷新或上游写入能力。

正文另有固定权限表：`权限维度 / 生效值 / 授权时间 / 授权来源 / 适用范围`。默认权限集合使用 `default-policy` 作为来源；任何生效值偏离默认策略时，必须逐维给出 ISO 8601 授权时间、可审计来源和有限适用范围，且不得包含凭据。Git/Web ready capture 必须是 `access=source-read-only + network=source-read-only + execution=deny + upstream-write=deny`；本地 capture 必须 `network=deny + upstream-write=deny`。受信任 Git/PowerShell 捕获工具的执行不改变来源内容 `execution_policy`。

正式卡只允许 `ready / retired`；staging 失败不生成正式卡，但允许保留被忽略的候选卡与 staging。ready 后身份与指纹字段不可改写，退役只追加固定管理历史表 `时间 / 旧状态 / 新状态 / 原因 / 确认`。ready→retired 前必须确认所有引用事项已是 `closed/cancelled`；P4t 要求 retired capture 不被任何活动事项引用，且不得删除终态事项的历史引用。`local-only` 缓存缺失给警告，存在但指纹不符为硬失败。

## C. 借鉴卡合同

frontmatter 至少包含：

```yaml
schema: borrowing-item/v1
borrow_id: borrow-20260718-example
title: <事项标题>
lifecycle_status: draft
decision: pending
impact_level: L1
owner_pm: project-pm
blocked: false
created_at: 2026-07-18T00:00:00+08:00
updated_at: 2026-07-18T00:00:00+08:00
supersedes: ""
closure_seal_sha256: ""
```

正文固定包含：

1. 要解决的问题与成功标准。
2. 来源绑定表：`source_id / capture_id / fingerprint / 证据定位符`；支持多来源。
3. 候选矩阵：已有能力、可借鉴点、冲突、结论、理由。
4. 明确采纳内容与明确不采纳内容。
5. 目标文件、责任 PM、L1-L4、PROP/ADR 链接。
6. 验收标准、实施记录和 fresh 验证证据。
7. 状态历史：时间、旧状态、新状态、decision、原因、确认。

## D. 合法状态组合

| lifecycle_status | 允许 decision | 必须满足 |
|---|---|---|
| draft | pending | 问题、初始来源定位 |
| assessing | pending / adopt / adapt / reject / defer | 至少一个 ready capture 与候选矩阵 |
| implementation_ready | adopt / adapt | Q1-Q7、L1-L4 与所需审批通过 |
| implementing | adopt / adapt | 目标范围和责任角色已确定 |
| verifying | adopt / adapt | 实施记录存在 |
| closed | adopt / adapt | 目标文件、适配差异、fresh 验证证据 |
| closed | reject | 评估证据与拒绝理由 |
| parked | defer | 恢复条件或复查时间 |
| cancelled | 任意 | 取消原因；不得伪装成 reject |

进入 `implementation_ready`、`implementing`、`verifying` 或 `closed` 后，`adopt` 的每个来源绑定要求 `reuse_scope=copy-internal-approved`，`adapt` 要求 `reuse_scope=adapt-internal-approved`。`inspect-and-analyze-only`、不匹配的内部范围与 `redistribute-approved` 均不得被推导为当前内部实施权限。

合法相邻转换固定为：首次记录 `none → draft`；`draft → assessing`；`assessing → implementation_ready / parked / closed(reject)`；`parked → assessing`；`implementation_ready → implementing`；`implementing → verifying`；`verifying → closed(adopt|adapt)`；任一活动状态可转 `cancelled`。`closed/cancelled` 为终态；同状态追加证据仅限活动状态，不伪造一次转换。

`blocked=true` 只允许活动状态，并要求 `blocked_from`、`reason`、`resume_condition`。解除后回到原状态。P4t 必须逐行校验相邻转换、时间非递减和 decision 条件，历史末行必须与 frontmatter 当前值一致。

`closed` 时 `closure_seal_sha256` 必填：以 UTF-8、LF、单个末尾换行规范化整张卡，把 seal 行的值置空后计算 SHA-256。其他状态 seal 必须为空。它用于发现意外或不合规改写；重新计算 seal 不构成合法修订，合法变更必须新建 `supersedes` 事项。

## E. P4t 最小合同

### 模板模式

- `.czxt-template-root` 存在，`.czxt-project-root` 不存在；双标记或无标记硬失败。
- `借鉴区/` 只有 README、忽略规则、模板和空目录骨架。
- `实例化项目.ps1` 不递归复制借鉴区，不复制模板标记。
- 模板卡字段集合、状态枚举与规则文档一致。

### 实例模式

- `.czxt-project-root` 存在，模板标记不存在；双标记或无标记硬失败。
- source/capture/borrow ID 唯一且与目录一致。
- 来源卡 schema、类型字段和指纹格式合法。
- 借鉴卡引用的 capture 存在；所有活动事项只能引用 ready capture，retired capture 只允许 `closed/cancelled` 终态事项保留历史引用。来源退役前必须先证明无活动引用。
- 状态/decision 组合、每一条相邻转换、历史末条、条件关闭与关闭 seal 合法；`borrowing-evidence/v1` 精确绑定 bullet time、command、exit 与目标文件清单摘要，禁止任意非空文件和 `.staging-*` 成员充当 fresh evidence。
- 所有路径留在根内，无 reparse point、symlink、junction 或任何硬链接；所有常规文件 `NumberOfLinks` 必须等于 1，链接计数 API 不可用均硬失败。
- 原始缓存由忽略规则隔离；若根位于 Git 仓库，任何被 `git ls-files` 跟踪的缓存均硬失败；轻量证据不得伪装成第二来源。
- `{{APP_REPO_DIR}}` 不通过 import、require、`file:`、工作区/构建配置、脚本调用、符号链接或运行时读取依赖借鉴区。

业务隔离在树基线、业务扫描和最终树复核中执行三轮实际读取：`≤8 MiB` 文件每轮绑定 identity、length、全量字节与 SHA-256；`>8 MiB` 文件每轮只绑定 identity、length 与前 `64 KiB`，不承诺发现观测范围外的尾部同身份同长度改写。文本只接受严格 UTF-8，或带 BOM 的 UTF-16LE / UTF-16BE；大文件前缀使用非终止解码器，已观测范围内的畸形编码仍硬失败。

三轮实际读取共用一次 fail-closed 预算：最多 `20000` 个文件、`100000` 个目录项、`512 MiB` 摘要读取；项目卡单次 `1 MiB`，首尾两次合计 `2 MiB`。树基线、业务扫描和最终树复核都按实际读取与枚举计费，任何子阶段不得重置预算。

P4t 退出码：`0` 通过、`5` 非阻塞警告、`10` 硬失败。检查器不得联网、刷新或执行外部内容。

## F. 契约测试矩阵

正例：空模板、空实例、Git capture、本地 capture、网页 capture、多来源事项、reject 关闭、defer/恢复、adopt/adapt 验证关闭、来源刷新保持旧引用。

反例：模式标记冲突、递归复制泄漏、重复 ID、目录/ID 不一致、指纹缺失、引用不存在、非法状态跳转、历史不一致、无证据关闭、路径逃逸、symlink/junction、缓存误跟踪、业务直接依赖、外部内容触发执行。

测试全部使用临时 fixture：Git 使用本地临时仓库，本地来源使用临时目录，网页使用离线响应字节；不依赖网络。

## G. 失败恢复

- 捕获失败：不登记正式 ready；可保留被忽略的候选卡与 staging，并报告 staging 路径和失败阶段。
- 刷新不得改写旧 capture：完整 fingerprint 不变且与唯一合法 ready 的稳定事实一致时返回 REUSED；fingerprint 改变时新增 capture；旧事项保持原 `source_id + capture_id + fingerprint` 引用，不得自动跟随。
- 快照损坏或指纹不符：P4t 硬失败，禁止进入实施或关闭。
- 验证失败：保留在 `verifying`，追加失败证据，不执行 reset、删除用户改动或静默回滚。
- 刷新失败：旧 capture 与旧事项不受影响。
- 关闭失败：候选安装与 seal 提交都采用 no-overwrite，不覆盖后来对象。仅在 ownership 可证明且尚未进入 `content-deleted` 时恢复原活动卡；材料已绑定当前正式对象、仅 `borrow_id` 不一致仍可按完整快照安全恢复。其他 `seal-ownership-unproven` 必须保留当前正式卡与 staging；`content-deleted` 是不可逆完成点，其后不回滚正式卡。
- staging 所有权链固定：通过受信父目录句柄相对原子创建 staging 目录；首个 `原活动卡.bin` 以目录句柄相对 CreateNew，并在同一 handle 写入、flush 并绑定，文件 lease 贯穿整个事务以让目录保持非空；候选 `借鉴卡.md` 也以目录句柄相对 CreateNew。
- 清理顺序固定为 `Candidate→retained Original→content-deleted→directory`：Candidate 以单次打开的绑定 handle 完成验证并在同一 handle 设置 delete-pending；retained Original 通过保留 lease 在同一 handle 设置 delete-pending；随后立即进入 `content-deleted`，最后由目录创建句柄同句柄删除。验证与路径打开之间不得留窗口；创建失败只删除本事务句柄绑定对象。
- P4t exit 0 后，正式卡终锁必须单次 OPEN_REPARSE_POINT 打开，并从同一 handle 复核 canonical path、常规非 reparse 类型、link count=1、identity、length 与 bytes；该排他 lease 持有到 staging 清理结束。禁止“先安全路径验证再按路径重开”。
- seal 后 staging 候选更新遵循双状态合同：正式卡所有权快照与当前 staging 候选快照是两个独立状态，回滚必须分别验证；不得提前把 staging 期望改成 sealed 字节。`Set-BctCandidateBytes` 的 Set 提交后状态对象先更新，再执行后续可失败复核，确保异常分支看到实际已提交候选。
- 实例化失败：文件采用 `target→backup`、`prepared→target` 的 no-overwrite 事务；项目根以及源与目标通过 handle、`GetFinalPathNameByHandleW` 绑定，拒绝 `subst` 等物理别名。每个输出即时进入输出 manifest 并保持只读共享 lease；多文件安装失败不承诺全局原子回滚，所有权不明时保留可审计残留。
- 清理、删除、移动或退役前先检查引用关系，并按现有 B/C 边界单独确认。
