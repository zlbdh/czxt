# Borrowing Lifecycle: Design Specification

- **Status:** Completed and passed final acceptance; no commit, push, tag, release, or external distribution performed.
- **Date:** 2026-07-18.
- **Classification:** L4 / Class B: root-level evidence layer, workflow, permission model, and health-check extension.
- **Responsible roles:** Project PM orchestrates; Operating System PM manages borrowing metadata; the target decision PM evaluates; the existing responsible PM/implementation agent is selected by the target path allowlist; testing-related PMs perform acceptance.
- **Implementation authorization:** The user requested a persistent goal and implementation. Commit, push, tag, release, and external distribution are outside that authorization.
- **Detailed contracts:** [Design specification appendix](2026-07-18-借鉴闭环-设计规格-附录.md).

## 1. Goal and completion criteria

Extend the current one-time cross-project reverse-learning principle into a repeatable, auditable capability: freeze sources, extract candidates, decide on adoption, adapt material to the current project, bind verification evidence, and retain rejections, deferrals, and historical versions.

Completion requires all of the following: the template contains only a generic skeleton; all three source types have stable fingerprints; all four decisions are traceable; application code is isolated from external content; P4t blocks invalid cards, paths, states, and closure conditions; temporary instantiation leaks no data; and PowerShell 5.1, P4s, P4t, and P4a-P4t all pass.

## 2. Non-goals

- No automatic search, recommendations, or continuous monitoring of external projects.
- No automatic source refresh or execution, building, or installation of external source code.
- No central JSON/YAML manifest, database, new hooks, or new PM roles.
- No original repositories, large files, or complete web pages committed into the template.
- No automatic commit, push, tag, release, distribution, or upstream writes.
- No specific source project, product path, or application terminology embedded as a current template fact.

## 3. Single-root architecture

Establish one root entry point, `借鉴区/`. Do not maintain a parallel `参照区/`, borrowing ledger, or second active index.

## 4. Template and instance modes

Existing README/directory heuristics can make an instance still appear to be a template. Add explicit markers:

- The template tracks `.czxt-template-root`; this file is not copied.
- `实例化项目.ps1` generates `.czxt-project-root` in the target root.
- Mode detection reads markers. P4t fails hard when both or neither exist. Older heuristics provide migration advice only.

Do not include `借鉴区/` in the recursive `$copyItems` list. Instantiation copies only its README, templates, and ignore rules, then creates empty `来源/` and `事项/` directories. Even with `-Force`, it must not overwrite existing instance source cards, item cards, or local caches.

The installer writes files through two no-overwrite moves: existing `target→backup`, followed by this transaction's `prepared→target`. Backup, prepared, and target objects are bound to canonical paths, file identity, length, and bytes. If a later object occupies a path, stop and preserve every object. Resolve the physical final paths of the project root, source, and target through handles and `GetFinalPathNameByHandleW`. Reject boundary crossings or overlaps caused by junctions, reparse points, hardlinks, `subst`, or other physical aliases. Register each installed or rewritten output immediately in the output manifest. Before the final marker/success output, retain read-only shared leases on every manifest entry. This consists of multiple per-file transactions and promises no global atomic rollback on failure. Preserve auditable remnants of backups, prepared objects, installed objects, or concurrent objects whose ownership cannot be proven; never guess which objects to delete or overwrite.

Template mode prohibits concrete source and item cards. Conduct the first end-to-end trial in the ignored `项目区/本地实例/` directory.

## 5. Source capture

Items pin `source_id + capture_id + fingerprint`. Refresh must not rewrite an older capture. Return REUSED when the complete fingerprint is unchanged and matches the stable facts of the sole valid ready capture. Create a new capture when the fingerprint changes. Existing items retain their original `source_id + capture_id + fingerprint` references and must not follow updates automatically.

- **Git:** Pin ref, object format, and commit/tree. Read-only detection and recording of LFS and submodules are allowed; initialization, downloading, and execution are prohibited. Hooks, credential prompts, and release assets remain prohibited.
- **Local directory:** Copy through staging on the same volume. Normalized SHA-256 manifests before and after copying must match.
- **Web/document:** Preserve raw response bytes and response metadata. Calculate SHA-256 from the raw bytes.

All identifiers, locators, authorization descriptions, and fact/response metadata that might enter a tracked source card undergo shared credential detection twice: after normalization and in the final renderer. Detection includes whitespace-delimited sensitive keys, JSON Unicode-escaped keys, and explicit nonempty values beginning with punctuation. Malformed Unicode escapes fail closed as credentials. The public P4t source/isolation leaves independently determine actual RootMode and reject forged Mode values; they must not rely solely on façade prechecks.

All source types reject path traversal, link escape, and silently skipped reads. External commands and prompts are untrusted data only. Type-specific fields are in the appendix.

Capture begins in `.staging-<uuid>`. Atomically move it into an official capture only after fingerprinting, safety checks, and card validation all pass. Failure writes no official ready card or partial index. Ignored candidate cards and staging may remain. Matching fingerprints reuse captures idempotently; different fingerprints create new captures.

`能力资产/tools/scripts/capture-borrowing-source.ps1` and type-specific helpers implement these safety semantics and receive offline contract tests. The Skill is the sole operator-facing entry point; the executor is its trusted machine layer, not a second workflow. Safe Git parameters, before/after local manifests, raw web bytes, same-volume staging, idempotent reuse, and failure without partial artifacts must be implemented behavior, not merely command documentation.

## 6. Default permissions

The generic template must not infer complete authorization from a request to add a source. Defaults:

```yaml
rights_status: unverified
access_policy: local-read-only
reuse_scope: inspect-and-analyze-only
execution_policy: deny
network_policy: deny
storage_policy: local-only
distribution_policy: deny
upstream_write_policy: deny
auto_refresh: false
```

Record access, reuse, source-content execution, networking, storage, distribution, and upstream writes separately. Authorization in one dimension implies none in another. Every departure from defaults requires a per-dimension entry in the fixed permissions table with authorization time, source of authorization, and applicable scope; all three are mandatory. Remote Git/Web capture requires `access_policy: source-read-only + network_policy: source-read-only + execution_policy: deny + upstream_write_policy: deny`. Running a trusted capture tool does not authorize running source content.

## 7. Borrowing-item lifecycle

Lifecycle and decision are separate:

- Main progression: `draft → assessing → implementation_ready → implementing → verifying → closed`.
- Deferral/resumption: `assessing → parked → assessing`.
- Any active state can transition to `cancelled`.
- `decision: pending | adopt | adapt | reject | defer`.

Rules:

- A ready source capture is required before `assessing`. There is no item-level `frozen` state.
- Enter `implementation_ready` only with `adopt/adapt` and satisfied Q1-Q7 and L1-L4 gates.
- In `implementation_ready / implementing / verifying / closed`, every source binding for `adopt` requires exactly `copy-internal-approved`; `adapt` requires exactly `adapt-internal-approved`. Do not infer a permission hierarchy from other `reuse_scope` values.
- `reject` may close from assessment, but requires assessment evidence and rejection reasons.
- `defer` enters `parked` with a resumption condition or review date.
- `blocked` is a supplemental field recording the original state, reason, and resumption conditions; it is not a main state-machine state.
- Append state changes to history. P4t validates each adjacent transition, and the last history entry must match current state.
- The Skill may invoke only the trusted `close-borrowing-item.ps1` closure entry point. It installs the candidate without overwrite, calls `seal-borrowing-item.ps1` to write `closure_seal_sha256` for normalized content, and runs full-root P4t. After exit 0, it verifies the final official-card lock and performs cleanup under lock. Report closed only after all steps succeed. Restore the original active card only when ownership is proven and `content-deleted` has not been entered. If evidence binds the current official object and only `borrow_id` differs, ownership remains provable and the complete snapshot supports safe restoration. Other `seal-ownership-unproven` cases retain the current official card and staging. After the irreversible `content-deleted` completion point, do not roll back the official card. P4t verifies read-only; closed items are not rewritten later. Changes in direction require a revision or superseding relationship. The seal detects accidental or noncompliant edits; it does not claim to resist malicious writers able to modify both body and seal.
- The staging ownership chain is fixed: atomically create the staging directory relative to a trusted parent-directory handle. Create the first `原活动卡.bin` with handle-relative CreateNew, then write, flush, and bind it on that same handle. Retain its file lease throughout the transaction so the directory stays nonempty. Create candidate `借鉴卡.md` with handle-relative CreateNew as well.
- Cleanup order is fixed: `Candidate→retained Original→content-deleted→directory`. Validate Candidate through one opened, bound handle and set delete-pending on that same handle. Set delete-pending for retained Original through its retained lease on the same handle. Immediately enter `content-deleted`, then delete the directory through its creation handle. Leave no gap between validation and path opening. Creation failures delete only objects bound to this transaction's handles.
- After P4t exit 0, acquire the final official-card lock through one OPEN_REPARSE_POINT open. Recheck canonical path, regular non-reparse type, link count=1, identity, length, and bytes from that same handle. Hold this exclusive lease until staging cleanup finishes. Never validate a safe path and then reopen by path.
- Updating the staging candidate after sealing follows a two-state contract: the official-card ownership snapshot and current staging-candidate snapshot are independent states. Rollback must validate each separately. Do not prematurely change the staging expectation to sealed bytes. After the Set operation in `Set-BctCandidateBytes` commits, update the state object before later checks that may fail, ensuring exception branches see the actual committed candidate.
- Before `adopt/adapt` closure, require adaptation differences, target files, implementation records, and fresh verification evidence. Evidence uses `borrowing-evidence/v1`, binding verification time, command summary, exit status, and a digest of the complete target-file inventory. An arbitrary nonempty file cannot stand in for acceptance results.

## 8. Entry point and roles

The sole operator-facing entry point is `能力资产/skills/借鉴.md`, with four modes: intake, assessment, implementation, and audit. For intake, the Skill calls the tested capture executor; operators need not assemble safety-sensitive commands manually.

- `rules/借鉴治理.md` defines only schema, permissions, safety invariants, and A/B/C boundaries.
- `skills/借鉴.md` defines only triggers, execution steps, failure output, and the fixed summary.
- `07_完整工作流/借鉴闭环.md` defines only role switches, state transitions, approvals, and recovery.

Project PM receives requests and routes work. Operating System PM manages sources, cards, and framework. Product/Technical/Test/Operations PMs assess within their target domains. Implementation roles follow existing target-file path allowlists only: Operating System PM for framework, Product PM for requirements, Development PM for application/test code, and Test and Release PM for release actions. Do not generalize “target decision PM” or “implementation PM” into permission to write outside these boundaries. Add no roles.

## 9. P4t and acceptance order

Preserve P4s template-cleanliness semantics without relaxing source-keyword rules. Explicit markers allow instances to skip template-cleanliness scans. P4t runs for both templates and instances.

P4t performs only offline consistency checks: mode, skeleton, cards, references, states, closure conditions, paths, and zero application dependencies. Build/runtime artifacts that may be deployed or executed, such as `dist / build / .next / target / out`, remain in scope. Exclude only clearly identified third-party, VCS, coverage, and cache trees. Do not connect to the network, refresh sources, or execute source content. Detailed contracts are in the appendix.

Application-isolation scans share one resource budget per invocation. Files `≤8 MiB` are read fully on three passes; for files `>8 MiB`, the three passes bind only identity, length, and the first `64 KiB`. Therefore v1 does not promise detection of tail changes outside the observation range when identity and length remain unchanged. Actual reads for the tree baseline, application scan, and final tree review each count toward fail-closed limits of 20,000 files, 100,000 directory entries, and 512 MiB of digest reads, plus a project-card limit of 1 MiB per read / 2 MiB across two reads.

Fixed acceptance order:

1. Gate 0: mode markers and Windows PowerShell 5.1 encoding baseline.
2. Positive and negative P4t contract tests.
3. Temporary instantiation, proving skeleton-only copying.
4. Focused P4s and P4t checks.
5. Overall P4a-P4t health check.

Failure at any step prevents a claim that the complete lifecycle is finished. Detailed fields, state combinations, negative cases, and affected files are in the appendix.

## 10. Gate 0 decision

The task's starting baseline tracked 124 `.ps1` files. Windows PowerShell 5.1 `ParseFile` then failed on 95 files with 648 parsing errors, while explicit UTF-8 decoding passed 124/124. These values describe only the task's starting baseline, not the current script count. Retain the existing PowerShell 5.1 contract, migrate tracked scripts to UTF-8 BOM in a separate mechanical batch, and add a zero-ParseFile-error gate for every file. Record this only as an acceptance-baseline repair, not a borrowing-feature deliverable.

## 11. Governance and migration

Create a PROP and ADR for this feature. Add only a current “extended by the new ADR” note to ADR-021 and repair invalid pointers; do not rewrite its historical body. Synchronize current entry points, instantiation lists, health-check scope, and active indexes with the new source of truth. Do not bulk-replace historical states, older handoffs, or archived logs.

Preserve workspace changes that predate the task throughout implementation and completion. Do not commit, push, tag, release, or distribute externally.
