## Context

ADR-012/013/015 established the **handoff content structure**: 6 sections, an extracted format, and a handoff-area event stream. Two gaps remained:

1. **No process-problem rule**: whether to stop business implementation for a process bug—misclassified rules, false warnings, wrong paths—depended on PM judgment.
2. **No mandatory compact chat format**: a complete file did not guarantee the PM/Owner could recognize the handoff immediately in chat; a 179-line card differs from a 5-line compact form.

PROP-014 closes both gaps and requires the compact ①–⑥ format.

## Decision

Introduce **3 meta-rules**.

### Rule 1: Three-Level Process-First Triage

Record in `agent/workflows/实施循环.md`:

| Severity | Symptoms | Action |
|---|---|---|
| 🔴 Blocking | Affects code, tests, or implementation | Stop immediately; open a governance PROP; fix the process before continuing |
| 🟡 Nonblocking bug | False warning, inconsistent document, wrong path | Continue business work; immediately add to RETRO backlog |
| 🟢 Improvement | Another approach may be better | Continue business work; discuss at next RETRO |

This prevents both process overhead blocking business work and business work hiding process debt.

### Rule 2: Mandatory Handoff Matrix

Record in `agent/workflows/实施循环.md` and `agent/workflows/交接卡格式.md`:

| Action | Full card required? | Compact chat ①–⑥ required? |
|---|---|---|
| Cross-tool switch: Cowork ↔ Claude Code ↔ Codex ↔ zlbdh | Required | Required |
| Implementation complete: code, framework, QA, push | Required | Required |
| Internal PM progress: PRD, option selection, answers | Update 状态.md only | Optional |
| Temporary discussion: confirmation, simple Q&A | No | No |

### Rule 3: Mandatory Compact Chat Handoff ①–⑥ ⭐

Record in `agent/workflows/交接卡格式.md`. **After implementation, write the full file and also send a compact ①–⑥ handoff in chat.**

Standard compact format, 5–10 lines:
```
[Handoff — <Task> from <A> to <B>]
① Time: YYYY-MM-DD HH:MM
② Files: N new / M modified (key commit hash, size checks, APK path)
③ Tests: vitest ✅/❌ N/N | esbuild ✅/❌ | build ✅/❌ | APK ✅/⏳ | smoke ✅/⏳ | push ✅/⏳
④ Your tasks: [1] xxx [2] xxx [3] xxx
⑤ Warnings: ✅/🟡/🔴 Key warning
⑥ Details: read 交接区/待接手/...md
```

**❌ A summary paragraph cannot replace it**, however detailed. The PM must see ①–⑥ matching the full card's 6 sections.

## Consequences

### Benefits
- ✅ Process severity follows rules rather than subjective PM decisions.
- ✅ Mandatory chat format makes tool behavior and visual signals consistent.
- ✅ The no-summary-substitution rule prevents tools such as Claude Code from skipping the format.
- ✅ The **fourth framework governance change using a recurring pattern**, after PROP-011/12/13; this fills missing rules instead of correcting misplaced ones.

### Costs
- ❌ A compact 5–10-line handoff adds about 30 seconds, but was already expected.
- ❌ Triage adds cognitive load, though three levels are more appropriate than stopping for every issue.

### Mitigated Risks
- ✅ If Claude Code / Codex omits chat handoff, the PM's 5 startup steps inspect cards and can prompt for it.
- ✅ Concrete examples standardize triage: path self-correction is 🟡; ProfileCard exceeding an advisory is 🟢.
- ✅ The canonical template in 交接卡格式.md standardizes new files and Codex output.

### Preserved
- ✅ The stable full 6-section card from PROP-009/010/011.
- ✅ Pending/received/historical handoff directories.
- ✅ 状态.md's top summary.
- ✅ AI Class A/B/C boundaries, which classify behavior rather than process.
