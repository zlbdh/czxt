# ADR-019 · Resolve Competing Data Sources: Merge profiles into userProfile (PROP-015)

- **Status**: Current
- **Date**: 2026-05-12
- **Decision maker**: zlbdh
- **Related**: [PROP-015](../../../确认改动/已审批/已完成/PROP-015-2026-05-12-数据双源治理.md) · Removes a prerequisite blocker for Sprint-3

## Context

Sprint-2 introduced `userProfile` for the 5-part Profile page, while the early schema retained `profiles`:

- `profiles`: the v1–v2 physical profile, including `height` / `weight` / `bodyFat` / `goal`.
- `userProfile`: the v3 profile, covering physical data, work schedule, drink habits, goals, and Mimi's personality mode.

Their coexistence caused 3 problems:

1. The UI could show both old physical-profile and new personal-profile entries.
2. Overlapping fields, especially `height` / `weight`, had no clear source.
3. Sprint-3 Chat / Plan features read only `userProfile`, leaving data entered in `profiles` unused.

## Decision

Starting in v3.2, use `userProfile` as the only profile source in the application read/write layer.

### 1. Upgrade Dexie Schema to v4

Add a v4 migration: at startup, read `profiles.get('main')`, transform it, and merge into `userProfile.get(1)`.

Temporarily keep declaring the `profiles` store in v4. Do not physically delete it: mobile IndexedDB migration failures must preserve old data. Consider dropping it only after stable v3.3/v5 verification.

### 2. Field Mapping

| Old profiles | New userProfile | Strategy |
|---|---|---|
| `height` | `height` | Copy unchanged |
| `weight` | `weight` | Copy unchanged |
| `bodyFat` | `bodyFat` | Add to ProfileCard's basic physical section |
| `goal: "recomp"` | `mainGoal: "目标A"` | Enum mapping |
| `goal: "cut"` | `mainGoal: "减脂"` | Enum mapping |
| `goal: "bulk"` | `mainGoal: "增肌"` | Enum mapping |
| `activity` | Do not migrate | Not yet in userProfile; `calcTargets` falls back to `moderate` |

The literal enum values above describe the existing data contract.

### 3. mergeFillEmpty Strategy

Use `mergeFillEmpty(existing, patch)`:

- Fill only fields that are empty in `existing`.
- Do not overwrite fields the user already entered in the new ProfileCard.
- Catch migration failures and retain old `profiles` data.

This prevents old values from replacing `userProfile` entries made in v3.0/v3.1.

### 4. Bidirectional Enum Compatibility Period

Keep temporary old/new compatibility in `calcTargets` and `analyzeMealImage` during v3.2:

- Old: `goal = cut | recomp | bulk`.
- New: `mainGoal = 减脂 | 目标A | 增肌 | 维持 | 其他`.

All callers now pass `data.userProfile`, but retain compatibility branches for one version to reduce upgrade and backup-import risk. Reassess old enum removal in RETRO-007 or v3.3.

## Consequences

### Benefits

- The Profile page has one ProfileCard instead of two entries.
- Chat / Health / Home / AI meal-image analysis all read `userProfile`.
- Old backups and `profiles` data migrate automatically.
- Extract migration logic from `database.js` to `databaseMigration.js`, limiting database-file growth.

### Costs

- v4 retains the physical `profiles` store, leaving some underlying debt.
- `calcTargets` temporarily retains legacy enum branches.
- Adding `bodyFat` may change existing profile completeness from 5/5 to 5/6 until users enter body-fat percentage.

### Risks and Mitigations

- Migration failure: wrap v4 upgrade in try/catch, retain old `profiles` data, and allow a later retry.
- Conflicting fields: `mergeFillEmpty` fills blanks without overwriting the new profile.
- Old profiles in backups: call `tryMigrateImportedProfile` after `importAllData`.
- Physical-device verification: the v3.2 APK was installed, Dexie v4 opened without error, and Chat read `userProfile.mainGoal` correctly.

## Summary of the Recorded Decision

ADR-019 consolidates application reads/writes from `profiles` plus `userProfile` into `userProfile`, while retaining the old store for one version as migration insurance. Sprint-3 can build plans, schedules, and richer AI context on this single source.
