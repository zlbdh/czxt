# ADR-020 · Architectural Debt Cleanup: Split 4 Files and Remove 2 Dead-Code Locations (PROP-016)

- **Status**: Current
- **Date**: 2026-05-12
- **Decision maker**: zlbdh
- **Related**: [PROP-016](../../../确认改动/已审批/已完成/PROP-016-2026-05-12-架构债清理.md) · RETRO-007 · Removes a prerequisite blocker for Sprint-4

## Context

After Sprint-3, functionality was stable at v3.5, but 4 files approached the warning range and 2 dead-code locations remained:

- `timelineBuilder.js`, 6918B: today's timeline logic mixed with utilities.
- `Health.jsx`, 6331B: the page container still included weight-trend JSX.
- `dailyBriefing.test.js`, 6272B: all F-CHAT-4 tests in one file.
- `defaults.js`, 6069B: obsolete `TASK_HINTS` remained.
- `TaskDetailModal.jsx`: no business entry point after F-DAY-1 switched to DayDrawer `taskDetail`.

Starting Sprint-4 directly would make every expansion encounter file-size overhead. PROP-016 cleans this debt before new business work.

## Decision

Perform pure refactoring starting with v3.5.1:

1. Keep `buildWorkdayTimeline` / `buildWeekendTimeline` / `buildTodayTimeline` in `timelineBuilder.js`. Extract nonbusiness utilities to `timelineBuilderUtils.js` and re-export them from the main file to preserve existing imports.
2. Keep page state and orchestration in `Health.jsx`; extract the weight-trend Card to `HealthWeightTrend.jsx`. Do not extract a hook, which would complicate the tightly coupled `weight/bodyFat/chartData/actions` flow.
3. Split `dailyBriefing.test.js` by feature: keep greeting, stats, and main entry tests; move suggestions and warnings to `dailyBriefing.suggestions.test.js`.
4. Delete `TaskDetailModal.jsx` and `TASK_HINTS` from `defaults.js`. Make `taskDetails.js` plus DayDrawer `taskDetail` the only task-detail implementation.
5. No schema, business-logic, dependency, or visual-target changes. Use the `refactor:` commit prefix.

## Key Tradeoffs

### 1. Accept timelineBuilder / Health Above the 5KB Target

PROP-016 initially targeted <5KB per file. Actual results:

| File | Before | After | Reason |
|---|---:|---:|---|
| `timelineBuilder.js` | 6918B | 5897B | Outside warning range; further splitting fragments core builders |
| `Health.jsx` | 6331B | 5426B | Outside warning range; extracting BMI/training offers little benefit |

Accept 5.3–5.8KB: readability takes precedence over mechanically reaching 5KB, with margin below the 6500B warning line.

### 2. Temporarily Duplicate Test Fixtures

Both `dailyBriefing.test.js` and `dailyBriefing.suggestions.test.js` retain their own `FULL_DATA`, avoiding another shared fixture file. If briefing tests grow further, extract `dailyBriefing.fixtures.js`.

### 3. HealthWeightTrend Is a Component, Not a Hook

The goal is to reduce JSX in `Health.jsx`. Weight input state, chart data, and `actions.addRecord` remain controlled by the main page. A hook would lengthen state-update paths without enough benefit.

## Consequences

### Benefits

- All 4 warning-level files leave that range: `timelineBuilder.js` -15%, `Health.jsx` -14%, `dailyBriefing.test.js` -30%, `defaults.js` -33%.
- Smaller source files are easier for Codex / Claude Code / Cowork to read and modify before Sprint-4.
- Removing `TaskDetailModal.jsx` and `TASK_HINTS` leaves only DayDrawer `taskDetail` for task details.
- vitest remains 399/399, with no reduction in test count; physical-device smoke covers 5 Sprint-3 functions.

### Costs

- Approximately 2 more modules: Vite build modules increase from 2284 to 2286, considered acceptable.
- `timelineBuilder.js` and `Health.jsx` remain above 5KB; further expansion requires context review.
- Slight fixture duplication reduces coupling between `dailyBriefing` test files.

### Risks and Mitigations

- Import breakage: utility re-exports from `timelineBuilder.js` preserve compatibility.
- Dead-code removal: grep, esbuild, and APK smoke showed no runtime errors involving `TaskDetailModal` / `TASK_HINTS`.
- Functional regressions: v3.5.1 device smoke covers Home timeline, both DayDrawer modes, Health weight trend and posture, Profile schedule, and Chat daily briefing.

## Follow-up

- Start Sprint-4 business PRDs after PROP-016 cleanup.
- If `dailyBriefing` grows, first extract fixtures or move proactive suggestions from rules to LLM generation.
- If Health grows, first extract training records or HealthCalendars responsibilities rather than adding them back to `Health.jsx`.
