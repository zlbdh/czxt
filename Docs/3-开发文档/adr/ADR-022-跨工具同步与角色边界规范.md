## Decision

### Decision 1: Cross-tool source authority (topic D)

When operating on framework files or making decisions across tools, use this **source priority**:

```
PS1 (Windows host ground truth; authoritative)
  > Read tool (direct host-file access, bypassing the mount cache)
  > Cowork bash wc -c / stat / ls (mount cache may be stale)
```

**Four defensive rules for the Cowork PM** (implemented by PROP-018 P2 in PS1 P4e and check 9 of agent/skills/项目体检-检查项-7-8.md):

| # | Rule | Trigger |
|---|---|---|
| ① | Recheck warning / danger file sizes with Read | Near the 6500B warning / 8KB advisory thresholds |
| ② | Immediately Read the tail after Edit/Write changes a framework file | Confirm that the write actually took effect |
| ③ | Refresh the mount or restart the Cowork session when git status disagrees | bash misses new files or shows an old diff |
| ④ | Trust PS1, not Cowork bash, for P4b warning-list byte counts | The two counts differ |

**When bash is trustworthy**: Read-only grep, cross-file statistics, tasks that do not require exact byte counts, or cross-session checks after several minutes.
**When bash is not trustworthy**: wc -c immediately after Edit/Write, or deciding whether a file crosses a size threshold.

### Decision 2: AI configuration defaults move from Class C to Class B with six safeguards (topic V; follows PROP-012)

AI configuration defaults (baseUrl / model / apiKey) move in AI边界.md from **Class C (never modify) to Class B (zlbdh review + six safeguards)**.

**Six safeguards**:
1. `.env.local` must be covered by `.gitignore`, with four layers: `*.local` + `.env` + `.env.local` + `.env.*.local`.
2. Do not put keys in code or git tracked files.
3. **Dev mode gate**: Check for the presence of `VITE_DEV_DEFAULT_AI_APIKEY`. **Field correction: the original `import.meta.env.DEV` is false in a debug APK.**
4. User configuration has the highest priority: IndexedDB > localStorage > dev-default > none (fallback).
5. Do not give the APK to third parties; it is zlbdh's personal debug APK.
6. Do not publish it on Google Play or in a public release.

### Decision 3: Rules for highly sensitive / partially sensitive disclosure (topic X)

**Classification**:
- **Highly sensitive**: API keys / secret tokens / account passwords — **must never enter chat, git, or conversation logs**.
- **Partially sensitive**: baseUrl / model names / internal PROP IDs — prefer placeholders in concise chat, such as `<your gateway baseUrl>`, without making that mandatory.
- **Public**: FOSS library names / public documentation links / similar information — unrestricted.

**Recorded incident #1** (topic X): zlbdh pasted an API key into chat through an explicit override, and the PM configured `.env.local`. **Mitigation**: Rotate the key after Sprint-4 closeout, a ten-second action in the gateway administration console.

**Template for future explicit overrides**:
1. PM warns explicitly about the risk and alternatives.
2. zlbdh explicitly approves: "I accept the risk; please handle it."
3. After acting, the PM proactively reminds the user to rotate / revoke the key.

### Decision 4: PRDs must include empty states / defaults / boundary values (topic P)

**Meta-rule**: Every PRD, including F-XXX sections in Sprint-X 需求清单.md and PROPs, must explicitly include an empty-states / defaults / boundary-values section.

**Example, revised after F-PREP-1 acceptance**:
```
### User-input boundaries
- Empty quantity → default (count: 5 / decimal: 0.2)
- Numeric string → corresponding numeric value
- Explicit 0 → intentional zero (distinguish empty → default from explicit 0 → actual 0)
- null / undefined / "" → three-state interception (topic M: consistent empty-form handling)
```

**Implementation**: Add it to `agent/rules/写PRD.md` during PROP-018 P6-2 closeout.

### Decision 5: Four role categories (topic AF; PM self-corrections #38/#39)

**Responsibilities**:

| Category | Owner | Scope |
|---|---|---|
| **Framework maintenance** | **PM directly** | agent/ .md files + tools/ + root AGENTS.md / 状态.md / README.md + PROP / ADR / RETRO editing + topic backlog management |
| **Application code** | Claude Code, with a PM handoff card | {{APP_REPO_DIR}}/src/ features + {{APP_REPO_DIR}}/android / {{APP_REPO_DIR}}/package.json |
| **Test code** | Claude Code, with a PM handoff card | Mock design, describe blocks, and cases in {{APP_REPO_DIR}}/src/__tests__/*.test.js |
| **End-to-end verification** | Codex, after Claude Code finishes | Version bump + APK build + vitest recheck (N/N, zero regression) + device smoke + screenshots + git commit/push under ADR-016's six Class B conditions |

**Counterexamples: my PROP-018 P1/P2 mistakes**:
- PM asks Claude Code through a handoff card to change `agent/CHANGELOG.md` ❌ — the PM should do it.
- PM asks Claude Code through a handoff card to change `tools/check-operating-system.ps1` ❌ — the PM should do it.

**Two meanings of testing** (topic AF.2; PM self-correction #39):
- **Writing test code**: Claude Code writes mocks, describe blocks, and cases.
- **Running tests**: Claude Code self-checks; **Codex performs the final recheck** for N/N and zero regression. **Device smoke testing belongs exclusively to Codex**.

**Implementation**: Add these categories to the Class A / B lists in `agent/agents/AI边界.md` during PROP-018 P6-2 closeout.

## Key tradeoffs

### 1. Consolidate six topics into one ADR or split them into six

**Consolidate**: The six topics share meta-rules and cross-tool safeguards; one compact record avoids archive growth. If a topic evolves substantially, such as automatic bash-versus-PowerShell comparison for topic D, split it into ADR-023+ later.

### 2. Topic AG (PS1 unit tests) is outside PROP-018

AG is an evaluation candidate, not mandatory remediation. Pester takes 0.5-1d plus test-design work, while **PROP-018 already spans 4-5h**. Defer to RETRO-009 + PROP-019.

### 3. Topic D uses static guidance for the MVP, not dynamic comparison

PS1 on the Windows host cannot directly read the Cowork bash view, and automatic cross-tool synchronization is complex. **The MVP is awareness plus procedural defenses**. A future ADR-023 candidate could add "PS1 baseline output + Cowork diff verification."

### 4. ADR-022 title

Choose the current long, self-describing title, "Cross-tool synchronization + AI configuration reclassified from Class C + role boundaries," to improve future keyword searches.

## Consequences

### Benefits

- **Explicit source authority**: Ten field cases from topic D become procedural rules, replacing intuition about bash / Read / PS1.
- **A standard configuration reclassification pattern**: Reuse PROP-012's git push model, with six safeguards and the field correction from DEV to APIKEY-presence gating.
- **Disclosure tiers**: Topic X gains an explicit override process and a standard key-rotation mitigation.
- **Stronger PRDs**: After the same failure in RETRO-007 card 1 and F-PREP-1 #07, templates require empty states and defaults.
- **Fixed role boundaries**: Lessons from PM self-corrections #38/#39 become systematic and avoid confusion in later PROPs / features.
- **A PS1 testing candidate**: Topic AG remains in RETRO-009 + PROP-019 to avoid expanding PROP-018.

### Costs

- **ADR-022 length**: About 9-10KB; six topics exceed the usual ~5KB ADR, but Docs/ is exempt.
- **Pending `agent/rules/写PRD.md` update**: Add the empty-state / default section template at PROP-018 P6-2 closeout.
- **Pending `agent/agents/AI边界.md` update**: Add four role categories and explicit framework maintenance to the Class A / B lists.
- **Learning curve**: New tools, such as future Cursor / Devin, must learn the source-priority rules.

### Risks and mitigations

- **Topic V safeguard ③ needed a field correction**: Debug APKs have `DEV=false`; the gate now checks `VITE_DEV_DEFAULT_AI_APIKEY` presence, fixed in PROP-018 P2.
- **Topic D's static reminder may be ignored**: PS1 P4e prints it on every run for repeated cross-session awareness. A future ADR-023 candidate can add dynamic comparison.
- **Topic X mitigation depends on manual rotation**: A second or third disclosure may require promoting partially sensitive information to highly sensitive, tightening the threshold.
- **Ambiguous category boundaries in topic AF**: For example, {{APP_REPO_DIR}}/build-apk.bat is both framework and an application pipeline. Default to direct PM ownership: framework takes precedence.
