# ADR-039 · Unified borrowing area and lifecycle governance

- **Status**: Current
- **Date**: 2026-07-18 (implementation accepted on 2026-07-19; final-review hardening completed on 2026-07-22)
- **Decision responsibility**: Project PM orchestrates; Operating System PM drafts and implements; testing-related PMs accept.
- **Related**: [PROP-004](../../../确认改动/已审批/已完成/PROP-004-2026-07-18-完整借鉴闭环.md) · [Design specification](../2026-07-18-借鉴闭环-设计规格.md) · [Design appendix](../2026-07-18-借鉴闭环-设计规格-附录.md)

> This ADR has passed implementation, temporary-instance dogfood, and fresh P4a-P4t acceptance on both the template and a generic project. It is the current decision boundary for the unified borrowing lifecycle.

## Context

ADR-021 introduced reverse learning from sibling projects, but its historical design focused on entry points, health checks, and lightweight logs. It lacked a unified executable contract recording the source, frozen version, adoption or rejection rationale, implementation destination, and verification. Temporary conversations or external paths allow source drift, mix decisions with implementation, and can introduce project-specific facts or application runtime dependencies into the template.

Borrowing must now become a lifecycle that templates can instantiate, instances can audit, and checkers can verify offline, without adding PM roles, changing existing path allowlists, or executing source content. Reliable Windows PowerShell 5.1 compatibility and template/instance detection are prerequisites.

## Decision

1. **One unified root.** All borrowing metadata lives in root-level `借鉴区/`. The template contains only README, card templates, ignore rules, and empty directory scaffolding, with no second active source index. Source cards and item cards in an instance are the respective single sources of truth for source facts and item facts.

2. **Immutable source captures.** Items pin `source_id + capture_id + fingerprint`. Once an official capture is ready, its identity and fingerprint fields cannot be rewritten. Refresh must not rewrite older captures. Return REUSED only when the complete fingerprint is unchanged and matches the stable facts of the sole valid ready capture. Changed fingerprints create new captures; older items retain their original binding and never follow updates automatically. Retirement only appends administrative history and first requires proof that no active item references the capture.

3. **Separate lifecycle status from decisions.** `lifecycle_status` represents process progress; `decision` independently records `pending / adopt / adapt / reject / defer`. Every state change appends history. Closure conditions depend on the decision branch. `adopt / adapt` targets must be actual safe regular files. Fresh bullets use the machine format `time / command / exit / evidence` and cannot predate the most recent transition into `verifying`. Their evidence must be exactly `borrowing-evidence/v1`, binding the bullet fields and a digest of the complete target-file inventory. Arbitrary nonempty files or staging members cannot stand in for evidence. Closed-item seals detect accidental or noncompliant edits; they do not claim to resist malicious writers able to recompute both body and seal.

4. **Explicit root modes and no-overwrite instantiation.** Template roots use `.czxt-template-root`; instance roots use `.czxt-project-root`. Both present or both absent is a hard failure. Instantiation creates only the project marker, never copies the template marker, and copies only empty borrowing scaffolding without overwriting existing sources, items, or local caches. During planning and immediately before writing, `AppRepoDir` and every copy, directory-creation, and direct-write target must be proven inside the project root with no reparse ancestors. File updates use two no-overwrite moves: `target→backup`, then `prepared→target`. Bind project root, source, and target to physical final paths through handles and `GetFinalPathNameByHandleW`; reject physical-alias overlap such as `subst`. Register each installed or rewritten output immediately in the output manifest. Before the final marker/success output, retain read-only shared leases on every manifest entry. `状态.md` is a required transaction output: `-Force` first binds and preserves its existing five-part state, skips template overwrite, then unconditionally performs a CAS append against manifest ExpectedState. If the file disappears or becomes a directory after the snapshot, hard-fail without a marker or success output. `-Force` merges existing directories file by file in place and must not create nested copies. Instantiation is a collection of per-file transactions, with no promise of global atomic rollback on failure. Preserve auditable remnants when ownership is unclear; never overwrite or guess what to delete.

5. **Gate 0 first.** PowerShell scripts in the formal scope must satisfy Windows PowerShell 5.1 parsing and UTF-8 BOM contracts. Mode contracts, BOM preservation after instantiation, and failure-exit propagation must pass before core capability and P4t acceptance.

6. **Read-only, offline P4t.** P4t checks only modes, scaffolding, card schemas, references, state transitions, closure conditions, path safety, cache consistency, and zero application dependencies. Exit codes distinguish pass, warning, and hard failure. Each public leaf independently determines actual RootMode from a safe marker and rejects forged Mode values. Identify application text by strict decoding rather than a limited extension list. Block root-relative `借鉴区/` at path-token boundaries; oversized suspected text fails closed; binaries are not executed. Deployable build or runtime outputs such as `dist / build / .next / target / out` must not be skipped wholesale. Isolation scans fully read files ≤8 MiB on three passes. For larger files, all three passes bind only identity, length, and the first 64 KiB; they explicitly do not guarantee detection of same-identity, same-length tail changes outside the observed range. The three read passes share one fail-closed budget: at most `20000` files, `100000` directory entries, and `512 MiB` of digest reads. Project-card reads allow `1 MiB` each and `2 MiB` across initial/final reads. P4t does not connect to the network, refresh sources, execute/build/install external content, or repair/write back cards.

7. **One user entry point and a tested machine layer.** The sole operator entry point is `能力资产/skills/借鉴.md`, covering intake, assessment, implementation, and audit. The Skill invokes contract-tested capture façades/helpers to freeze Git, local, or web sources. The machine layer does not create a second user workflow or expose source execution.

8. **Neutral template, zero direct application dependencies.** The template must not carry source-specific code, source cards, or item cards. Application code, dependency configuration, build scripts, and runtime reads must not directly consume `借鉴区/` or source caches. Approved content must be copied or adapted into an existing target path and verified under that path's responsibility boundaries. Documentation source links and audit identifiers are not runtime dependencies.

9. **Fixed acceptance boundaries.** Completion evidence proceeds through Gate 0, core contracts, positive/negative P4t cases, temporary-instance dogfood, dedicated P4s/P4t checks, and the full P4a-P4t health check. None of these acceptance activities connects to the network or executes source content. Without separate authorization, they also do not commit, push, tag, release, publish, or distribute externally.

10. **Closure and metadata fail closed.** Official closure uses only `close-borrowing-item.ps1`: create a candidate from the active card, install it in a no-overwrite transaction, invoke seal, and run full-root P4t. After P4t exit 0, still lock the official card and recheck identity and sealed bytes; cleanup must finish under that lock before success. Restore the original active card only when ownership is proven and `content-deleted` has not been entered. If evidence binds the current official object and only `borrow_id` differs, ownership remains provable and the complete snapshot supports safe restoration. Other `seal-ownership-unproven` cases retain the current official card and staging. After the irreversible `content-deleted` completion point, do not roll back the official card. The staging ownership chain is fixed: atomically create the staging directory relative to a trusted parent-directory handle. Create the first `原活动卡.bin` with handle-relative CreateNew, then write, flush, and bind it on that same handle. Retain its file lease throughout the transaction so the directory stays nonempty. Create candidate `借鉴卡.md` with handle-relative CreateNew as well. Cleanup order is fixed: `Candidate→retained Original→content-deleted→directory`. Validate Candidate through one opened, bound handle and set delete-pending on that same handle. Set delete-pending for retained Original through its retained lease on the same handle. Immediately enter `content-deleted`, then delete the directory through its creation handle. Leave no gap between validation and path opening. Creation failures delete only objects bound to this transaction's handles. After P4t exit 0, acquire the final official-card lock through one OPEN_REPARSE_POINT open. Recheck canonical path, regular non-reparse type, link count=1, identity, length, and bytes from that same handle. Hold this exclusive lease until staging cleanup finishes. Never validate a safe path and then reopen by path. Updating the staging candidate after sealing follows a two-state contract: the official-card ownership snapshot and current staging-candidate snapshot are independent states. Rollback must validate each separately. Do not prematurely change the staging expectation to sealed bytes. After the Set operation in `Set-BctCandidateBytes` commits, update the state object before later checks that may fail, ensuring exception branches see the actual committed candidate. Never overwrite concurrent changes. All identifiers, locators, authorization descriptions, and fact/response metadata entering tracked source cards reuse the same credential detector at normalized input and final rendering. Enumerate capture roots and direct snapshot members exactly by source type; every unknown member is a conflict.

## 2026-08-24 pre-check-in security addendum

- Capture transactions separately bind staging, official captures, existing captures, and P4t components to persistent handles. After an atomic staging move, recheck root/member identity, length, and SHA-256 against the pre-move ledger. Repair reseals between its snapshot and state-file moves.
- Tree sealing no longer retains whole files in memory: Stream SHA-256 through the same file handle using a 1 MiB buffer, retaining only the 32-byte digest. Explicit DFS counts every discovered member, with fixed limits of `20000` members and `536870912` total bytes; exceed either and immediately return `resource-limit`.
- Cleanup consumes only bound objects in the ownership ledger. The initial Git runner and post-move auxiliaries use the same exact ledger. Late ordinary files, same-byte new identities, or native ADS fail closed and preserve unknown objects. If native rename has committed before an exception, refresh truth through the same handle before deciding whether to roll back.
- HealthyReuse and RepairMissingCache add a final binding check after cleanup, placing the transaction linearization point after the final internal action. This contract does not promise that external processes can never modify a directory after return. Late unknown objects are preserved, but registered members may already be partially pending deletion; this must not be described as whole-tree atomic rollback.
- Fresh acceptance: WinPS `362/362`, assets `6/6`, scaffolding `63/63`, documentation `148/148`, top-level capture `8/8`, atomic `10/10`, orchestrator `16/16`, tree seal `10/10` on both x64/x86, exact Git cleanup `3/3`, P4t runner `11/11`; independent security review `P0/P1/P2 = 0`.

## Consequences

### Benefits

- Source versions, assessment decisions, implementation targets, and verification evidence are independently traceable; source refreshes cannot silently change old conclusions.
- The template remains neutral and reproducible. Specific source facts exist only in instances, and application runtimes are decoupled from borrowing evidence.
- Explicit modes, PowerShell 5.1 gates, and P4t contracts turn critical prose boundaries into repeatable checks.

### Costs and tradeoffs

- Each borrowing activity creates source captures, item cards, state history, and verification evidence, costing more than direct code copying.
- No automatic refresh or source execution sacrifices convenience and immediacy in return for determinism, permission isolation, and auditability.
- Offline P4t proves only local contract consistency. It cannot replace human license/permission confirmation or prove that external sources remain online or trustworthy.
- A single root and fixed schema impose migration constraints. Capture façades, P4t helpers, and contract tests also require ongoing maintenance.

### Reversal process

Changing the single root, immutable captures, mode markers, or acceptance boundaries requires a new L4 PROP and successor ADR that defines the superseded scope, historical-card migration, compatibility period, and rollback strategy. Do not rewrite this ADR, old captures, or closed items to fabricate continuous history. These boundaries remain effective until the successor passes complete offline contracts and instance acceptance.
