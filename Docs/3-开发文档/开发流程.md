## Standard five-step cycle, following intake

| Stage | Responsibility and output |
|---|---|
| 0. Intake | Receive the request |
| 1. Align requirements, PM role | Clarify uncertainty and record it in the PRD |
| 2. Design, PM + Dev | UI sketches, data structures, and technical decisions |
| 3. Implement, Dev role | Change code file by file and write tests |
| 4. Verify, QA role | vitest, esbuild syntax, vite build, and manual smoke |
| 5. Release | APK, commit, and `docs/CHANGELOG.md` update |

Each stage produces a visible document, code change, or report.

## 0. Intake

When zlbdh sends a request, Mimi first:

- **Classifies it**:
  - **Small change**: fewer than 50 changed lines, one file, visual adjustment, or documentation → go directly to Step 3.
  - **New feature / refactor / module**: multiple files, data schema, or a new UI flow → use the complete process.
- **Clarifies ambiguity**: use AskUserQuestion for 1–3 questions and establish direction before proceeding.
- **Creates tasks**: record the breakdown with TaskCreate, one task per step.

## 1. Requirements alignment: PM role

Inputs: the user's original wording, current code, and plan documents.

Outputs:

- A PRD entry in `docs/PRD-v3.md`: user story, acceptance criteria, and priority.
- An update to the Unreleased section of `docs/CHANGELOG.md`.

Procedure:

1. Use the user-story format: As a _user_, I want to _do something_, so that _I can achieve a goal_.
2. Write 3–5 acceptance criteria: specific, checkable behaviors.
3. Assign P0 / P1 / P2.
4. List affected files, tables, and APIs.
5. If anything is uncertain, stop and use `AskUserQuestion`; do not guess.

## 2. Design: PM + Dev

Input: the PRD entry.

Outputs:

- Data schema changes in database.js / defaults.js.
- Files to add, modify, or delete.
- UI sketches using ASCII, Mermaid, or prose.
- Potential risks.

Template:

```markdown
## Design: <feature>

### Data
- Table: xxx
- Fields: ...
- Migration: how legacy data moves to v3

### UI
- Entry point: ...
- Main interaction: 1) ... 2) ... 3) ...
- Error states: ...

### Code changes
- + src/features/xxx/Xxx.jsx (new)
- M src/shared/components.jsx
- M src/shared/database.js

### Risks
- Writes above 9KB → use outputs + cp
- ...
```

## 3. Implementation: Dev role

Work file by file. The historical mount write limit was **9105B**:

- Below 8KB: write directly to the target.
- Above 8KB: write to outputs/X.jsx, then overwrite using Bash `cp -f`.
- Above 9KB: write part1 and part2 under outputs, then use Bash `cat part1 part2 > target`.
- Small changes: an in-place Python `re.sub` is the preferred method.

Verify file completeness immediately after each edit: inspect the ending with `tail -3` and size with `wc -lc`.

## 4. Verification: QA role

All three layers must pass before completion:

| Layer | Command | Passing criterion |
|---|---|---|
| Syntax | `node syntax-check.mjs` | All checks pass; 0 failures |
| Unit tests | `npm test` | 33+ tests pass |
| Production build | `npx vite build` | 0 errors and a bundle report |

Optional fourth layer: manual smoke tests across five tabs, a check-in, an accounting entry, and an AI briefing.

## 5. Release

- Move Unreleased entries to vX.Y in `docs/CHANGELOG.md`.
- Ask the user to run `npm run android:build-apk` on Windows.
- After the APK is built, run smoke tests and transfer it to the phone.

## Known technical constraints at the time

| Constraint | Response |
|---|---|
| Mount write limit of approximately 9105B | Use outputs + cp or concatenate parts |
| Edit tool occasionally truncates files | Prefer in-place Python edits or complete-file writes |
| No Android SDK in the sandbox | Build APKs on the user's Windows machine |
| Slow sandbox npm install | Retry in 35-second intervals; approximately 60–90 seconds total |
