## When to use it

| Scenario | Appropriate? |
|---|---|
| Taking over a project and assessing its development framework's maturity | ✅ |
| Assessing a project before adding a PM/AI framework | ✅ |
| Growing disorder, lost context between tools, or unclear processes for new features | ✅ |
| A project just starting out, with fewer than 50 lines of code | ❌ Too little to assess |
| A solo project or short-lived tool | 🟡 May be excessive; choose the 5–6 most relevant dimensions |

## Full prompt: copy to the target AI

````text
You are this project's PM / architect. Perform a development operating system health check of the rules, processes, and collaboration mechanisms supporting application development.

=== Background ===

Think of application code, the core product, as bread. The development operating system is the tooling, processes, rules, and collaboration used to make it.

Many projects focus entirely on the product while neglecting these supporting tools. Disorder grows, context is lost when switching tools, processes for new features become unclear, and rules drift away from reality.

This assessment scores those supporting tools.

=== 19-dimension checklist ===

Rate each dimension: ✅ Complete / 🟡 Partial / 🔴 Missing / 💡 Suggested improvement.

[A: Requirements management]
1. Are PRDs / requirement lists structured documents?
2. Can requirement changes be traced through version history?
3. Are business requirements separate from technical tasks, preventing the PM from directly handling implementation details?

[B: Change classification]
4. Are changes classified, for example L1 typo, L2 bug fix, L3 feature, L4 architecture?
5. Does each level have an appropriate approval process?

[C: AI / tool boundaries]
6. Are permitted and prohibited AI actions explicit?
   Pay special attention to sensitive actions such as git push, API keys, and deleting user data.
7. Do rules distinguish automatic actions, actions requiring prior approval, and actions that must never be performed?
8. Must the AI look up rules before sensitive actions rather than rely on memory?

[D: Cross-tool / cross-session collaboration]
9. Are handoffs among IDEs, CLIs, browser AIs, and terminals standardized?
10. Is there a cached cross-session state to avoid rebuilding context each time?
11. Are handoffs structured, such as a six-section card and chat items ①–⑥, or merely prose summaries?

[E: Decision records]
12. Are important architecture decisions recorded in ADRs?
13. When reversing a decision, must a new ADR be written while preserving the original?

[F: Project self-checks / health]
14. Are there automated or partly automated checks for file sizes, documentation consistency, and counts?
15. Is there state inference: proactively reconciling documentation with actual status?

[G: Retrospectives / learning]
16. Are retrospectives scheduled, for example after every three L3+ changes?
17. Are proposed improvements tracked to prevent suggestions from being forgotten?

[H: Process versus reality]
18. Is there a feedback → recognition → governance cycle when rules are too strict, tools change, or user preferences change?
19. Are exceptions recorded, with a PROP required when the same exception occurs a second time?

[I: File sizes / tool limitations]
20. Are there file-size rules tailored to actual tool capabilities rather than one uniform limit?

=== Output format ===

Use this report format:

```
🔬 Development Operating System Health Report — <project> — <date>

[Overall score]
X/19 ✅ Complete / Y 🟡 Partial / Z 🔴 Missing

[Strengths: 3–5 concrete points]
1. ...
2. ...

[Key gaps: ordered by priority, no more than 5]
🔴 P0 — <gap> — Address immediately → Reason
🟡 P1 — ...
🟡 P2 — ...

[Improvement path: start with the lowest-cost steps]
Step 1 (half a day): ...
Step 2 (1–2 days): ...
Step 3 (1 week): ...

[References]
For an example of an established development operating system, consult another project's framework:
- agent/{agents,workflows,skills,rules,mcp}/ — Five semantic groups
- 确认改动/{待审批,已审批/{进行中,已完成,已弃用},拒绝}/ — PROP lifecycle
- 交接区/{待接手,已接手,历史归档}/ — Cross-tool handoff event stream
- Docs/{1-需求文档,3-开发文档/adr,7-复盘}/ — Long-term documentation
- 状态.md — Cross-session snapshot
- Practical records: 14 PROPs / 18 ADRs / 5 RETROs

[One-sentence assessment]
Where can an improvement make the greatest difference to this project's development operating system?
```

=== Execution rules ===

- Inspect what exists and what is missing; do not assume what the project should have.
- Recommend practices appropriate to the project's current stage; do not copy another project's rules wholesale.
- Prioritize whether a gap blocks development or prevents expensive reversals later.
- If a rules document conflicts with actual practice, mark the dimension 🟡 Partial and explain why.
- Suggest a minimum viable version; do not start by proposing 14 PROPs.

=== Start here ===

1. Inspect the project root with ls / find.
2. Read README.md if available, and main / index files to identify the project type.
3. Search with grep -r "ADR\|PROPOSAL\|RETRO\|交接\|状态.md" for existing framework elements.
4. Assess each of the 19 dimensions.

Then produce the report.
````
