# Reusable Prompt: Improve a Development Operating System

> 📦 **Type**: Framework asset reusable across projects, paired with `通用提示词-开发操作系统体检.md`.
> 📅 **Created**: 2026-05-12.
> 🔗 **Source**: This project's ({{PROJECT_NAME}}) PROP-014 three-level process-first triage and accumulated RETRO experience.
> 🎯 **Purpose**: Lead improvements to the gaps exposed by a development operating system health check.

> ⚠️ **Historical template notice (2026-06-15)**: This early cross-project improvement prompt is not a current {{PROJECT_NAME}} execution rule. The current implementation cycle begins at `操作系统/07_完整工作流/实施循环.md`.

## When to use it

| Scenario | Appropriate? |
|---|---|
| After obtaining a report from the [health-check prompt](通用提示词-开发操作系统体检.md) | ✅ Use the pair together |
| Deciding which gaps to address first | ✅ Use as a thinking framework |
| No key gaps in the health report | ❌ Unnecessary |
| Very early project with fewer than 10 files | ❌ The assessment itself has little value yet, and improvements are premature |

## Core design

| Feature | Description |
|---|---|
| **Limit overload** | No more than 3 immediate actions and 5–10 backlog items |
| **Reuse meta-rules** | Use PROP-014's three levels, 🔴 / 🟡 / 🟢, to classify severity |
| **Pause at each stage** | Each of the five steps pauses so the Owner retains control |
| **Minimal PROP template** | Provide a minimal template for a new project, not this project's complex version; 14 PROPs / 18 ADRs took a month to accumulate |
| **Grow as needed** | Add rules when development requires them instead of installing an entire framework at once |

## Recommended tools

| Situation | Recommendation |
|---|---|
| Continue in the health-check session with its context | **The same AI**, without switching |
| Resume in a different session from an archived report | **Any AI with a PM perspective**: Cowork, Claude Code, or Codex |

## Full prompt: copy to the target AI

````text
You are this project's PM / architect. You have just completed a development operating system health check and produced a report with Strengths, Key gaps, and an Improvement path.

Now lead improvements to those gaps. Follow all five steps below, pausing after each so I can review.

=== Input ===

Read the health report you just wrote, either earlier in the conversation or in its saved file.

=== Step 1: Reclassify with three-level process-first triage ===

The report's P0 / P1 / P2 labels describe importance. Whether to act now depends on whether a gap blocks current development. Reclassify each key gap:

| Severity | Situation | Action |
|---|---|---|
| 🔴 Blocking | Prevents current implementation, testing, or release; work cannot continue without a fix | Fix immediately |
| 🟡 Nonblocking bug | False warnings, inconsistent documentation, or incorrect paths; work can continue, but risk remains | Add to the backlog for a later improvement pass |
| 🟢 Improvement opportunity | Another approach might work better; leaving it unchanged causes no immediate problem | Monitor long term; it may never need implementation |

=== Step 2: Produce three lists: ≤3 immediate, 5–10 backlog, long-term ===

```
🔴 Act now: no more than 3 items
1. <gap> — <why it blocks work> — <minimum viable fix> — <S/M/L estimate>
2. ...

🟡 Backlog: 5–10 items
- <gap> — <long-term effect> — <when to address it>

🟢 Monitor long term: no immediate action
- <gap> — <signal that would trigger action>
```

Pause for the user to review and decide whether to continue.

=== Step 3: Draft a minimum viable proposal for the first immediate item ===

Do not copy the reference project's ({{PROJECT_NAME}}) complex PROP template. That project took a month to accumulate 14 PROPs / 18 ADRs. A new project should start small.

Use this minimal template:

```
# Improvement Proposal: <one-line title>

## Goal
<Desired final state>

## Why now: 1–2 pieces of blocking evidence
- ...
- ...

## Steps
1. ...
2. ...
3. ...

## Tests / acceptance
- [ ] Verification point 1
- [ ] Verification point 2

## Out of scope: prevent expansion
- ❌ Do not implement X
- ❌ Do not change Y

## Estimate
S: less than 1 hour / M: less than 1 day / L: 1–3 days
```

Pause for the user to review and approve the proposal.

=== Step 4: Implement and record ===

Implement the Step 3 proposal. After completion:
- Pass the verification points.
- Add a record to README.md or a new `改进日志.md`: date, changes, and effect.
- If the project involves multiple tools, write a brief 5–10-line handoff for the next tool.
- If it is a solo, single-tool project, the log entry is sufficient; no handoff is needed.

=== Step 5: Continue with the next item or stop ===

After the first item:
- If 🔴 items remain, return to Step 3 for the next one.
- If all 🔴 items are resolved, stop and report: “All blocking items are resolved. The remaining N 🟡 and N 🟢 items are in the backlog. You decide whether to continue with the 🟡 items.”

=== Mandatory overload safeguards ===

- ❌ Do not begin by proposing 14 PROPs.
- ❌ Do not begin by creating the entire `agent/{agents,workflows,skills,rules,mcp}/` tree.
- ❌ Do not begin by creating the complete `确认改动/`, `交接区/`, and `状态.md` infrastructure.
- ❌ Do not write an ADR README index before the first ADR exists.
- ✅ Add rules as development requires them; do not install the entire framework at once.
- ✅ Keep the minimum viable unit: one improvement, one verification, one log entry.

=== Special cases ===

- If the report has zero key gaps, skip Steps 3–5 and say that no correction is required; resume normal development.
- If every item is 🟢, do the same.
- If the project is too early, with fewer than 50 lines of code / fewer than 10 files, explain that the assessment is premature and the first working product should come first.

=== Start here ===

1. Reread the health report.
2. Reclassify key gaps using Step 1.
3. Produce the three lists in Step 2.
4. Pause until I say, “Step 3: do the first item.”

Do not run all five steps without stopping. Pause after each so I retain control.
````

## Pairing with the health-check prompt

1. Start with a new project.
2. Run `通用提示词-开发操作系统体检.md`.
3. Produce the report: the historical 19-dimension score, key gaps, and improvement path.
4. Run this prompt, `通用提示词-开发操作系统修正.md`.
5. Steps 1–2: reclassify severity and create the three lists.
6. The Owner decides.
7. Steps 3–5: implement one item, record it, and move to the next.
8. When all 🔴 items are resolved, report and return to normal development.
