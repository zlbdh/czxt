## 1. F-205 — ErrorBoundary prevents blank screens

### Work

Implemented on 2026-05-08. Each of five routes received a React class ErrorBoundary. Runtime exceptions were recorded in the deviceEvents.error table and displayed through a warm “Mimi had a little hiccup” fallback card. A “Recent small problems” Profile card showed the latest five events. This was L3 work, with five vitest unit tests for serializeErrorPayload.

### What worked

- React's established class-component ErrorBoundary pattern made the implementation straightforward.
- Reused the existing deviceEvents table, defining the payload without a schema change or another ADR.
- “Mimi had a little hiccup 🫧” matched the product's tone.

### Problems

Device fault-injection smoke testing found that **the five boundaries shared one component instance**. After Health failed, switching to Home still showed the fallback. React reused the same component type as one node without resetting its state.

The fix assigned a distinct key, such as `key="health"`, to each ErrorBoundary so each route had an independent boundary.

### Lessons

- Cross-route ErrorBoundary state reuse is a hidden risk; use independent keys.
- Unit tests and builds do not establish device correctness. The three test layers plus smoke testing must exercise at least one fault path on a device.
- Give sibling ErrorBoundary instances distinct keys by default.
- Plan recovery and tab-switching scenarios, beyond simply checking whether the error is caught.

### Next steps

- Add an “independent state required?” decision to the checklist for cross-route wrappers.
- Add this template comment: `// Use a distinct key for each boundary.`

## 2. ADR-004 — Split large files under PROP-001's full B3 plan

### Work

Implemented on 2026-05-08. Nine source files were at least 6500 B, including five above 9 KB. Mount writes around 9105 B repeatedly truncated files, with two actual byte-loss incidents. The B3 plan created 13 small files and rewrote five feature imports. All source files were below 6.7 KB; Home was largest at 6673 B, then a follow-up patch reduced it to 5647 B.

### What worked

- Split by responsibility: HomeStatBar, HomeTaskSections, HomeHydration, HomeWorkout, HomeHabits, HomeAIBriefing, and HomeChat. The boundaries were clear without excessive fragmentation.
- Used Python throughout to avoid Edit/Write truncation, with independently verified stages: components → Home → Timeline → Health → Profile → Accounting → Home v2.
- Sandbox bracket balance, tail completeness, and import-path checks verified replacements. The historical comparison recorded them as 10 times faster than device verification.

### Problems

- During import replacement, Profile.jsx again hit the 8713 B mount-truncation issue and lost its final `);}`. It illustrated the first known constraint: Edit could be more deceptive than Write.
- PROP-001 had omitted Accounting.jsx. It grew from 8162 B to 8288 B after import changes and was split the same day.
- The initial Home split left 6673 B, still near the limit. Extracting two more inline cards brought it to 5647 B.

### Lessons

- The mount write limit was the project's most disruptive physical constraint. The historical guidance—Edit below 6 KB, Python for 6–9 KB, and splitting above 9 KB—came from it.
- Resolving the issue fully saved time: a 6673 B file would cross the limit after a few additions, while the 5 KB range left room.
- PROP-001 recorded Mimi's proposal for zlbdh's decision; ADR-004 recorded the decision and implementation. The two records served different purposes.
- Scan all source areas, including shared, app, and test, rather than features alone.
- Maintain a current high-risk-file section in `rules/code/README.md` and revisit it after changes.

### Next steps

- Propose splitting any .jsx file approaching 6500 B, without waiting for 9 KB.
- Run `wc -c` before writing a commit.

## 3. PROP-003 — Navigation refactor and a separate chat feature

### Work

Implemented on 2026-05-09, including integration after F-203. The five bottom tabs became Today, Health, **Chat**, Accounting, and Timeline. Profile moved to a permanent avatar in the upper-right corner, using PageHeader's rightAction prop and default ProfileAvatarLink.

Created `{{APP_REPO_DIR}}/src/features/chat/Chat.jsx`, moved HomeChat interactions into it, added automatic scrolling, and attached F-203's archive drawer. This L3 change added 16 vitest tests for chatInteraction and Chat; all 66 tests passed.

### What worked

- zlbdh's PROP-003 was clear enough to implement with almost no design disagreement.
- F-203 had already extracted chatArchive.js and ChatHistoryDrawer.jsx, enabling direct reuse.
- An ADR-number collision was caught immediately because F-203 already used 005. Both sides confirmed the correction, and zlbdh updated PROP-003 in Cowork.
- PageHeader's default `<ProfileAvatarLink />` and explicit `null` hiding behavior formed a natural API, requiring almost no changes across five features.

### Problems

- Device smoke testing found the Profile page showing an avatar link to itself. ADR-006 required `rightAction={null}` there, but implementation missed it. Adding that line to Profile.jsx's PageHeader, rebuilding the APK, and reinstalling verified the hotfix.
- Estimated adb tap coordinates missed two or three times before hitting the target. This was an adb/Capacitor WebView automation issue, rather than a project-code defect.

### Lessons

- Check off every ADR requirement during implementation; detailed decisions alone do not prevent hotfixes.
- Moving Profile to the upper-right corner reduced the user path from four steps to one.
- A shared ProfileAvatarLink also worked in Home's custom hero header, providing visual consistency.
- The implementation checklist must include both the ADR's decision and visual-specification sections before smoke testing.
- Before cross-feature migration such as HomeChat → Chat, inspect all references so removal leaves no stale uses.

### Next steps

- Ask what each new feature passes as PageHeader's rightAction.
- Build a reference matrix before migrations: importers and incoming props.

## Patterns across the three changes

### Practices to retain

1. ADRs record decisions and implementation; proposals record the approval chain.
2. Each L3+ change updated the relevant `Docs/3-开发文档/` sections and `需求历史.md`.
3. Extract pure functions and test them with vitest instead of putting all logic in React components.
4. Verify on a device in addition to trusting vitest.

### Recurring problems

1. F-203, ADR-004, and PROP-003 all encountered mount write limits. A soft limit below 6 KB and Python fallback largely controlled them, but every new file still needed a size check.
2. Device smoke testing exposed ErrorBoundary keys and the missing Profile `null` prop. Both missed small ADR implementation details; using the ADR as a checklist is the defense.
3. Repeated adb coordinate errors made automated smoke testing costly. Complex interactions were better assigned to zlbdh for manual verification.

### Remaining Sprint-1 work

The original heading counted five remaining requirements while listing six identifiers: F-001, F-002, F-003, F-006, F-LAYOUT-1, and F-LAYOUT-2. Most were L3 calendar features with the repeated pattern of selecting a day and opening its detail drawer.

Reuse opportunities:

- Adapt ChatHistoryDrawer's slide-up pattern for DayDrawer.
- Apply summarizeChatCounts' pure-function and unit-test pattern to per-day summaries.
- Use PageHeader's established rightAction default for new features.

Potential problems were prop drilling from calendar clicks and empty-state wording for days with no records. The proposed response was a shared useDayDetail() hook for F-001, F-002, F-003, and F-006.
