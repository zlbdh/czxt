## Change 1: PROP-004, restructure rules/ as agent/

### Decision path

zlbdh asked why there were no agents, skills, or workflows directories. The audit found ADR-003's rules/ directory carried several different meanings. PROP-004 led to seven implementation stages, 25 file moves, and path updates in more than 30 files. ADR-003 was marked partially superseded by ADR-007, which became current.

### What worked

- Comparing A, rename; B, split completely; and C, leave unchanged made the decision clear.
- The code boundary held: zero path references in `{{APP_REPO_DIR}}/` were changed.
- Historical records remained as time-specific evidence; a new ADR succeeded rather than erased the old decision.
- Placeholder areas for git, security, and mcp advanced from README-only directories to substantive files.

### Problems and lessons

- This was the first mount-cache incident: Bash byte counts and content lagged behind Edit/Write by several minutes.
- Health-check dimension G incorrectly classified ADR-003's historical decision text as a stale reference.
- Use Read for authoritative content instead of relying on Bash. Add self-exclusion via `--exclude=` and historical-ADR filtering to the health skill.

## Change 2: PROP-005, framework automation to 90%

### Decision path

zlbdh asked whether completed APK and smoke work would be remembered automatically. The audit found 12 semiautomatic bottlenecks. Four phases and 13 actions added three files—state inference, F-number rules, and `状态.md`—and modified seven. ADR-008 became current, closing all 12 concrete issues.

### What worked

- Define automation honestly: the AI responds to prompts rather than running as a daemon. This set realistic expectations.
- State inference and health checks complemented rather than duplicated each other: health versus progress.
- The reported targets were measurable: 70% less user-initiated reporting and 75% fewer cross-session information gaps.
- The proposal workflow held even when the user asked to do everything: write PROP-005 and archive under section A before implementation.

### Problems and lessons

- Mount-cache severity became clear: Bash wc -c reported ADR-008 as 419 B, while Read showed a complete 6.5 KB document.
- Bash `[ -z ]` repeatedly misjudged strings containing newlines, as in earlier v9, v15, and v17 checks.
- Bash commands immediately following Edit may read stale cache. All health skills received known-limitations sections requiring Read verification.

## Change 3: PROP-006, framework v2 from 90% to 95%

### Decision path

The v20 health check found six incremental improvements. zlbdh selected four and deferred items 5 and 6 to RETRO-003. PROP-006 proceeded through four stages; ADR-009 became current and triggered this retrospective.

### What worked

- Stop at an appropriate point: implementing four of six improvements avoided over-optimization.
- Reorganize the DoD into five core checks plus linked extensions instead of allowing endless growth.
- Prevent duplicate truth sources by defining `状态.md` as a cache, not authoritative truth.
- Make session startup explicit with warnings at the top of both INDEX and README.

### Problems and lessons

- A typo in README's state-inference filename was corrected immediately.
- Inference 3's simplified RETRO threshold, `3 × (count+1)`, was inaccurate. It should count three additional L3+ changes since the previous RETRO.
- Health checks must examine historical increments, not only numeric thresholds.

## Five recurring insights

1. **Framework changes are harder to verify than business code.** Code has tests; governance lacked an equivalent, often exposing defects only through later use. Defend with health checks, state inference, and retrospectives.
2. **Mount caching is a Cowork limitation, not a project defect.** Edit/Write use direct Cowork access and apply immediately; Bash reads through a mount and may lag minutes. Work around the limitation using the Read-first principle in every skill.
3. **One maintenance point is not the same as one directory name.** ADR-003 used rules/ for everything to centralize maintenance, creating semantic confusion. ADR-007's agent/ root with five subdirectories achieved both clarity and centralization. Evaluate both dimensions in future decisions.
4. **Automation does not mean unattended operation.** The AI needs a prompt. The recorded 90% automation meant minimizing the user's reminder burden; do not promise an unattainable 100%.
5. **Marginal returns diminish across iterations.** v9→v10→v11→v15 found two to four real problems each round, yielding high returns. v15→v20→v22 found six monitoring-level improvements per round, yielding moderate returns. After v22, three more rounds might reveal only one real issue. The framework had reached a steady state where reflection was more valuable than another iteration.

## Main meta-level lesson

Framework perfection is an asymptotic goal. Each fix can reveal a finer gap. Stop deliberately when marginal improvements dominate. After v22, attention should return to F-001 device installation and the F-006 habit calendar.

Revisit the next framework improvements after one or two weeks of real use, when meaningful friction can be distinguished from negligible issues.
