## 3. Problems and inefficiencies

### 1. Duplicate profile sources

The old db.profiles table, containing height/weight/age/goal/bodyFat, overlapped with the new db.userProfile singleton, id=1, with five sections and a personality mode. Literal execution of "insert before existing content" created two Profile cards that users might fill twice. Claude Code's implementation, Codex's push handoff, and Sprint-2 closure all flagged it. Open PROP-015 and choose migration, read-only legacy access, or merging.

### 2. Simple deviation keywords caused false positives

The current includes check matched the Chinese phrase meaning "Can I eat"; even an ordinary question meaning "Can I have a meal?" triggered deviation mode. Claude Code flagged this in F-CHAT-23-DEVIATION. Improve precision through regular-expression boundaries or LLM judgment.

### 3. Three files remained above the Cowork warning threshold

- `{{APP_REPO_DIR}}/src/app/useAppData.js`: 6789 B.
- `{{APP_REPO_DIR}}/src/shared/database.js`: 7084 B.
- `{{APP_REPO_DIR}}/src/features/profile/ProfileSections.jsx`: 7290 B.

Under PROP-013 these were soft recommendations for Cowork and below the 8 KB guidance for Claude Code/Codex. They did not block current work, but components should be extracted before further expansion.

### 4. State freshness depended on prompt discipline

F-CHAT-3's reconfirmation before key decisions was only a system-prompt instruction. There was no structured sessionMemory mechanism tracking stale decisions, so LLM behavior could miss it. Consider stronger support in Sprint 3.

### 5. Behavioral LLM testing depended on device smoke tests

The 211 Vitest tests checked prompt composition, such as included fields. Actual late-night behavior, three-mode tone, and deviation detection required ADB and questions to Mimi on a device. This was costly and not automated. Consider mock-LLM replay tests.

### 6. PM self-correction

PM supplied features/me/ instead of features/profile/ without searching project structure. The earlier package.json version violation was already recorded as PROP-012 signal 3. PM should use the new pre-sensitive-operation search reminder itself.

### 7. Four long-term memory-system weaknesses

zlbdh's question triggered an audit identifying no topic view, such as Git rules spread across three directories; accumulated history without a pruning mechanism, already 18 handoffs and potentially 100 later; a growing accepted-card list at the top of `状态.md`; and no global loading limit when a user asks to read every ADR. None blocked business delivery. Consider proposals numbered 015–018 after Sprint 3, as provisionally recorded at the time.

## 7. Meta-level insights

1. **The framework began driving business work.** RETRO-005 still focused on rules changing rules, PROP-011/012. RETRO-006 saw all five Sprint-2 features pass through the full delivery pipeline. Rules consumed less attention and supported delivery speed.
2. **Tool behavior can converge through clearer rules.** RETRO-004/005 exposed screenshot and handoff-format differences between Claude Code and Codex. PROP-014 substantially aligned their behavior. The benefit was reduced randomness across tools.
3. **Response time improved from days to hours.** PROP-012 followed three signals over about two days; PROP-014 followed one signal and completed within an hour. The two-exception proposal trigger also improved PM's own habits.
4. **Identify the risk, offer options, and let the user decide is a project principle.** It applies to all deviation modes, PM proposals, and v3.0 PRD principles for flexibility and system-state awareness. zlbdh repeatedly emphasized avoiding unconditional agreement.
5. **The five-layer memory structure stabilized.** Truth, work, rules, snapshots, and indexes had distinct responsibilities. The five startup steps loaded about 50 KB, reported as roughly 7% of context. Topic views, accumulated history, state-file growth, and loading limits were long-term nonblocking concerns. See `Docs/3-开发文档/通用-记忆系统架构.md`, completed during this retrospective.
6. **Self-correction counts do not alone indicate failure.** PM recorded three corrections involving the wrong path, version violation, and PROP-014 short format. User feedback or tool correction led to rule changes, extending RETRO-004's lesson about testing rules against their own mistakes.
