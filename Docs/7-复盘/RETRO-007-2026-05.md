## 3. Problems and inefficiencies

### 1. PM did not specify the empty-state mechanism

F-PLAN-1 acceptance required guidance for an empty profile, but the prompt did not distinguish a true empty state from default-value fallback. Claude Code supplied defaults. Codex's fourth smoke check failed, requiring a return and roughly 30 extra minutes. Explicitly state implementation intent for empty/default/fallback/unavailable cases rather than leaving it implicit.

### 2. PM search missed five readers during PROP-015

The draft named only three callers. Claude Code found five more: Home, Health, calcTargets, analyzeMealImage, and HealthMeals. Search reads such as data.X, profile.X, and props.profile as well as writes such as saveX/dbX.

### 3. PM self-correction 5: the three-target card was on Health, not Home

PROP-015 referred to three numbers on Home, but the card was actually on Health. Codex used pass-with-note. PM should search or inspect the interface before writing smoke acceptance rather than rely on memory.

### 4. PM self-correction 6: unspecified empty-state behavior

This is the F-PLAN-1 mechanism problem above.

### 5. dailyBriefing used rules rather than an LLM

F-CHAT-4 generated content such as low recent protein intake from mealRecords through rules. LLM-generated briefings were a Sprint-4 proposal candidate.

### 6. inventoryMonitor was only a Sprint-3 skeleton

It returned an empty array because userProfile had no inventory field. Sprint 4 could add userProfile.inventory for items such as skincare products and supplements, together with complete inventory estimation.

### 7. Today did not refresh at midnight

A briefing left open across midnight did not switch days until the app refreshed. Consider useEffect with a timer or focus refresh as a Sprint-4 edge-case fix.

### 8. Consecutive anomalies deliberately excluded today

The three-day missing-spending detector excluded the current day to avoid premature warnings before lunch. This reasonable design needed documentation so device smoke tests would not misclassify it.

### 9. Five posture exercises took six minutes, versus ten in the PRD

PM accepted six minutes as more approachable. Future PRDs should use justified ranges instead of arbitrary exact durations.

### 10. SLEEP_PLAN had a fixed start date

The four-week plan began at hardcoded 2026-05-12, although users could start later. A Sprint-4 start-adjustment button could record the actual date.

### 11–14. Architecture and size debt

- timelineBuilder.js: 6918 B, retained.
- Health.jsx: 6331 B, retained.
- dailyBriefing.test.js: 6272 B, nearing the warning band.
- TaskDetailModal.jsx and TASK_HINTS: retained dead code.

Open PROP-016 before Sprint 4 for size-driven responsibility splits and dead-code removal.

### 15. Memory-system weaknesses remained unchanged

Topic views, state-list folding, loading limits, and historical pruning carried over from RETRO-006 without progress.

### 16. Training time defaulted to one hour after work

TodayTimeline hardcoded this slot. Sprint-4 F-TRAIN-1 should allow a user-defined training time.

## 7. Meta-level insights

1. **Resolve prerequisite governance debt before feature work.** PROP-015 took about half a day and benefited six work items, five business features plus the proposal. Treat such blockers as primary work, not indefinite backlog.
2. **A quality-gate return demonstrates verification, not failure.** The extra 30 minutes prevented a known bug reaching production. Encourage Codex to report a failure when evidence supports it.
3. **Development and PM should supply each other with evidence.** Claude Code's 19 candidate issues saved an estimated 30% of PM's issue-inventory effort. Collaboration is reciprocal, not one-way management.
4. **Falling RETRO action completion signals squeezed improvement capacity.** The drop from 100% to 33% justified a one-to-two-day framework window in sprint planning.
5. **Six PM corrections showed insufficient source inspection.** The recorded cases were the features/me versus features/profile path; version-rule violation; overapplying the short handoff to the owner; five missed readers; the misplaced Home target card; and unclear empty-state implementation. All reflected reliance on memory rather than grep/Read. The sensitive-action reminder from RETRO-005 problem 1 and the PROP-014 demonstration helped, but source-inspection habits remained incomplete.
6. **Growing test counts indicated a rising quality baseline.** The historical summary reported Sprint 1 at 96, Sprint 2 at 211 (+115), and Sprint 3 at 399 (+188), with roughly 15–20 new tests per feature and recorded averages of 16 for Sprint 2 and 31 for Sprint 3. These historical baselines differ from some closure tables above and are retained as originally stated. Test density roughly doubled, alongside the discipline established by PROP-013/014.
