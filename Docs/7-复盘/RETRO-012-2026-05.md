## Problems

PM corrections 54–58 accumulated. On May 20 from about 09:30 to 15:30, approximately six hours passed without a state-tracking row. ### 2. Issue generation exceeded closure

The backlog grew from 14 issues at Sprint-5 end to more than 30 mid-Sprint-7. Repeated requests to stop indicated that framework work was creating more complexity than value. After zlbdh approved enhanced option C and delegated routine decisions, PM entered maintenance mode. Repeated self-correction still showed recurrence of the same pattern.

### 3. Unit-test success again failed to predict device behavior

F-NIGHT-1's 70-character reply against an arbitrary fewer-than-50-character criterion and W-3's gated prompt path both passed incomplete unit-level assumptions but failed device checks. Candidate CC, evidence-based acceptance and tests covering actual device call paths, now had two practical examples and became a tenth-meta-rule candidate.

## Three lessons

1. **Tests must cover the path used on the device.** W-3 v1 tested buildPersonaPrompt in isolation, missing that the actual path called it only under deviation gating. v2 added real-path regression coverage. Future acceptance criteria should identify which device call path each test represents.
2. **Framework work has a complexity threshold.** When issue generation outpaces closure, PM should enter maintenance mode, freezing new proposals, RETROs, and memory records and prioritizing business delivery. The historical decision made maintenance mode the Sprint-8 default, with new documents only when zlbdh explicitly triggered them or feature delivery required them.
3. **AJ tracking needs an external trigger.** Verbal role changes without decision-checkpoint or state records were insufficient in long sessions. PROP-027 option A recommended a mandatory tracking check in short-chat section ⑥, explicitly stating how many PM-transition rows were added.
