## 📚 Three engineering patterns proposed for the meta-rule pool

### 1. Three #95 bare-word-in-comment collisions: formalize the pattern 🔴

v3.19's `/normalizeEvent/` matched a comment about bypassing normalizeEvent; v3.20 repeated the pattern; v3.22's `/查看食谱/` matched a Modal comment explaining that F-F2/F-F4's recipe-viewing feature was not copied. All three came from **source-grep bans that matched bare words also used in explanatory comments**.

**Rule:** Source-grep bans must target **code identifiers**: calls with parentheses such as `fn\(`, component names such as `RecipeDetailModal`, or import paths. Never target bare natural-language terms that appear in comments/documentation or function names without the call delimiter. The v3.22 implementer caught and corrected this independently and documented it in a comment. This retrospective proposes a meta-rule; Knowledge PM will assign its ID.

### 2. v3.20 device blocker: passing unit tests does not prove the LLM chain works 🔴

All 1237 unit tests passed for the second weekly-recurrence stage, yet a request for a follow-up every Wednesday went through ordinary chat on the device. Two causes combined: prompt rule ① classified time-bound temporary plans in a way that set recurring items to isEvent:false; normalizeEvent's `if(!date||!startTime)return null` silently discarded recurrence without a date/time anchor. Monthly recurrence happened to pass because its date-of-month wording supplied an anchor; weekly recurrence lacked one.

**Underlying cause:** The LLM behavior layer had no deterministic test. Pure-function tests did not cover LLM output shape → normalization → card creation.

**Rule:** Every new LLM output shape—frequency, scenario, or field—must add a deterministic **mock LLM output → normalize → card-ready** test. The v3.20 fix added a normalizeEvent fallback and a mock contract, bringing weekly/yearly parsing failures into vitest coverage. The fix combined two safeguards: permit the scenario in the prompt and fill only missing normalization values, with three structural guarantees against regressions.

### 3. Frequent stale/truncated Cowork mounts: retain the defensive workflow

Proposed ADR-025 addendum. Roughly eight incidents occurred in this session: Profile appeared as 7507 versus 7850 bytes; EventCard as 6217 versus 8059; a false Git diff truncation showed `isEventActiveOn` ending in `return fal` although that function was unchanged; defaults.js displayed an empty diff; index.js showed a false “2M versus three changes” discrepancy; and 状态.md exhibited a frozen tail, drifting line numbers, and delayed cache updates.

**Practically verified workflow:**

1. Read **committed** content with `git show HEAD:<path>` to bypass the mount cache and truncation through the Git object store.
2. **Git status/diff metadata was trustworthy.** `wc -c` and Read were unreliable for files already read in the session, but reliable for newly created files.
3. For append-only files such as 状态.md, use only `>>` with O_APPEND, writing at the real EOF without clobbering. Never use read-modify-write: writing back stale content can erase another writer's rows. Delayed readback was common and no rows had been lost; **do not append twice**.
4. **Final integrity evidence came from build + vitest in the implementer's/Codex's actual shell.** Truncation causes syntax errors and build failure. Cowork checked metadata and implementation sections while stating its limitations honestly.
