# PM Self-Correction #64 — PM Roles Must Not Be Bound to Particular Tools ⭐⭐⭐

## Summary

Role definitions used tool names—Cowork PM, Claude Code PM, Codex PM—locking the roles to tools and contradicting the operating system's portability across tools.

## Trigger

**Time:** 2026-05-21 23:55 through 2026-05-22 00:00.

1. While drafting task #95's v4.0 target vision, PM wrote five internal roles under Cowork PM, Development PM “Claude Code,” and Test and Release PM “Codex.”
2. In four corrections, zlbdh emphasized that Cowork, Claude Code, and Codex were replaceable tools and must not limit the system.
3. PM recognized that naming roles after tools removed that replaceability.

## Causes

- The target vision conflated tools and roles.
- In the then-eight-PM matrix, six roles used responsibility names while two new roles used tool names.
- The naming philosophy was inconsistent: role names and tool names were mixed.
- Correct distinction: **PMs are abstract collaboration roles; tools are replaceable execution environments.**

## Implemented safeguards

Revised `操作系统/06_工具治理/操作系统终态愿景-v4.0-2026-05-21.md`:

1. The eight-PM matrix became Project PM, five decision PMs, Development PM “Implementer,” and Test and Release PM “Closer,” all tool-independent names.
2. Added §2, the tool/runtime matrix, explicitly separating abstract PM and tool layers.
3. Cross-tool handoffs, short chat summaries, 状态.md, PROP/ADR/RETRO, and decision-checkpoint use plain Markdown and remain tool-independent.
4. Added PM/tool decoupling to the v4.0 industry comparison, described in the historical vision as a distinctive innovation.

## Repeated pattern

- Similar to #60, but deeper: naming constrained system portability.
- Similar to #61's role/workspace naming inconsistency; both concern naming philosophy.
- A prerequisite for v4.0: removing tool binding enables open-source use and reuse across projects.

## Meta-rule candidate

**Issue CT: PM roles must not be bound to specific tools.**

- Trigger: defining a new PM or drafting framework documentation.
- Actions: use abstract responsibility names without tool names; maintain runtime mappings separately, with `操作系统/01_架构/工具载体矩阵.md` proposed; use plain Markdown for cross-tool handoffs, summaries, and decision records.
- Evidence: #64 and the v4.0 vision rewrite.
