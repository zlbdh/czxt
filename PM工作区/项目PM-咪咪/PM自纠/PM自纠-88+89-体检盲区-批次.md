# PM Corrections #88 and #89 — Health-Check Blind Spots

> Trigger: comprehensive operating-system review on May 28, 2026, followed by PROP-042 splitting work, revealed two quality issues. Recorded together under issue CN v2 because both concern health checks.

## #88: PM-产品经理.md was incorrectly classified as residue

At PROP-042 initiation, the report called `PM-产品经理.md` obsolete residue and recommended deleting it in one minute with zero risk.

Comparison with the replacement showed:

- `产品PM-需求拆解者.md` explicitly absorbed and superseded the old file while retaining it as a historical record under PROP-004 / ADR-007.
- `项目PM-咪咪.md` also explicitly prohibited deleting that historical file.
- All work steps, example dialogue, and F-024 content had already migrated.

The file was intentionally preserved history, not accidental residue. The check considered only an old filename and a replacement, missing the preservation notices. It almost violated ADR-007 and broke three active references. The deletion recommendation was withdrawn; the file remained.

## #89: Byte counts alone could not determine whether files should be split

The check marked seven files above 8 KB as red-zone files and proposed splitting them, leading to five PROP-042 stages.

Reading each file showed:

- Stage 1, decision-checkpoint, 18 KB: substantial case/history material could be separated. Task #117 completed this, reducing about 5 KB.
- Stage 2, INDEX, 14.8 KB: all six sections were core; the only historical section, section 6, was 728 B. Splitting would save little.
- Stage 3, role boundaries, 13.6 KB: already split in task #106.4; the remaining nine-PM matrix was core and should not be split again.
- Stages 4–5 still required assessment.

The check measured bytes without distinguishing removable case/history sections from necessary core content. Forcing a split of core-only material would hurt frequent use. Stages 2–3 were withdrawn; stages 4–5 moved to backlog until a meaningful structural opportunity arose.

## Issue DN candidate: improve health-check procedure

Above-8-KB flags must be followed by an assessment of separable content versus core content:

1. Use awk to measure bytes by section.
2. Classify each section as case/history material or necessary core.
3. Recommend splitting only when separable material is at least 30% of the file.
4. Check preservation notices for historical exemptions under ADR-007; filenames alone are insufficient.

Add this issue DN candidate to Knowledge PM's quick references. Health-check quality itself needs a procedure. The 8 KB figure is an engineering recommendation, not a hard rule; do not split core content merely to meet a number.
