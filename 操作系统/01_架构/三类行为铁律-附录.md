## Ambiguous cases

Ask by default when no explicit rule applies, especially for actions that appear small but may cross a boundary:

- Editing the project introduction in `README.md`: first distinguish a product-positioning change (Class B) from a typo (Class A).
- Editing `.gitignore`: usually reversible, but first obtain Class B confirmation if the change affects build outputs, secret protection, or the release chain.
- Editing existing tests: synchronizing their contract after a PRD change is permitted; if a test is merely inconvenient, stop and explain first.

## Complete Class A examples

| Action | Notes |
|---|---|
| L1 change: wording, typo, or a single style adjustment | Proceed directly. Framework paths need a lightweight `状态.md` / CHANGELOG record, without PROP or a full handoff. |
| Write a PROP in `确认改动/待审批/` | An AI proposal itself does not require approval. |
| Run tests (`vitest` / `esbuild` / `vite build`) | Class A means no approval is required; role boundaries still apply, and release verification belongs to the Test and Release PM. |
| Read existing code or documentation | At any time. |
| Create or modify sandbox files in `/tmp/mimi-test` | Does not affect real code. |
| Write or update development documentation in `Docs/3-开发文档/` | Update documentation with code changes. |
| Write test code (`*.test.js`) | No approval required. |
| Write task lists and update task status | Self-management. |
| Write sandbox code drafts for demos or verification | Apply the appropriate change level before moving them into `src/`. |
| Write or update the knowledge base within the role allowlist, such as framework records in `Docs/3` / `Docs/7` or requirements in `Docs/1` | Record code facts without exceeding the path allowlist. |

## Rollback

When zlbdh changes their mind after Mimi performs a Class A action:

- **Code**: inspect the Git diff and restore the previous state with the smallest patch.
- **Documentation**: restore it manually, or revert the relevant commit when explicitly authorized.
- **Prevention**: after each Class A action, explain “I changed X; here is the diff” so zlbdh can immediately reconsider it.

Do not treat a Class A change as irreversible merely because it has been made.

---

## Principles

> **Reversible + sandbox = automatic; irreversible + real environment = ask first.**

- Experiment freely in the sandbox.
- Recording documentation-level facts can be automatic, but framework paths require a record.
- Apply more caution as code, configuration, release, or data actions approach real users and external distribution.

## Mapping to L1–L4 change levels

The A/B/C AI boundaries and L1–L4 change levels are orthogonal but overlap: the former determine whether an action is permitted; the latter determine how to perform it.

| Level | Example | A/B/C boundary | Reason |
|---|---|---|---|
| **L1**: wording, typo, or a single style adjustment | Change a subtitle or one text string | **Class A: automatic** | Reversible; proceed directly. Framework paths need only a lightweight record. |
| **L2**: behavior adjustment or a localized bug | Fix one behavior or add an error message | **Class A: automatic** | A reversible, local fix the AI can perform directly. |
| **L3**: new feature or change across multiple files | Add a feature or change multiple modules | **Class B: ask first** | zlbdh must review the new feature's PRD before work begins. |
| **L4**: architecture or data-schema change | Add a table, change a schema, split a module, or add a native plugin | **Class B: ask first** | Architecture changes require both PRD and ADR review; wait for zlbdh's decision. |
