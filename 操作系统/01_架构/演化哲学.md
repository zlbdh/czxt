# Framework Evolution Philosophy

> Shared by both PMs; required reading before adding roles or expanding the framework.
> Trigger: when zlbdh or any PM wants to add a role, split the framework, or expand PM subclasses, read this file first.
> Historical trigger: on 2026-05-19, zlbdh asked whether to imitate a real company's structure. The PM explicitly recommended against it, favoring actual workflow constraints.
> Related lessons: issue AJ, where PROP-020 path C was abandoned for unclear direction, and issue AY, where framework complexity was recognized as debt alongside code debt.

## 1. Core principle: do not imitate a real company's structure

Company structures—CEO / CTO / CMO / CFO / COO / VP / Director / Manager / IC—serve five constraints. This framework's comparison treats most as inapplicable or counterproductive in an AI collaboration project:

| # | Company constraint | This project's comparison |
|---|---|---|
| 1 | Human energy limits: one person cannot cover many disciplines | AI roles have no energy limit |
| 2 | Information isolation: department walls, KPIs, and politics | All information is in Markdown files |
| 3 | Shared legal responsibility requiring named accountable people | This is a personal project; zlbdh is the sole decision-maker |
| 4 | Communication costs and a management span of 7±2 | Files and handoff cards imply zero translation loss |
| 5 | Recruiting efficiency through specialized roles | There is no recruiting |

Copying the company model leaves most roles idle and introduces hierarchy, departmental barriers, and role friction. The resulting framework debt is harder to split than application-code debt because Markdown role files have no corresponding split path.

## 2. What determines a role?

Use thinking mode, workflow constraints, and path allowlists to define roles, rather than job titles or departments.

Each role consists of a thinking mode, a path allowlist, and a startup procedure. These are different perspectives of the same Mimi at different times, not separate employees.

The current nine PMs divide responsibilities as follows:

| PM | Perspective |
|---|---|
| Project PM “Mimi” | Global orchestration |
| Knowledge PM | Meta-rules, memory, and retrospective knowledge at the meta layer |
| Operating System PM | Framework maintenance: `操作系统/`, `能力资产/`, `Docs/3+7`, `确认改动`, and `交接区` |
| Product PM | Requirements analysis: `Docs/1-需求文档/` and `确认改动/待审批/` |
| Technical PM | Fix strategy; read-only `{{APP_REPO_DIR}}/` |
| Test PM | Read all files; acceptance strategy |
| Operations PM | Business growth in a separate outward-facing workflow |
| Development PM | Application-code implementation; worker runtime may change |
| Test and Release PM | Release completion, push, APK, and smoke; release-control runtime may change |

## 3. Three expansion questions for a new role

Ask all three before adding any PM role. Any NO means do not add it. These questions concern expansion specifically; they do not replace everyday `decision-checkpoint` Q1–Q7 role-switch checks.

| Question | Criterion | Required evidence |
|---|---|---|
| Q1: Recurring practical pain | Is there a recurring workflow we cannot handle, with unclear boundaries or misrouting? | At least three documented instances |
| Q2: Frequency | How many times per week does the workflow occur? | At least once per week; do not add a role for fewer than four occurrences per month |
| Q3: Alternatives | Can an existing role's sub-mode, as in issue P, cover it? | It cannot |

If all three pass, create a PROP to design the role. Otherwise, add it to the issue backlog and reconsider when it becomes frequent.

## 4. Approaches to adding roles

### Discouraged: company structure

- Job titles: CEO, CTO, CMO, HR, legal, or administration.
- Departments: product, engineering, marketing, or sales.
- Hierarchy: VP, Director, Manager, or IC.

### Recommended: workflow constraints

- Repeated thinking-mode changes: orchestration, maintenance, analysis, fixes, and acceptance.
- Path allowlist divisions, with different roles protecting different directories.
- External triggers, such as customer support, analytics, or monetization that arise only in stage A.

## 5. Current assessment and future evolution

### Current position: 2026-06-14

- Nine roles: one lead, one meta, five decision, and two implementation PMs. This is the final v4.0 model; continue consolidating it instead of expanding it.
- Issue AJ has more than 30 practical uses with zero boundary violations, supporting its necessity.
- ADR-038 replaced adding more PMs with centralized Project PM scheduling of worker/explorer agents.

### No new PM roles in the near term

For parallel checks, controlled writes, or verification, first use workers/explorers under `子agent调度机制.md`. Return to the expansion questions only when a new workflow is consistently frequent and the current nine PMs cannot express it.

Requirements, design, frontend, backend, and hardware specialties first follow [specialized PM modes](PM专业mode能力层.md). Do not add a PM when a mode, plugin, worker, or explorer can cover the work.

### Future candidates: consider only after stage A public release

| Candidate | Trigger | Preferred alternative |
|---|---|---|
| Customer Support PM | Users request bug fixes or answers after public release | Project PM + Technical PM sub-mode |
| Data PM | DAU and retention data become available after public release | Operations Mimi sub-mode |
| Monetization PM | Choosing subscription or payment models | zlbdh decides directly; Project PM breaks the work into Sprints |

Do not add roles that sub-modes can cover. Add one only when a new workflow is consistently frequent and sub-modes are insufficient.

## 6. Issue BJ candidate: conditions for making this philosophy a permanent meta-rule

If a structural blind spot emerges—for example, application or growth work becomes misdirected within six months of adding a role—create PROP-N to revise this file and promote issue BJ through ADR-N.

The current version is v0: one strategic reflection by zlbdh, without long-term field validation. Apply it cautiously; prioritize zlbdh's arbitration when disputed.

## 7. Prohibited approaches

- Adding a role without the three expansion questions: the issue AJ lesson.
- Defining roles through a company structure: CEO/CMO-style roles become idle.
- Adding a role without a playbook and path allowlist: the PROP-020 path C failure; an invisible role effectively does not exist.
- Establishing reporting relationships or hierarchy among roles: these are branches, not ranks; zlbdh arbitrates conflicts.
- Ignoring framework complexity: apply the issue AY lesson to the framework as well.
