# Workflow: Handoff Format

Across sessions and PM responsibilities, the card explains who takes over, what changed, what was tested, what happens next, and what risks remain. Cowork, Claude Code, and Codex are execution tools; use PM responsibilities as the main actors in filenames and content.

> This is the frequent-use entry. See the [appendix](交接卡格式-附录.md) for historical triggers, failure cases, and the mandatory-use matrix.

## Automated-alignment boundary

Hooks and health scripts check, remind, or block. They do not silently edit handoff cards, `状态.md`, PM records, or final chat output. Only deterministic indexes such as the ADR README support Apply. The current main session confirms card moves, summaries, and sections ①-⑦ under its PM role before writing them.

## Three layers

1. `交接区/待接手/YYYY-MM-DD-HHMM-task-from-to.md`: standalone full card, requiring ①-⑥ with optional file section ⑦.
2. Top of `状态.md`: link the latest pending card when one exists; otherwise link the latest accepted card or state “No pending handoffs”.
3. Short chat handoff ①-⑦: completion signal to zlbdh or the next PM.

See the actual directory rules in the [handoff-area README](../../交接区/README.md).

## Full-card template

Write to `交接区/待接手/`, naming PM roles. Frontmatter `status` must initially be `pending`.

```markdown
---
status: pending
from: <sending PM>
to: <receiving PM>
created: YYYY-MM-DD HH:MM
scope: framework/project
---
# <Task> — <sending PM> to <receiving PM>

## ① Time and role transition
- **Time**: YYYY-MM-DD HH:MM
- **From** → **To**: <sending PM responsibility> (runtime: <Cowork / Claude Code / Codex>) → <receiving PM / zlbdh>
- **Task**: core implementation work

## ② File changes
~~~
+ path (new file and byte count)
M path (modified file; old bytes → new bytes)
- path (deleted file)
~~~
Explain any file at or above 6500B; use P4b and manual review.

## ③ Test status by environment capability
| Check | Environment | Status | Result |
|---|---|---|---|
| vitest | Windows | ✅/❌/— | N/N |
| esbuild | Cowork/Win | ✅/❌/— | 0 fail |
| vite build | Windows | ✅/❌/— | 4.32s |
| dev APK | Windows | ✅/❌/— | path |
| Device smoke | Android | ✅/❌/— | Screenshots complete |

## ④ Receiver checklist: concrete actions, not “test it”
- [ ] **zlbdh confirm** XXX
- [ ] Concrete action 1
- [ ] Concrete action 2

## ⑤ Cautions
Status: <DONE / BLOCKED / HANDOFF / RISK / OBSERVE>

- 🔴/🟡/✅ Description, including large-file alerts, TODOs, and risks

## ⑥ Follow-up questions: two-way when the receiver returns a question
- None yet

## ⑦ PM transitions / next steps: recommended for framework cards; optional otherwise
- Add, or record having added, N PM-transition rows to 状态.md this round.
```

The full file requires at least ①-⑥. New pending cards must use headings `## ①` through `## ⑥` in that order. Section ⑤ `Status:` accepts only `DONE / BLOCKED / HANDOFF / RISK / OBSERVE`. Frontmatter `status` is the routing state: pending is `pending`, accepted is `accepted`. Body `Status:` is the delivery caution state. Section ⑦ is recommended for framework cards; the short chat handoff requires all seven sections.

## When the sender completes implementation

1. Move the card previously accepted by this sender from `交接区/待接手/` to `交接区/已接手/`, meaning that the accepted work is complete.
2. Write a new card to `交接区/待接手/YYYY-MM-DD-HHMM-task-from-me-to-next-role.md`.
3. Update the top status summary and link the new card.
4. If a PM role changed or framework files changed, append a PM-transition row in `状态.md`.
5. Send the short seven-part chat handoff.

## When the receiver starts

1. Read the top status summary.
2. Read the latest file in `交接区/待接手/` or the card specified by the user.
3. Do not move the card merely because work starts. Move it upon completion using the sender-completion procedure.

## Short chat handoff ①-⑦

After implementation work, including code, framework changes, QA, or push, write the full card and also send this compact chat format:

```text
[Handoff: <task>, from <A> to <B>]
① Time: YYYY-MM-DD HH:MM
② File changes: N new / M modified (key commit hash, byte-size checks, APK path)
③ Tests: vitest ✅/❌ N/N | esbuild ✅/❌ | build ✅/❌ | APK ✅/⏳ | smoke ✅/⏳ | push ✅/⏳
④ Your next steps: [1] xxx [2] xxx [3] xxx (concrete checklist, not “test it”)
⑤ Cautions: ✅/🟡/🔴 Key cautions, including the six ADR-016 conditions
⑥ Details: Read 交接区/待接手/YYYY-MM-DD-HHMM-<task>-<from>-to-<to>.md
⑦ PM transitions: Added N rows this session (状态.md L<line>)
```

## Requirements

- Do not replace ①-⑦ with a summary paragraph. Fields must appear in order.
- For implementation or cross-role handoffs, section ⑥ must use a plain-text path to an existing `.md` file under `交接区/待接手/`. When finalizing acceptance/archive work and `交接区/待接手/` is empty, it may point to a `status: accepted` `.md` file under `交接区/已接手/`. Do not use Markdown links.
- For implementation or cross-role handoffs, section ⑦ must include `状态.md L<line>`, and the line must be a PM-transition table row. Simple conversation needs no handoff card. If a hook incorrectly classifies it as completion, section ⑥ may say “None” and section ⑦ may use `N=0 / no role switch this session`.
- Older three-section cards remain readable. New cards require at least ①-⑥; `handoff-zone-check` validates pending cards' heading order and five-state `Status` automatically.
