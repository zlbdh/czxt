## 反思 8 — 路径安全不得把卷根元数据误判为项目 ADS

- **记录**：2026-07-19 04:15 by Codex — 借鉴闭环首次在 D 盘真实 dogfood 前置检查中暴露，需防止用删除卷元数据或整体放宽 ADS 守卫修绿。
- **现象**：参考目录、模板根和未来实例根都通过内容盘点，却统一报 `source-boundary`；C 盘 fixture 全绿，D 盘真实根不可进入。
- **根因**：`D:\` 卷根有安全软件维护的 `:sguard:$DATA`，旧逻辑把卷根、项目内祖先与目标路径的命名流等同处理。
- **修复**：仅当卷根作为祖先时跳过流检查；目标路径与所有非卷根祖先仍检查 ADS，reparse、硬链接和固定盘约束不变。
- **教训**：路径守卫必须同时跑隔离 fixture 与真实 workspace；遇到卷根 ADS 先区分卷元数据和项目边界，禁止删除外部元数据或放宽整条守卫。

## 反思 9 — WinPS 5.1 重定向进程需先物化 Handle

- **记录**：2026-07-19 04:21 by Codex — P4t 并发 façade 合同稳定复现两次假失败，需保留最小运行时兼容结论。
- **现象**：`WaitForExit(timeout)` 返回 true 且 `HasExited=true`，但 `Start-Process -PassThru -RedirectStandardOutput/-RedirectStandardError` 的 `ExitCode` 仍为 null。
- **根因**：Windows PowerShell 5.1 的 `Process` 句柄为惰性物化；带重定向时进程退出后再取句柄可能丢失 exit code。
- **修复**：启动后、等待前先执行 `[void]$process.Handle`，并发合同由稳定 9/1 恢复为 10/0。
- **教训**：WinPS 5.1 用 `Start-Process` 做并发验收时，必须在 `WaitForExit` 前保留 Handle；不能把 null ExitCode 误判成被测程序失败。

## 反思 10 — 公开检查 leaf 必须独立闭合治理边界

- **记录**：2026-07-19 04:49 by Codex — P4t 事项 helper 聚焦审查发现 façade 全绿仍不足以证明 leaf 自身安全。
- **现象**：直接调用事项 leaf 时，`unknown/conflict` 模式、任意 owner、凭据 query、活动事项 supersedes 和取消占位理由仍可能返回通过。
- **根因**：模式校验依赖 façade 先验，schema、引用和历史只做形状检查，没有把跨文档治理语义锁进公开 leaf。
- **修复**：leaf 自行 fail-closed；owner 严格使用 9 PM 枚举；URL 解码后拒绝凭据参数名；supersedes 只允许终态前身；取消原因拒绝规范占位符。
- **教训**：每个可直接调用的公开检查入口都必须独立验证安全前置条件；总 façade 的编排顺序不能替代 leaf 自身的 fail-closed 合同。

## 反思 11 — 占位文件也必须纳入字节级契约

- **记录**：2026-07-19 05:03 by Codex — 首个真实临时实例在空借鉴区即触发 P4t 硬失败。

## 反思 12 — 占位符替换不能改写校验器的规范常量

- **记录**：2026-07-19 05:10 by Codex — 真实实例首次 Local capture 在零写入 preflight 报 `missing-trusted-component`。
- **现象**：所有生产叶都存在且 `.gitignore` 合法，但实例来源卡骨架哈希与校验器硬编码不一致。
- **根因**：实例化器递归替换 `{{PROJECT_NAME}}` 时，也改写了 `source-card-skeleton.ps1` 用来恢复规范模板的同名字面量；预期哈希仍属于未改写模板。
- **修复**：校验器在运行时分段构造规范 token，源码不再出现可被实例化器命中的完整占位符；新增真实实例 capture 合同。
- **教训**：模板占位符既是数据也是代码改写模式；生产校验器、正则和 golden 常量不得直接嵌入会被全局替换的完整 token，必须用不可命中的构造方式并跑实例级端到端验收。

## 反思 13 — 跨卡实施权限必须与决策精确相等

- **记录**：2026-07-19 05:18 by Codex — P4t 事项审查发现单卡枚举合法仍可能在跨卡绑定时错误扩权。
- **现象**：事项进入 `implementation_ready / implementing / verifying / closed` 后，只要来源卡的 `reuse_scope` 属于合法枚举，另一种内部复用范围或更宽的 `redistribute` 也可能被误当成当前 decision 的实施授权。
- **根因**：来源卡与事项卡分别校验了字段形状，却没有在实施态逐一核对每个绑定 capture 的授权值与 `adopt / adapt` 决策。
- **修复**：实施及后续状态中，`adopt` 只接受 `copy-internal-approved`，`adapt` 只接受 `adapt-internal-approved`；每个绑定 capture 都必须精确匹配，不从 `inspect`、另一内部范围或 `redistribute` 推导权限。
- **教训**：跨卡授权是关系合同，不是两个枚举合同的并集；测试 fixture 必须同时更新 frontmatter、权限表和磁盘重读路径，并覆盖 seal / façade 的真实重读行为。

## 反思 14 — 根模式不能代替业务来源画像

- **记录**：2026-07-19 09:49 by Codex — 全新 generic project 首次全量体检稳定报出 32 条旧需求/PROP 假失败，需固化模式与业务谱系分轴原则。

- **根因**：旧逻辑只区分 `template / project`，错误地把“这是项目实例”推导成“这是某个旧来源项目”；部署模式与业务来源画像被混成一个布尔量。
- **修复**：在公共 scope 中增加三类高置信历史资产同时存在的 legacy profile 判定；模板与 generic project 只跳过旧业务 helper，通用治理 helper 继续执行，单个诱饵文件不能激活 legacy。
- **教训**：根 marker 只回答运行模式，不能证明业务谱系；来源专属守卫必须由显式、合取、高置信签名启用，默认按 generic 收敛且保留通用门禁。

## 反思 15 — WinPS 子进程 stderr 必须让位于退出码判定

- **记录**：2026-07-19 09:49 by Codex — generic project 尚未初始化业务 Git 仓库时，P4r 从预期跳过变成未处理 exit 1。
- **现象**：`app/.git` 不存在，`install-hooks.ps1` 抛出可诊断错误；P4r 尚未读取 `$LASTEXITCODE` 就以 `NativeCommandError` 中止。
- **根因**：父脚本使用 `$ErrorActionPreference='Stop'`，同时以 `2>&1` 捕获原生 PowerShell 子进程 stderr；WinPS 5.1 会先把 stderr 包成终止错误。
- **修复**：未绑定业务仓库的 generic project 显式 info/exit 0；一旦 `.git` 存在仍执行 hooks 漂移检查；子进程边界临时使用 EAP Continue，并在 `finally` 恢复后按真实退出码判定。
- **教训**：WinPS 包装子进程时，输出采集与成败判定必须解耦；stderr 是诊断证据，不应在读取退出码前改变控制流。

## 反思 16 — 编码门禁 bootstrap 不得依赖自身待校验编码

- **记录**：2026-07-19 09:49 by Codex — legacy profile 修复首次 GREEN 后，Gate0 去 BOM 负向契约从规范 exit 10 回退为启动期 exit 1。
- **现象**：编码门禁故意移除 `framework-scope.ps1` BOM 时，P4a 在调用公开编码 gate 前已经加载失败。
- **根因**：`framework-scope.ps1` 是 P4a 的前置 dot-source；新增的中文路径字面量在无 BOM 的 WinPS 5.1 中先被误解码，形成 bootstrap 自依赖。
- **修复**：保持公共判定函数位置不变，但新增源码使用纯 ASCII，并通过 Unicode code point 在运行时构造精确中文签名路径；Gate0 恢复 12/12。
- **教训**：负责发现编码损坏的启动链必须能在目标文件编码已损坏时继续运行；任何 pre-gate bootstrap 改动都要重跑“去 BOM 后仍由公开门禁返回规范错误码”的集成契约。

## 反思 17 — 业务零依赖不能靠扩展名白名单证明

- **记录**：2026-07-19 10:10 by Codex — 借鉴闭环独立审查复现了常见运行时文本绕过，需固化内容识别与资源上限的组合边界。
- **现象**：JavaScript、JSON 等已知扩展能拦截对 `借鉴区/` 的直接依赖，但 HTML、`.env`、`.conf` 和无扩展名启动器携带同一引用时 P4t 仍返回通过。
- **根因**：隔离 leaf 先按有限扩展名挑选文件，再读取内容；“未列入清单”被错误等同于“不是运行时文本”。
- **修复**：8 MiB 内所有可严格解码的 UTF-8 或带 BOM UTF-16LE/BE 常规文件都按内容扫描；疑似超限文本硬失败，二进制跳过，并用非终结 Decoder 防止多字节字符跨采样边界被误判。
- **教训**：安全扫描应以可验证内容为主、扩展名只可作提示；引入资源上限时，必须同时测试超限、二进制和编码边界，不能让限额本身形成绕过。

## 反思 18 — tracked 授权说明也必须按凭据处理

- **记录**：2026-07-19 10:58 by Codex — 独立审查证明“不是 URL”不能作为授权元数据无密钥的证据，需统一捕获前与离线审计语义。
- **现象**：`token=...`、`Authorization: Bearer ...`、URL 编码凭据和常见 raw token 可进入来源卡的授权来源/范围，P4t 仍返回通过。
- **根因**：capture 只检查长度与控制字符，P4t 另有一套只覆盖 URI userinfo 和少数 query 的窄规则；写入边界与审计边界语义分叉。
- **修复**：新增共享强凭据检测器，递归处理 URL/form 编码、userinfo、credential assignment、Bearer/Basic、常见 token 前缀与 private-key header；写卡前与 P4t 复用同一函数并 fail closed。
- **教训**：任何 tracked 自由文本都可能承载凭据；敏感检测必须在首次持久化前执行，并由后验守卫复用同一实现，不能维护两套逐渐漂移的正则。

## 反思 19 — closed 是完整事务结果，不是 seal 字段结果

- **记录**：2026-07-19 10:58 by Codex — 关闭 helper 的局部全绿掩盖了完整根 isolation 失败、空壳证据和并发覆盖风险。
- **现象**：seal helper 可成功把卡写成 closed+sealed，随后完整根 P4t 才因业务直依赖失败；不存在的目标/证据、空 bullet 或旧验证也能过，关闭前并发用户编辑还会被覆盖。
- **根因**：seal、事项 leaf 与完整根 P4t 被当成松散步骤；没有保存原字节、候选 staging、机器证据与 compare-before-replace 事务边界。
- **修复**：新增可信 close façade，按候选→原子安装→seal→完整根 P4t→清理执行；初版“失败恢复原字节”口径已由反思 28 与反思 31 的后继约束收窄：仅在 ownership 可证明且尚未进入 `content-deleted` 时恢复，所有权不明或越过不可逆点后只保留并报告。目标/evidence 验真实安全文件，fresh 绑定最近 verifying，正式替换前复核快照。
- **教训**：终态只能由完整事务产生；任何可能失败的后验门禁都必须位于提交点之前，并同时测试回滚、失败证据保留和并发改写拒绝。

## 反思 20 — 实例化路径校验必须发生在第一次写入之前

## 反思 26 — fresh evidence 必须绑定事实而非存在性

- **根因**：证据 locator 与被证明事实之间没有机器关系，存在性被误当成可复验性。
- **修复**：定义精确五行 `borrowing-evidence/v1`，绑定 bullet time、command SHA-256、exit 和全部目标文件清单 SHA-256；P4t 双读目标清单并拒绝 `.staging-*`。
- **教训**：机器证据至少要绑定“谁、何时、以什么结果验证了哪些字节”；无法从当前事实重算并比对的文件只是附件，不是验收证据。

## 反思 27 — 负向契约必须证明命中了目标失败条件

- **根因**：负向测试只断言“发生异常”，未设置成功控制组，也未区分同长度字节变化与 identity 替换。
- **修复**：先锁未修改控制组必须成功，再显式传入 baseline，分别验证同长度改写、identity 替换和 P4t 后最终锁拒绝。
- **教训**：异常不是证据；每个安全 RED 都要让前置条件成立，并用控制组或精确结果证明失败来自被测守卫而非更早的无关错误。

## 反思 28 — 回滚所有权必须同时绑定身份与补偿材料

- **记录**：2026-07-19 12:41 by Codex — 关闭事务终审暴露了清理失败与同字节换 identity 会穿透字节级回滚判断。
- **现象**：staging 两个自有文件已删除后目录删除失败，回滚无法取回 sealed 候选，正式卡留在 closed；并发写者以相同字节替换正式卡 identity 时，旧回滚又会将其覆盖。
- **根因**：失败候选只保存在将被清理的磁盘目录，未把内存原字节/候选字节作为补偿源；主流程丢弃每次受信替换后的正式卡快照，回滚只比对 bytes。
- **修复**：回滚前从内存重建并复核 `原活动卡.bin` 与失败 `借鉴卡.md`；主流程保存最后一次受信正式卡的 path/identity/length/bytes，回滚只能覆盖该完整快照。
- **教训**：事务补偿不能依赖成功路径正在销毁的唯一副本；“字节相同”也不代表“仍由本事务拥有”，回滚要同时验证路径、身份、长度与字节。

## 反思 29 — 不覆盖移动比“原子替换”更接近所有权真相

- **记录**：2026-07-22 10:45 by Codex — 安装器与 seal 终审连续发现 backup、prepared、正式目标路径可能在两个动作之间被后来对象占用。
- **现象**：覆盖式 replace 即使单次系统调用原子，也可能把并发写者刚落下的同路径对象当成本事务对象覆盖；失败补偿又可能误删无法证明所有权的残留。
- **根因**：把“路径名属于事务”误当成“路径当前对象属于事务”，并把单文件原子操作外推成整棵安装的全局原子性。
- **修复**：所有落盘改为 no-overwrite 移动，target→backup 与 prepared→target 分别绑定对象身份；冲突即停止，保留 backup、prepared、已落地对象和后来对象供审计。
- **教训**：原子性不能替代所有权；多文件安装应准确承诺“逐对象不覆盖”，不能承诺无法实现的全局回滚。

## 反思 30 — 大文件扫描必须公开观测模型

- **记录**：2026-07-22 10:45 by Codex — P4t 隔离扫描为控制资源改用大文件前缀读取后，旧文档仍暗示所有文件全量摘要。
- **现象**：超过 8 MiB 的文件实际只绑定 identity、length 和前 64 KiB；尾部同身份同长度改写在 v1 观测范围外，若文档继续宣称全量一致性会产生虚假安全保证。
- **根因**：实现层的资源策略没有被当成安全合同，测试只证明当前分支行为，没有同步说明可见与不可见边界。
- **修复**：固定小文件三轮全量、大文件三轮前缀的观测模型，并把文件、目录项、摘要字节与项目卡读取纳入一次调用共享预算。
- **教训**：安全扫描既要说明检测什么，也要说明明确不保证什么；资源上限、重复读取和采样边界都属于公共合同。

## 反思 31 — 不可逆完成点必须早于成功输出、晚于可恢复材料

- **记录**：2026-07-22 10:45 by Codex — close 清理两个 staging 文件后若删除目录失败，继续“恢复原卡”既缺补偿材料，也可能回滚一个实际上已完成的正式状态。
- **现象**：旧口径把任何清理失败都当作可回滚；实际在两个 owned 文件被删除并进入 `content-deleted` 后，事务只能保留正式 closed 卡并显式报告清理失败。
- **根因**：把成功输出、业务提交和物理清理视为同一个瞬间，没有标记补偿材料被销毁后的不可逆边界。
- **修复**：`content-deleted` 成为不可逆完成点；其前只有 ownership 完整可证才允许回滚，其后禁止回滚正式卡并保留可审计残留。
- **教训**：事务必须显式命名不可逆点；一旦补偿证据被销毁，失败处理应转为“保留并报告”，不能继续假装可恢复。

## 反思 32 — Windows PowerShell 可选 ref 不是稳定的嵌套传参协议

- **记录**：2026-07-22 10:45 by Codex — close staging 为兼容“可选输出路径”把参数写成 `[object]` 并从嵌套函数传入 `[ref]$local`，WinPS 5.1 将其解引用成普通字符串。

- **根因**：依赖 PowerShell binder 对 `[ref]` 到非 `[ref]` 可选参数的上下文相关行为，且失败结果隐藏了真实异常位置。
- **修复**：改用带可写 `Value` 属性的显式状态对象，在进入创建逻辑前写入尝试路径；测试通过具名注入点覆盖目录、第二文件写入和第二快照失败，不再替换脚本级函数。

## 反思 33 — staging 安全依赖句柄生命周期而非路径复核

- **记录**：2026-07-22 by Codex — close 终审发现 staging 目录虽然已核验，子文件若再按绝对路径创建，验证与打开之间仍存在可被目录替换的窗口。
- **现象**：空 staging 目录可在首文件创建前被移动或替换；仅保存路径与 identity，不能保证后续 CreateNew 和清理仍作用于同一个目录对象。
- **根因**：没有把受信父目录句柄、staging 创建句柄和首文件 lease 组成连续所有权链；路径级验证与相对 CreateNew、delete-pending 被拆成多个可竞态动作。
- **修复**：staging 所有权链固定：通过受信父目录句柄相对原子创建 staging 目录；首个 `原活动卡.bin` 以目录句柄相对 CreateNew，并在同一 handle 写入、flush 并绑定，文件 lease 贯穿整个事务以让目录保持非空；候选 `借鉴卡.md` 也以目录句柄相对 CreateNew。清理顺序固定为 `Candidate→retained Original→content-deleted→directory`：Candidate 以单次打开的绑定 handle 完成验证并在同一 handle 设置 delete-pending；retained Original 通过保留 lease 在同一 handle 设置 delete-pending；随后立即进入 `content-deleted`，最后由目录创建句柄同句柄删除。验证与路径打开之间不得留窗口；创建失败只删除本事务句柄绑定对象。
- **教训**：验证、创建、写入、flush、绑定和删除必须落在连续句柄生命周期内；创建失败只删除本事务句柄绑定对象，不能按路径猜测清理。

## 反思 34 — P4t 通过后的终锁必须以一次句柄打开闭合

- **记录**：2026-07-22 by Codex — close 终审发现正式卡在安全路径验证之后、终锁按路径重开之前仍可被换成 reparse 或新增硬链接。
- **现象**：路径验证和终锁打开各自成功，却可能观察到两个不同对象；P4t 已通过不能证明后续清理时正式卡仍是同一安全常规文件。
- **根因**：把路径级安全结论跨越到下一次打开，没有从终锁实际 handle 重做 canonical path、类型、link count 与完整快照复核。
- **修复**：P4t exit 0 后，正式卡终锁必须单次 OPEN_REPARSE_POINT 打开，并从同一 handle 复核 canonical path、常规非 reparse 类型、link count=1、identity、length 与 bytes；该排他 lease 持有到 staging 清理结束。禁止“先安全路径验证再按路径重开”。
- **教训**：终锁的安全事实必须来自实际持锁 handle，并持有到 staging 清理结束；禁止“先安全路径验证再按路径重开”。

## 反思 35 — 正式卡与 staging 候选是两个独立回滚状态

- **记录**：2026-07-22 by Codex — seal 已提交正式卡后，staging 候选更新在提交前失败，旧状态推进却把 staging 期望提前视为 sealed 字节。
- **现象**：正式卡所有权快照已经指向 sealed 正式对象，当前 staging 候选快照仍是未 seal 候选；共用一个“预期字节”会让本可安全回滚的分支误报 staging 被并发改写。
- **根因**：把正式卡所有权快照与当前 staging 候选快照两个独立状态合并，并在 Set 真正提交前先推进候选期望。
- **修复**：seal 后 staging 候选更新遵循双状态合同：正式卡所有权快照与当前 staging 候选快照是两个独立状态，回滚必须分别验证；不得提前把 staging 期望改成 sealed 字节。`Set-BctCandidateBytes` 的 Set 提交后状态对象先更新，再执行后续可失败复核，确保异常分支看到实际已提交候选。
- **教训**：回滚必须分别验证两个对象的当前快照；Set 提交后状态对象先更新，且不得提前把 staging 期望改成 sealed 字节。
