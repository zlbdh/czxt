## Reflection 8 — Do not mistake volume-root metadata for project ADS

- **Recorded:** 2026-07-19 04:15 by Codex — exposed in the first real D-drive borrowing-lifecycle dogfood preflight; do not fix it by deleting volume metadata or broadly relaxing ADS checks.
- **Observed:** reference directory, template root and future instance root all passed content inventory but reported `source-boundary`; C-drive fixtures passed, while the real D-drive root could not be entered.
- **Cause:** the `D:\` volume root had `:sguard:$DATA` maintained by security software. Old logic treated named streams on volume roots, project ancestors and targets identically.
- **Fix:** skip stream inspection only when the volume root is an ancestor. Target paths and every non-volume-root ancestor still undergo ADS checks; reparse, hard-link and fixed-drive constraints remain.
- **Lesson:** test path guards against both isolated fixtures and real workspaces. Distinguish volume metadata from project boundaries before addressing volume-root ADS; never delete external metadata or weaken the entire guard.

## Reflection 9 — Materialize Handle before waiting on redirected WinPS 5.1 processes

- **Recorded:** 2026-07-19 04:21 by Codex — the P4t concurrent façade contract reproduced two false failures; retain this minimal runtime-compatibility finding.
- **Observed:** `WaitForExit(timeout)` returned true and `HasExited=true`, yet `ExitCode` remained null after `Start-Process -PassThru -RedirectStandardOutput/-RedirectStandardError`.
- **Cause:** Windows PowerShell 5.1 materializes the Process handle lazily; obtaining it only after a redirected process exits can lose the exit code.
- **Fix:** execute `[void]$process.Handle` after startup and before waiting. The concurrency contract recovered from a stable 9/1 to 10/0.
- **Lesson:** when testing concurrency with WinPS 5.1 Start-Process, retain Handle before WaitForExit; a null ExitCode does not establish failure of the tested program.

## Reflection 10 — Public validation leaves must independently enforce governance boundaries

- **Recorded:** 2026-07-19 04:49 by Codex — focused P4t item-helper review found that a passing façade did not prove each leaf was safe independently.
- **Observed:** direct item-leaf calls could pass with unknown/conflict mode, arbitrary owners, credential queries, active-item supersedes or placeholder cancellation reasons.
- **Cause:** mode checks relied on façade preconditions. Schema, references and history checked only shape, without enforcing cross-document governance semantics in the public leaf.
- **Fix:** leaves fail closed independently; owner uses the strict nine-PM enum; URL decoding precedes rejection of credential parameter names; supersedes permits terminal predecessors only; cancellation reasons reject defined placeholders.
- **Lesson:** every directly callable public validation entry must validate its own safety preconditions. Façade orchestration cannot replace a leaf's own fail-closed contract.

## Reflection 11 — Placeholder files need byte-level contracts too

## Reflection 12 — Placeholder replacement must not rewrite validator constants

- **Recorded:** 2026-07-19 05:10 by Codex — the first Local capture in a real instance reported missing-trusted-component during zero-write preflight.
- **Observed:** all production leaves existed and .gitignore was valid, but the instance's source-card scaffold hash differed from the validator's hardcoded hash.
- **Cause:** recursive replacement of `{{PROJECT_NAME}}` also rewrote the same literal in source-card-skeleton.ps1 used to reconstruct the canonical template; the expected hash still described the unchanged template.
- **Fix:** construct the canonical token in pieces at runtime, keeping the full instantiator-matchable placeholder out of validator source; add a real-instance capture contract.
- **Lesson:** a template placeholder is both data and a code-rewrite pattern. Production validators, regexes and golden constants must construct globally replaced tokens in a way that cannot match the replacement, and undergo instance-level end-to-end tests.

## Reflection 13 — Cross-card implementation authority must exactly match the decision

- **Recorded:** 2026-07-19 05:18 by Codex — P4t item review showed that valid per-card enums could still broaden authority when bound across cards.
- **Observed:** after an item entered implementation_ready / implementing / verifying / closed, a valid reuse_scope from the other internal reuse mode, or the broader redistribute scope, could be mistaken for authorization under its current decision.

## Reflection 14 — Root mode does not establish a business-source profile

- **Recorded:** 2026-07-19 09:49 by Codex — a fresh generic project's first complete health check repeatedly produced 32 false legacy requirements/PROP failures; keep deployment mode and business lineage separate.
- **Observed:** the instance had only a valid `.czxt-project-root` and no inherited requirements, tests or PROP history, yet P4q still required all legacy business-specific anchors.
- **Cause:** old logic distinguished only template/project, incorrectly inferring that any project instance belonged to one legacy source project; deployment mode and business lineage became one boolean.
- **Fix:** add a public-scope legacy-profile check requiring all three high-confidence historical asset classes. Template and generic project skip only legacy business helpers, while general governance helpers still run; one decoy file cannot activate legacy mode.
- **Lesson:** a root marker establishes runtime mode, not business lineage. Source-specific guards need explicit, conjunctive, high-confidence signatures; default to generic while retaining general gates.

## Reflection 15 — Judge WinPS child processes by exit codes before stderr

- **Recorded:** 2026-07-19 09:49 by Codex — before a generic project's business Git repository was initialized, P4r changed from an expected skip to an unhandled exit 1.
- **Observed:** app/.git was absent and install-hooks.ps1 raised a diagnosable error, but P4r stopped with NativeCommandError before reading `$LASTEXITCODE`.
- **Cause:** the parent used `$ErrorActionPreference='Stop'` while capturing the native PowerShell child's stderr with `2>&1`; WinPS 5.1 first wrapped stderr in a terminating error.
- **Fix:** generic projects without a bound business repository explicitly report info/exit 0. Once .git exists, hook-drift checks still run. Temporarily use EAP Continue at the child-process boundary, restore it in finally, then decide from the actual exit code.
- **Lesson:** separate output collection from success/failure decisions when wrapping WinPS children. Stderr is diagnostic evidence and must not alter control flow before the exit code is read.

## Reflection 16 — Encoding-gate bootstrap must not depend on the encoding it validates

- **Recorded:** 2026-07-19 09:49 by Codex — after the first GREEN legacy-profile fix, Gate0's BOM-removal negative contract regressed from the specified exit 10 to startup exit 1.
- **Observed:** when the encoding gate deliberately removed framework-scope.ps1's BOM, P4a failed to load it before invoking the public encoding gate.
- **Cause:** P4a dot-sourced framework-scope.ps1 first; new Chinese path literals were misdecoded without a BOM in WinPS 5.1, making bootstrap depend on itself.
- **Fix:** retain the public detection functions' locations, but use ASCII source for additions and construct exact Chinese signature paths from Unicode code points at runtime. Gate0 recovered to 12/12.
- **Lesson:** a startup chain that detects encoding damage must run even when the target file's encoding is damaged. Any pre-gate bootstrap change must rerun the integration contract proving BOM removal still produces the public gate's specified error code.

## Reflection 17 — An extension allowlist cannot prove zero business dependencies

- **Recorded:** 2026-07-19 10:10 by Codex — independent borrowing-lifecycle review reproduced common runtime-text bypasses; retain the combined content-detection and resource-limit boundary.
- **Observed:** known extensions such as JavaScript and JSON blocked direct dependencies on 借鉴区/, while HTML, .env, .conf and extensionless launchers carrying the same reference still passed P4t.
- **Cause:** the isolation leaf selected a limited set of extensions before reading content, incorrectly treating unlisted files as non-runtime text.
- **Fix:** content-scan every regular file within 8 MiB that strictly decodes as UTF-8 or BOM-marked UTF-16LE/BE. Suspected oversized text fails hard; binary files are skipped. Use a nonfinalizing Decoder to avoid misclassifying multibyte characters across sampling boundaries.
- **Lesson:** verified content is the basis of safety scanning; extensions are only hints. Resource limits require oversized-text, binary and encoding-boundary tests so the limit itself cannot become a bypass.

## Reflection 18 — Treat tracked authorization descriptions as potential credentials

- **Recorded:** 2026-07-19 10:58 by Codex — independent review showed that “not a URL” does not prove authorization metadata is secret-free; align pre-capture and offline-audit semantics.
- **Observed:** `token=...`, `Authorization: Bearer ...`, URL-encoded credentials and common raw tokens could enter source-card authorization origin/scope while P4t passed.
- **Cause:** capture checked only length and control characters; P4t had a separate narrow rule set for URI userinfo and a few query fields. Write and audit boundaries diverged.
- **Fix:** add a shared strong-credential detector recursively handling URL/form encoding, userinfo, credential assignments, Bearer/Basic, common token prefixes and private-key headers. Reuse the same fail-closed function before card creation and in P4t.
- **Lesson:** any tracked free text can contain credentials. Detect them before first persistence and reuse that implementation in later guards; do not maintain two drifting regex sets.

## Reflection 19 — Closed is the result of a complete transaction, not a seal field

- **Recorded:** 2026-07-19 10:58 by Codex — locally passing closure-helper checks hid full-root isolation failure, empty evidence and concurrent-overwrite risks.
- **Observed:** seal could write closed+sealed before full-root P4t failed on a business dependency. Nonexistent targets/evidence, empty bullets and stale verification could pass, while concurrent user edits before closure could be overwritten.
- **Cause:** seal, item leaf and full-root P4t were treated as loosely connected steps, without original bytes, candidate staging, machine evidence or a compare-before-replace transaction boundary.
- **Fix:** add a trusted close façade: candidate → atomic installation → seal → full-root P4t → cleanup. Reflections 28 and 31 narrow the initial “restore original bytes on failure” rule: restore only with provable ownership and before content-deleted; otherwise preserve and report. Verify targets/evidence as actual safe files, bind fresh evidence to the latest verifying state, and recheck snapshots before official replacement.
- **Lesson:** only a complete transaction may produce a terminal state. Every fallible postcondition gate must precede commitment; test rollback, failure-evidence retention and rejection of concurrent rewrites together.

## Reflection 20 — Validate instantiation paths before the first write

- **Recorded:** 2026-07-19 10:58 by Codex — path parameters could fail later yet already pollute the project root or write outside it through a junction.
- **Observed:** absolute, `..`, blank and `借鉴区/`-overlapping AppRepoDir values, plus ProjectRoot/AppRepo ancestor junctions, were accepted; scaffolding could be written outside the root through a junction.

## Reflection 22 — Credential guards must cover the final tracked destination

- **Recorded:** 2026-07-19 11:38 by Codex — a second safety review found that JSON keys, provider tokens and Web-response metadata bypassed the existing shared detector.
- **Observed:** quoted JSON keys, AWS access/secret values, GitLab glpat- tokens and credential shapes in etag / last_modified could enter source cards; syntactically valid source_id and LocalDisplayName values could themselves resemble tokens.
- **Cause:** guards covered common input fields rather than all text ultimately written into tracked artifacts; the renderer trusted upstream sanitization.
- **Fix:** scan normalized inputs uniformly, then defensively recheck identifiers, locators, authorization descriptions and every fact in the final renderer. Add RED cases for JSON escaping, AWS/GitHub/GitLab/Slack and Web metadata.
- **Lesson:** derive validation coverage backward from the persistence destination. Field shape, source type and upstream validation cannot replace the final shared detector before writing.

## Reflection 23 — Instantiators must check every physical target twice

- **Recorded:** 2026-07-19 11:38 by Codex — even with a valid ProjectRoot, `-Force` could follow an existing Docs junction and copy the template outside the root.
- **Observed:** ProjectRoot, AppRepoDir and the borrowing area passed preflight, but a junction in a generic `$copyItems` target let `Copy-Item -Recurse -Force` create an external marker.
- **Cause:** root-layout safety was incorrectly extended to all descendants; the copy plan lacked containment and reparse-free checks for each `$dst`.
- **Fix:** preflight all copy, directory-creation and direct-write targets as a batch, then recheck immediately before each write. A real-junction fixture uses an outside-root sentinel to prove RED/GREEN.
- **Lesson:** root safety is not transitive. Batch installers need physical-path checks at both planning time and immediately before writing each actual destination.

## Reflection 24 — Lock the committed object after postcondition gates pass

- **Recorded:** 2026-07-19 11:38 by Codex — close could still return success when the official card changed between full-root P4t exit 0 and staging cleanup.
- **Observed:** a card valid during P4t was replaced or edited afterward; the old implementation still deleted rollback evidence and output CLOSED.
- **Cause:** gate return was mistaken for commitment; the official object was neither reverified nor protected from writers before compensation material was removed.
- **Fix:** after P4t, recheck canonical path, identity, length and sealed bytes; hold a FileShare.None exclusive read lock through staging cleanup. RED cases cover concurrent byte changes and identity replacement.
- **Lesson:** checks and commitment have a TOCTOU boundary. If success destroys compensation material, final snapshot verification and commit cleanup must occur under lock.

## Reflection 25 — Leaves must distrust both mode context and path tokens

- **Recorded:** 2026-07-19 11:38 by Codex — source/isolation leaves could skip project checks with a forged Mode=template; isolation regexes also missed cwd-relative paths.

## Reflection 26 — Fresh evidence must bind facts, not merely exist

- **Recorded:** 2026-07-19 11:38 by Codex — arbitrary nonempty files, even original bytes in failed staging, could masquerade as closure evidence.
- **Observed:** cards self-reported command, exit and time; evidence checks required only an existing nonempty file inside the root. Later target changes did not invalidate it.
- **Cause:** no machine-verifiable relationship linked the evidence locator to the fact asserted; existence was mistaken for reproducibility.
- **Fix:** define the exact five-line borrowing-evidence/v1 format binding bullet time, command SHA-256, exit and the SHA-256 of the entire target-file list. P4t reads the target list twice and rejects .staging-*.
- **Lesson:** machine evidence must bind who verified which bytes, when and with what result. A file that cannot be recomputed and compared against current facts is an attachment, not acceptance evidence.

## Reflection 27 — Negative contracts must prove the intended failure condition was reached

- **Recorded:** 2026-07-19 11:38 by Codex — the concurrent-installation contract accidentally passed because baseline was omitted.
- **Observed:** the test expected rejection of a concurrent rewrite but actually failed on a missing required snapshot. The real compare-before-replace logic could regress while the test stayed green.
- **Cause:** negative tests asserted only that an exception occurred, with no successful control and no distinction between same-length byte changes and identity replacement.
- **Fix:** first require the unchanged control to pass, then explicitly supply baseline and separately verify same-length rewrites, identity replacement and rejection by the final lock after P4t.
- **Lesson:** an exception alone is not evidence. Every safety RED needs valid preconditions and a control or exact result proving the tested guard caused failure, not an earlier unrelated error.

## Reflection 28 — Rollback ownership must bind identity and compensation material

- **Recorded:** 2026-07-19 12:41 by Codex — closure-transaction review found that cleanup failure and same-byte identity replacement bypassed byte-only rollback decisions.
- **Observed:** after deleting both owned staging files, directory deletion could fail; rollback could no longer recover the sealed candidate, leaving the official card closed. A concurrent same-byte replacement of the official identity could also be overwritten by old rollback logic.
- **Cause:** the failed candidate existed only in the directory being cleaned, with no in-memory original/candidate compensation source. The main flow discarded official snapshots after trusted replacements, and rollback compared only bytes.
- **Fix:** reconstruct and verify 原活动卡.bin and the failed 借鉴卡.md from memory before rollback. Retain the latest trusted official path/identity/length/bytes snapshot; rollback may overwrite only that complete snapshot.
- **Lesson:** compensation cannot depend on the only copy being destroyed on the success path. Equal bytes do not prove transaction ownership; rollback must verify path, identity, length and bytes together.

## Reflection 29 — No-overwrite moves express ownership more accurately than atomic replacement

- **Recorded:** 2026-07-22 10:45 by Codex — installer and seal reviews repeatedly found that later objects could occupy backup, prepared or official target paths between operations.
- **Observed:** even a single-call atomic replace could overwrite a concurrent writer's new object at the same path; failure compensation could then delete remnants whose ownership was unproven.
- **Cause:** a transaction's path name was confused with ownership of the current object there, and single-file atomicity was generalized to global atomicity of an entire installation.
- **Fix:** use no-overwrite moves for all writes. Bind object identity separately for target→backup and prepared→target. Stop on conflict and preserve backup, prepared, installed and later objects for audit.
- **Lesson:** atomicity does not establish ownership. Multifile installation should promise per-object no-overwrite behavior, not an unattainable global rollback.

## Reflection 30 — Large-file scanning must disclose its observation model

- **Recorded:** 2026-07-22 10:45 by Codex — P4t isolation switched to prefix reads for large files to bound resources, while old documentation still implied full-file digests everywhere.
- **Observed:** files over 8 MiB bound only identity, length and the first 64 KiB. Same-identity, same-length tail edits were outside v1's observation range; claiming full consistency would create a false assurance.
- **Cause:** the implementation's resource policy was not treated as a safety contract. Tests demonstrated current branches without documenting visible and invisible boundaries.
- **Fix:** define three full reads for small files and three prefix reads for large files; share one invocation budget across files, directory entries, digest bytes and project-card reads.
- **Lesson:** safety scanning must state both what it detects and what it explicitly cannot guarantee. Resource limits, repeated reads and sampling boundaries are public contracts.

## Reflection 31 — Name the irreversible point between recoverable material and success output

- **Recorded:** 2026-07-22 10:45 by Codex — if directory deletion failed after both staging files were deleted, restoring the original card lacked compensation material and could undo an actually completed official state.
- **Observed:** old guidance treated every cleanup failure as rollback-capable. Once both owned files were deleted and content-deleted reached, the transaction could only preserve the official closed card and explicitly report cleanup failure.
- **Cause:** success output, business commitment and physical cleanup were treated as one instant, without marking the irreversible boundary after compensation material was destroyed.
- **Fix:** content-deleted is the irreversible completion point. Before it, rollback requires complete provable ownership. After it, preserve auditable remnants and never roll back the official card.
- **Lesson:** transactions must explicitly name the irreversible point. Once compensation evidence is destroyed, failure handling becomes preserve-and-report; it cannot pretend recovery remains possible.

## Reflection 32 — Optional WinPS ref parameters are not a stable nested-call protocol

- **Recorded:** 2026-07-22 10:45 by Codex — close staging used `[object]` for an optional output path and passed `[ref]$local` from a nested function; WinPS 5.1 dereferenced it into an ordinary string.
- **Observed:** a direct-call control received PSReference, but the nested call failed with a nonwritable Value before staging creation. The caller saw only candidate-invalid and none (not created).
- **Cause:** the design relied on context-dependent binding from `[ref]` to a non-`[ref]` optional parameter, while failure reporting hid the actual exception location.
- **Fix:** use an explicit state object with a writable Value property; record the attempted path before creation starts. Named injection points test directory, second-file-write and second-snapshot failures without replacing script-level functions.
- **Lesson:** pass mutable outputs through explicit state objects or mandatory ref contracts. Test injection needs lifecycle boundaries so it cannot contaminate later cases in the same process.

## Reflection 33 — Staging safety depends on handle lifetimes, not path rechecks

- **Recorded:** 2026-07-22 by Codex — close review found that creating child files by absolute path after validating staging still left a directory-replacement window between validation and opening.
- **Observed:** an empty staging directory could move or be replaced before the first file was created. Retaining path and identity alone could not guarantee that later CreateNew and cleanup used the same directory object.
- **Cause:** trusted parent handle, staging creation handle and first-file lease were not a continuous ownership chain. Path validation, relative CreateNew and delete-pending were separate raceable operations.
- **Fix:** The staging ownership chain is fixed: atomically create the staging directory relative to a trusted parent-directory handle. Create the first `原活动卡.bin` using directory-handle-relative CreateNew; write, flush and bind through that same handle. Retain the file lease throughout the transaction so the directory stays nonempty. Create candidate `借鉴卡.md` with directory-handle-relative CreateNew as well. Cleanup order is fixed as `Candidate→retained Original→content-deleted→directory`: validate Candidate through a single-open bound handle and set delete-pending through that same handle; set retained Original delete-pending through its retained lease and same handle; immediately enter `content-deleted`, then delete the directory through its original creation handle. ## Reflection 34 — Acquire the post-P4t final lock through one handle open

- **Recorded:** 2026-07-22 by Codex — close review found that an official card could become reparse-backed or gain a hard link after safe-path validation but before the final lock reopened the path.
- **Observed:** path validation and final-lock opening could each succeed while observing different objects. A prior P4t pass did not prove the official card remained the same safe regular file during cleanup.
- **Cause:** a path-level conclusion was carried across a later open, without repeating canonical-path, type, link-count and complete-snapshot verification from the actual final-lock handle.
- **Fix:** After P4t exit 0, acquire the official card's final lock with one OPEN_REPARSE_POINT open. Through the same handle, recheck canonical path, regular non-reparse type, link count=1, identity, length and bytes. Hold that exclusive lease until staging cleanup finishes. Do not validate a safe path and then reopen it by path.
- **Lesson:** derive the final lock's safety facts from the actual locked handle and retain it through staging cleanup. Do not validate a safe path and then reopen it by path.

## Reflection 35 — Official cards and staging candidates are separate rollback states

- **Recorded:** 2026-07-22 by Codex — after seal committed the official card, a staging-candidate update failed before commitment, but old state advancement had already treated staging expectations as sealed bytes.
- **Observed:** the official ownership snapshot described the sealed official object while staging still held the unsealed candidate. Sharing one expected-byte state made a safely recoverable branch falsely report a concurrent staging rewrite.
- **Cause:** two independent snapshots, official-card ownership and current staging candidate, were merged, and the candidate expectation advanced before Set actually committed.
- **Fix:** Post-seal staging-candidate updates follow a two-state contract: the official-card ownership snapshot and current staging-candidate snapshot are separate states, each independently verified during rollback. Do not change the expected staging state to sealed bytes in advance. After `Set-BctCandidateBytes` commits its Set, update the state object before any later check that may fail, so exception paths see the candidate actually committed.
- **Lesson:** rollback must independently verify each object's current snapshot. Update the state object after Set commits; never advance expected staging state to sealed bytes beforehand.
