# 工作流：借鉴闭环

本工作流只定义角色切换、状态流转、审批、恢复和完成边界。面向操作者的步骤由唯一 Skill 承接，字段、安全与权限判断回到治理规则。

## 进入条件

marker 组合名用于描述根目录事实，RootMode 值用于机器分支，两者不得混用。

| marker 组合 | RootMode 实际返回值 | workflow 权限 |
|---|---|---|
| project-only | project | 允许写入型接入/建卡/状态变更 |
| template-only | template | 仅允许模板模式只读 P4t 审计 |
| 无标记 | unknown | 零写入；硬失败 |
| 双标记 | conflict | 零写入；硬失败 |

RootMode 函数只返回 `project` / `template` / `unknown` / `conflict`；禁止返回“项目模式”“模板模式”等人类标签。

写入型流程必须在创建 staging、卡片或本地状态前完成模式检查；非 project 一律不得进入写入分支。template 只运行离线、只读的模板审计，unknown 与 conflict 立即失败。

## 角色流

| 角色 | 本闭环职责 | 写入边界 |
|---|---|---|
| 项目 PM | 编排与路由 | 不借此扩大路径白名单 |
| 操作系统 PM | 管理来源与卡片 | 借鉴区/** 与 framework 白名单 |
| 目标决策 PM | 仅提供领域评估结论 | 不写来源卡或事项卡 |
| 测试 PM | 制定验证策略 | 不替代目标路径责任 PM |

落地必须重新按目标文件所在路径路由，借鉴事项本身不产生额外写权限。

| 目标路径 | 责任 PM/实施载体 |
|---|---|
| framework | 操作系统 PM |
| 需求 | 产品 PM |
| 业务/测试代码 | 开发 PM |
| 发布 | 测试发布 PM；仍需另行授权 |

## 状态流

每次变化只允许采用下表中的相邻转换。

| 旧状态 | 新状态 | decision/条件 |
|---|---|---|
| none | draft | pending；首次记录 |
| draft | assessing | pending；至少一个 ready capture |
| assessing | implementation_ready | adopt / adapt；Q1-Q7、L1-L4 与审批通过 |
| assessing | parked | defer；有恢复条件或复查时间 |
| assessing | closed | reject；有评估证据与拒绝理由；进入关闭事务 |
| parked | assessing | pending / adopt / adapt / reject / defer；恢复条件满足 |
| implementation_ready | implementing | adopt / adapt；范围与责任角色确定 |
| implementing | verifying | adopt / adapt；实施记录存在 |
| verifying | closed | adopt / adapt；fresh 验证证据完成；进入关闭事务 |
| 任一活动状态 | cancelled | 任意；有取消原因 |

从 `implementation_ready` 到 `closed` 的所有实施状态均逐一约束来源绑定：`adopt` 要求每个 capture 的 `reuse_scope=copy-internal-approved`，`adapt` 要求每个 capture 的 `reuse_scope=adapt-internal-approved`；其他范围不建立隐式权限层级。

`blocked=true 只允许活动状态`，并同时记录 `blocked_from`、`reason`、`resume_condition`；解除后回到原状态。

同状态追加证据仅限活动状态。
closed/cancelled 为终态且不可修改；后续变化必须新建 supersedes。

状态变化必须追加历史，时间非递减。历史末行的 lifecycle_status 与 frontmatter 当前值一致；历史末行的 decision 与 frontmatter 当前值一致。

## 决策与审批

- `pending` 只表示尚未形成采纳结论，不可据此进入实施。
- `adopt` 或 `adapt` 进入实施准备前，必须完成 Q1-Q7、L1-L4 与所需审批；实际落地仍由目标路径责任角色执行。
- `reject` 必须留下评估证据和拒绝理由后才能关闭。
- `defer` 必须进入 parked，并留下恢复条件或复查时间。

涉及治理调整、远端动作、执行、删除或发布时，只引用现有 A/B/C 判断，不在本工作流另建授权口径。

## 失败恢复

来源捕获的正式晋升固定为双闸顺序；晋升前根 P4t 检查现有正式根，staging 候选由 candidate validator 校验。

| 顺序 | 捕获晋升步骤 | 精确结果 |
|---|---|---|
| 1 | candidate validator/候选校验 | staging 候选卡可声明 capture_status: ready；exit 0 |
| 2 | 晋升前根 P4t | exit 0 |
| 3 | 原子移动 | staging→目标 capture |
| 4 | 晋升后根 P4t | exit 0 |
| 5 | 正式 ready | 前后根 P4t 均 exit 0 后才确认/输出 |

| 事件 | 精确结果 |
|---|---|
| candidate validator 或任一根 P4t exit 5/10 | 不得晋升为 ready |
| 晋升后根 P4t exit 5/10 | 原子移回 staging；不得保留 ready |
| 独立审计 exit 5 | 仅 WARN；不得推进任何状态 |
| 独立审计 exit 10 | FAIL；硬失败；不得推进任何状态；不得修复写入 |

捕获失败不生成 ready 的正式 capture；允许保留被忽略的 staging，并报告失败阶段与路径。后验失败只回退本次新增目录，不影响既有来源或事项。

刷新失败时，旧 capture 与旧事项不受影响。刷新时 fingerprint 不变返回 REUSED；fingerprint 改变才新增 capture。旧事项保持原 source_id + capture_id + fingerprint 引用，不得自动跟随新 capture。

验证失败时保留在 verifying，追加失败证据；不 reset，不静默删除用户改动、卡片或证据。

## 完成条件

关闭只能由 Skill 调用 `close-borrowing-item.ps1`；入口先调用 `seal-borrowing-item.ps1`，再运行完整根 P4t；exit 0 后还必须持终锁复核正式卡的身份、长度与 sealed 字节，并在锁内清理本事务 staging，全部成功才能对外确认 closed。

候选安装与 seal 提交都使用 no-overwrite，不得覆盖并发写者或后来对象。seal 材料已绑定当前正式对象、仅 `borrow_id` 不一致时，ownership 仍可证明，可按完整快照安全恢复原活动卡；其他 `seal-ownership-unproven` 必须保留当前正式卡与 staging。进入 `content-deleted` 不可逆完成点后不回滚正式卡。

staging 所有权链固定：通过受信父目录句柄相对原子创建 staging 目录；首个 `原活动卡.bin` 以目录句柄相对 CreateNew，并在同一 handle 写入、flush 并绑定，文件 lease 贯穿整个事务以让目录保持非空；候选 `借鉴卡.md` 也以目录句柄相对 CreateNew。

清理顺序固定为 `Candidate→retained Original→content-deleted→directory`：Candidate 以单次打开的绑定 handle 完成验证并在同一 handle 设置 delete-pending；retained Original 通过保留 lease 在同一 handle 设置 delete-pending；随后立即进入 `content-deleted`，最后由目录创建句柄同句柄删除。验证与路径打开之间不得留窗口；创建失败只删除本事务句柄绑定对象。

P4t exit 0 后，正式卡终锁必须单次 OPEN_REPARSE_POINT 打开，并从同一 handle 复核 canonical path、常规非 reparse 类型、link count=1、identity、length 与 bytes；该排他 lease 持有到 staging 清理结束。禁止“先安全路径验证再按路径重开”。

seal 后 staging 候选更新遵循双状态合同：正式卡所有权快照与当前 staging 候选快照是两个独立状态，回滚必须分别验证；不得提前把 staging 期望改成 sealed 字节。`Set-BctCandidateBytes` 的 Set 提交后状态对象先更新，再执行后续可失败复核，确保异常分支看到实际已提交候选。

- adopt/adapt：目标范围、适配差异、实施记录、fresh 验证证据、seal 与 P4t exit 0 全部成立。
- reject：评估证据、拒绝理由、seal 与 P4t exit 0 全部成立。
- cancelled：取消原因完整；parked 不视为完成。
- P4t 闸门通过前不得宣称 ready；关闭事务完成终锁复核与锁内清理前不得宣称 closed。

### 关闭事务

| 关闭顺序 | 精确动作 | 失败边界 |
|---|---|---|
| 1 | 保留原活动卡字节 | 对外仍为原活动状态 |
| 2 | 构造 closed 候选 | 状态与历史写为 closed；closure_seal_sha256 为空 |
| 3 | 以 no-overwrite 装入候选并调用 seal-borrowing-item.ps1 | seal helper 失败不得宣称 closed；不得覆盖后来对象 |
| 4 | 运行根 P4t | exit 0 仅进入终锁复核；不得输出 closed |
| 5 | 持终锁复核并清理 staging | 身份、长度、sealed 字节稳定；删除两份 owned 内容后进入 content-deleted 不可逆完成点；目录清理成功才输出 closed |
| 可证明失败 | ownership 可证明且尚未进入 content-deleted 时恢复原活动卡；失败候选保留到被忽略 staging | 显式报告失败阶段与规范化路径；不得宣称 closed |
| 所有权不明或不可逆 | seal-ownership-unproven 保留当前正式卡与 staging；content-deleted 后不回滚正式卡 | 保留可审计残留并显式失败；禁止覆盖或猜测恢复 |

该事务同时适用于 adopt/adapt 与 reject；只有仍能证明正式对象由本事务拥有且尚未进入 content-deleted 才回滚；seal-ownership-unproven 或不可逆后的失败保留证据且不回滚正式卡。

完成借鉴闭环不等于发布；发布仍需另行授权。
