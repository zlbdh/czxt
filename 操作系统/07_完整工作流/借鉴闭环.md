# Workflow: Borrowing Lifecycle

This workflow defines only role transitions, state transitions, approvals, recovery and completion boundaries. The single Skill owns operator steps; governance rules own field, safety and permission decisions.

## Entry conditions

Marker combinations describe facts about the root directory; RootMode values drive machine branches. Do not conflate them.

| Marker combination | Actual RootMode result | Workflow authority |
|---|---|---|
| project-only | project | Write-mode intake, card creation and state changes allowed |
| template-only | template | Read-only P4t audit in template mode only |
| No marker | unknown | Zero writes; hard failure |
| Both markers | conflict | Zero writes; hard failure |

RootMode returns only `project` / `template` / `unknown` / `conflict`; it must not return human labels such as “project mode” or “template mode.”

Write-mode flows must check the mode before creating staging, cards or local state. No non-project mode may enter a write branch. Template mode runs only an offline, read-only template audit; unknown and conflict fail immediately.

| Target path | Responsible PM / implementation runtime |

## State flow

Each change must follow an adjacent transition in this table.

| Previous state | New state | decision / conditions |
|---|---|---|
| none | draft | pending; first record |
| draft | assessing | pending; at least one ready capture |
| assessing | implementation_ready | adopt / adapt; Q1-Q7, L1-L4 and approval passed |
| assessing | parked | defer; resume condition or review time recorded |
| assessing | closed | reject; assessment evidence and rejection reason; enter the closure transaction |
| parked | assessing | pending / adopt / adapt / reject / defer; resume condition met |
| implementation_ready | implementing | adopt / adapt; scope and responsible role determined |
| implementing | verifying | adopt / adapt; implementation record exists |
| verifying | closed | adopt / adapt; fresh verification evidence complete; enter the closure transaction |
| Any active state | cancelled | Any decision; cancellation reason recorded |

Every implementation state from `implementation_ready` through `closed` individually constrains source bindings: `adopt` requires every capture to have `reuse_scope=copy-internal-approved`; `adapt` requires every capture to have `reuse_scope=adapt-internal-approved`. Other scopes create no implicit permission hierarchy.

`blocked=true is allowed only in active states`; also record `blocked_from`, `reason` and `resume_condition`. Unblocking returns to the original state.

Appending evidence without changing state is allowed only in active states.
closed/cancelled are immutable terminal states; later changes require a new supersedes item.

Every state change must append history with nondecreasing timestamps. The last history row's lifecycle_status must match current frontmatter; its decision must also match current frontmatter.

## Decisions and approval

- `pending` means no adoption conclusion yet; it does not permit implementation.
- Before `adopt` or `adapt` enters implementation readiness, complete Q1-Q7, L1-L4 and required approvals. The role responsible for the target path still performs the implementation.
- `reject` requires assessment evidence and a rejection reason before closure.
- `defer` must enter parked and record a resume condition or review time.

For governance changes, remote actions, execution, deletion or publication, refer to the existing A/B/C rules. This workflow does not create a separate authorization policy.

## Failure recovery

Promotion of a captured source follows a fixed two-gate sequence. The pre-promotion root P4t checks the existing official root; the candidate validator checks the staging candidate.

| Order | Capture-promotion step | Exact result |
|---|---|---|
| 1 | candidate validator / candidate validation | Staging candidate card may declare capture_status: ready; exit 0 |
| 2 | Pre-promotion root P4t | exit 0 |
| 3 | Atomic move | staging → target capture |
| 4 | Post-promotion root P4t | exit 0 |
| 5 | Official ready | Confirm/output only after both root P4t runs exit 0 |

| Event | Exact result |
|---|---|
| candidate validator or either root P4t exits 5/10 | Must not promote to ready |
| Post-promotion root P4t exits 5/10 | Atomically move back to staging; must not retain ready |
| Standalone audit exits 5 | WARN only; must not advance any state |
| Standalone audit exits 10 | FAIL; hard failure; must not advance any state or perform repair writes |

A failed capture creates no official ready capture. Ignored staging may remain; report the failure stage and path. A post-promotion failure rolls back only the newly added directory and does not affect existing sources or items.

A failed refresh leaves old captures and items untouched. An unchanged fingerprint returns REUSED; only a changed fingerprint creates a new capture. Existing items retain their original source_id + capture_id + fingerprint references and must not automatically follow a new capture.

Failed verification remains in verifying and appends failure evidence. Do not reset or silently delete user changes, cards or evidence.

## Completion conditions

Only the Skill may invoke `close-borrowing-item.ps1` to close an item. The entry first calls `seal-borrowing-item.ps1`, then runs the full root P4t. After exit 0, it must still hold the final lock while rechecking the official card's identity, length and sealed bytes, and clean this transaction's staging under that lock. Confirm closed externally only after every step succeeds.

Candidate installation and seal commit both use no-overwrite; neither may overwrite a concurrent writer or later object. When seal material binds the current official object and only `borrow_id` differs, ownership remains provable and the complete snapshot can safely restore the original active card. Other `seal-ownership-unproven` outcomes must preserve the current official card and staging. Do not roll back the official card after the irreversible `content-deleted` completion point.

The staging ownership chain is fixed: atomically create the staging directory relative to a trusted parent-directory handle. Create the first `原活动卡.bin` using directory-handle-relative CreateNew; write, flush and bind through that same handle. Retain the file lease throughout the transaction so the directory stays nonempty. Create candidate `借鉴卡.md` with directory-handle-relative CreateNew as well.

Cleanup order is fixed as `Candidate→retained Original→content-deleted→directory`: validate Candidate through a single-open bound handle and set delete-pending through that same handle; set retained Original delete-pending through its retained lease and same handle; immediately enter `content-deleted`, then delete the directory through its original creation handle. Leave no gap between verification and path opening. Failed creation deletes only objects bound to this transaction's handles.

After P4t exit 0, acquire the official card's final lock with one OPEN_REPARSE_POINT open. Through the same handle, recheck canonical path, regular non-reparse type, link count=1, identity, length and bytes. Hold that exclusive lease until staging cleanup finishes. Do not validate a safe path and then reopen it by path.

Post-seal staging-candidate updates follow a two-state contract: the official-card ownership snapshot and current staging-candidate snapshot are separate states, each independently verified during rollback. Do not change the expected staging state to sealed bytes in advance. After `Set-BctCandidateBytes` commits its Set, update the state object before any later check that may fail, so exception paths see the candidate actually committed.

- adopt/adapt: target scope, adaptation differences, implementation record, fresh verification evidence, seal and P4t exit 0 must all hold.
- reject: assessment evidence, rejection reason, seal and P4t exit 0 must all hold.
- cancelled: complete cancellation reason; parked is not completion.
- Do not claim ready before the P4t gates pass; do not claim closed before the closure transaction completes its final-lock verification and cleanup under lock.

### Closure transaction

| Closure order | Exact action | Failure boundary |
|---|---|---|
| 1 | Retain original active-card bytes | Externally, the original active state still applies |
| 2 | Construct a closed candidate | Set state and history to closed; closure_seal_sha256 empty |
| 3 | Install candidate with no-overwrite and call seal-borrowing-item.ps1 | A seal-helper failure must not claim closed or overwrite a later object |
| 4 | Run root P4t | exit 0 enters final-lock verification only; must not output closed |
| 5 | Verify under the final lock and clean staging | Identity, length and sealed bytes stable; deleting both owned contents enters the irreversible content-deleted point; output closed only after directory cleanup succeeds |
| Provable failure | Restore original active card only while ownership is provable and content-deleted has not been reached; retain failed candidate in ignored staging | Explicitly report failure stage and canonical path; must not claim closed |
| Unproven ownership or irreversible completion | seal-ownership-unproven preserves current official card and staging; no rollback of official card after content-deleted | Preserve auditable remnants and fail explicitly; do not overwrite or guess how to recover |

This transaction applies to both adopt/adapt and reject. Roll back only while the transaction's ownership of the official object is provable and content-deleted has not been reached. seal-ownership-unproven and failures after the irreversible point preserve evidence without rolling back the official card.

Completing the borrowing lifecycle is not publication; publication still requires separate authorization.
