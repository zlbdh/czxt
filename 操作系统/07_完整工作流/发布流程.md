# Workflow: Release Flow

At the end of each Sprint or feature, produce a development APK for zlbdh to install. Formal distribution follows the release lifecycle; zlbdh manually decides GitHub Release and APK distribution.

## Sprint/feature delivery: development APK

### 1. Full QA
```powershell
cd {{PROJECT_ROOT}}\{{APP_REPO_DIR}}
npm test
npm run build
```
Proceed only with 0 failures and 0 errors.

### 2. Update requirement history and release notes
Add a version section to `Docs/1-需求文档/需求历史.md`.

### 3. Produce the development APK

Prefer the PowerShell script, which archives the APK in `{{APP_REPO_DIR}}/apk/`:

```powershell
cd {{PROJECT_ROOT}}\{{APP_REPO_DIR}}
powershell -NoProfile -ExecutionPolicy Bypass -File .\build-apk.ps1
```

If using `build-apk.bat`, check whether it only runs Gradle assemble. Actual archival is determined by `build-apk.ps1` or the result of a manual copy.

### 4. APK archive path

Development APKs use:

```text
{{APP_REPO_DIR}}/apk/{{PROJECT_NAME}}-vX.Y.Z-debug.apk
```

Before archiving, confirm the target APK does not exist. If it exists, stop; do not overwrite a historical APK. If a version number must be reused, reassess under the Class B version rule first.

### 5. Smoke test

The Test and Release PM “Closer” ([playbook](../02_智能体/测试发布PM-闭环者.md), currently often hosted by Codex) and zlbdh install the APK and smoke-test core paths. Based on the result:
- No issues → the Test and Release PM “Closer” pushes under the six Class B conditions in the [Git flow](git流程.md), updates `状态.md` and the handoff card, sends chat sections ①–⑦, then starts the next Sprint.
- Bug found → fix it and rebuild the APK.

## Formal release: vX.Y.Z

### 1. Complete the release scope
Confirm that the corresponding requirements in `Docs/1-需求文档/`, requirement history, and P0/P1 acceptance items are complete.

### 2. Create the release keystore: one time
zlbdh performs this step manually. AI must not handle passwords, back up or disclose the keystore, or write key material into tracked files.

```cmd
keytool -genkey -v -keystore zlbdh-release.keystore ^
  -alias mimi -keyalg RSA -keysize 2048 -validity 10000
```
**Remember the password and keep multiple backups.**

### 3. Configure Gradle release signing
See the release-signed APK section in `Docs/5-运维文档/APK打包指南.md`.

### 4. Produce the release APK
```cmd
cd android
gradlew.bat assembleRelease
```
Output: `android/app/build/outputs/apk/release/app-release.apk`.
Copy to: `{{APP_REPO_DIR}}/apk/{{PROJECT_NAME}}-vX.Y.Z-release.apk`.

If the target release APK already exists, stop. Do not overwrite a historical APK.

### 5. Create the Git tag

Only the Test and Release PM “Closer” may do this, after satisfying all six ADR-016 conditions and confirming that `package.json`, the Android version, APK name, release notes, and handoff card all identify the same version. Other PMs must not create tags directly.

```cmd
git tag -a vX.Y.Z -m "vX.Y.Z release"
git push origin vX.Y.Z
```

### 6. Write release notes
Complete the vX.Y.Z section in `Docs/1-需求文档/需求历史.md`.
GitHub Release and APK distribution are Class C; AI must not perform them. zlbdh publishes manually if needed.

### 7. Install
- zlbdh's own phone.
- APK sharing with friends or family, if desired.

## Emergency fix: directly on main

### Trigger
- A P0 bug appears after installing the current release: data loss, startup crash, or AI not working.

### Process
1. Stay on `main`; first confirm all six ADR-016 commit/push conditions.
2. Fix the code and add regression coverage.
3. Run all three QA layers.
4. Build the next patch development APK for zlbdh to install.
5. After verification, produce the release.
6. Tag the next patch version. No separate branch is created, so no merge step is needed.

### Version increments
- Small fix → next patch version.
- New feature → next minor version.
- Major version → v4.0.
