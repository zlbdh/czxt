# Implementation Loop — Appendix

> Primary entry point: [implementation loop](实施循环.md). Less frequent details live here to keep that entry point concise.

## Design phase

### Data

- Is a new table or schema change needed?
- Does `useAppData` need new actions?
- Is a migration needed?

### UI

- Which page and position contain the entry point?
- Can existing components be used, or are new components needed?
- Are error, loading, and empty states covered?

### File list

Use `+ / M / D`, for example:

```text
+ src/shared/NewComponent.jsx
M src/features/health/Health.jsx
M src/shared/database.js
M src/shared/database.test.js
```

Record it in the relevant requirement section of `Docs/3-开发文档/sprint-N-技术拆解.md`.

## Code phase

Recommended order:

1. Data layer: database, defaults, and shared helpers.
2. Component layer: `components.jsx`.
3. Feature layer: `features/*.jsx`.
4. Tests.

Check for truncation after editing each key file:

```bash
wc -lc src/path/file.jsx
tail -3 src/path/file.jsx
```

See [known technical constraints](../../能力资产/rules/已知技术约束.md) for file sizes, mount write limits, and splitting recommendations.

## Test phase

All three layers must pass:

1. esbuild syntax.
2. vitest: existing tests remain intact and new tests pass.
3. vite build.

If any fails, return to fixes. Do not report done first.

## APK and smoke

Sandboxes normally do not produce APKs. Three routes are available:

- The Test and Release PM “Closer” uses an available runtime to run `powershell -NoProfile -ExecutionPolicy Bypass -File .\build-apk.ps1`, then archives to `{{APP_REPO_DIR}}/apk/{{PROJECT_NAME}}-vX.Y.Z-debug.apk`.
- zlbdh manually runs the same script on a local Windows machine.
- GitHub Actions provides a manual fallback build; see `Docs/5-运维文档/GitHubActions说明.md`.

Run smoke testing from `Docs/4-测试文档/手动测试用例.md`. Specifically test new features; return to fixes if a bug appears.

## Closeout details

- Move the item from Sprint X to completed in `Docs/1-需求文档/需求历史.md`.
- Update the top-level `README.md` for user-visible changes.
- Mark the task plan / handoff state completed.
- Report to zlbdh using chat summary ①–⑦: changes, test results, APK location, detail card, and PM transitions.
