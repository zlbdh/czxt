# Workflow: Implementation Loop

The standard cycle from confirmed requirements to deployed code. This document keeps frequent entry points and mandatory constraints. Phase details, the complete runtime capability table, and APK/smoke details are in the [implementation appendix](实施循环-附录.md); the complete DoD is in the [DoD checklist](实施循环-DoD.md).

## ⭐ Required session startup

**At the start of every session**, follow `AGENTS.md` and the [main entry point](../00_总入口.md) through status, roles, handoff, and health checks. Then use [status inference](../../能力资产/skills/状态推断.md) as a supplementary reconciliation:

1. Read root `状态.md`, the main entry point, role boundaries, and the latest pending handoff card.
2. Run the project health check and any necessary status inference to find the previous stopping point and reconcile APK/progress records.
3. Do not interrupt the user: keep the inferred results as internal context, and proactively report them only when asked or when a conflict appears.

After 30 or more consecutive interactions in a session, another pass is recommended to prevent process drift.

## ⭐ Three-level process-first triage: PROP-014 / ADR-018

If a process problem appears before or during implementation—misaligned rules, false warnings, inconsistent documentation, or incorrect paths—classify its severity:

| Severity | Symptom | Action |
|---|---|---|
| 🔴 Blocking | Prevents code, tests, or implementation | Stop immediately; open a governance PROP, fix the process, then resume business work |
| 🟡 Nonblocking bug | False warning, inconsistent documentation, or wrong path; work can continue but risk remains | Continue business work and immediately add the issue to the RETRO backlog |
| 🟢 Improvement opportunity | A different approach might be better; no immediate obstacle | Continue business work and discuss at the next RETRO |

The goal is to keep process from obstructing business work while keeping business work from burying process debt.

## ⭐ Required handoff matrix: PROP-014 / ADR-018

At implementation completion, both forms are mandatory: the full file and chat summary ①–⑦.

| Activity | Full handoff card required? | Chat summary ①–⑦ required? |
|---|---|---|
| ✅ Cross-role transition: PM responsibility is primary; Cowork / Claude Code / Codex are only runtimes | Required | Required |
| ✅ Implementation completion: code, framework, QA, or push | Required | Required |
| 🟡 Work within a PM role: PRD, option selection, or answers | Update `状态.md` only | Optional; recommended for tasks with more than three steps |
| ❌ Temporary discussion: confirmation or simple questions | No | No |

See the [handoff format](../03_交接/交接卡格式.md), which also defines chat summary ①–⑦.

## Phase overview

```text
Requirements (PRD)
   ↓
Design (data / UI / file list)
   ↓
Code (file by file)
   ↓
Tests (vitest + esbuild + vite build)
   ↓
APK (Test and Release PM / Windows / GitHub Actions)
   ↓
Smoke test
   ↓
CHANGELOG / 状态.md / handoff card
   ↓
Wait for the next requirement
```

| Phase | Required output | Details |
|---|---|---|
| Design | Data, UI, and file list in the relevant requirement section of `Docs/3-开发文档/sprint-N-技术拆解.md` | [Appendix](实施循环-附录.md), Design phase |
| Code | Data layer → components → features → tests; check for truncation after file edits | [Appendix](实施循环-附录.md), Code phase |
| Tests | esbuild syntax, vitest, and vite build; return to fixes on failure and do not report done | [Appendix](实施循环-附录.md), Test phase |
| APK / smoke | Test and Release PM “Closer” ([playbook](../02_智能体/测试发布PM-闭环者.md)), zlbdh on Windows, or GitHub Actions; physical-device smoke follows the manual test cases | [Appendix](实施循环-附录.md), APK and smoke |
| Closeout | CHANGELOG, `状态.md`, handoff area, chat ①–⑦; close PRD/PROP when needed | [DoD checklist](实施循环-DoD.md) |

## PM DoD boundaries

- **Operating System PM “Framework Steward” DoD**: documentation, static validation, project health check, status inference, handoff card, and status record.
- **Development PM “Implementer” DoD**: business code, tests, and a vitest/necessary-build self-test report; no version bump, APK production, physical-device smoke, or default commit/push.
- **Test and Release PM “Closer” DoD**: tests, build, APK, physical-device smoke, and conditional commit/push/tag. Codex may currently host this role; zlbdh may verify manually.
- **Runtime capability does not confer PM authority**: permissions come from [role boundaries](../01_架构/角色边界.md) and [Git flow](git流程.md).

**Six Git commit/push conditions** (PROP-012 / ADR-016): ① main only; ② truthful commit message; ③ no force or rebase; ④ no retry after failure; ⑤ explicit hash in the handoff; ⑥ contextual authorization.

An implementation completion report must state which checks I ran and which remain for zlbdh.

## Definition of Done

The complete DoD—L1–L4, cross-session synchronization, and failure fallback—is maintained in the standalone [DoD checklist](实施循环-DoD.md).

**Six mandatory core items**; see the [DoD checklist](实施循环-DoD.md) for details:

- [ ] **Decision checkpoint** Q1–Q7 completed: PROP-020 path D / issue AJ misrouting defense plus ADR-038 agent instantiation; see [decision-checkpoint.md](decision-checkpoint.md).
- [ ] **Code** implements the PRD, with no remaining TODOs.
- [ ] **Tests**: vitest, esbuild, and vite build all pass.
- [ ] **PRD**: status moves from in progress to completed, with an entry in requirement history.
- [ ] **PROP archival**: status changes to completed, file is moved, and README counts are updated.
- [ ] **Both reconciliation skills** pass: project health check and status inference.

L1/L2 simplified checklists, additional items, cross-session synchronization, and failure fallback are in the [DoD checklist](实施循环-DoD.md).
