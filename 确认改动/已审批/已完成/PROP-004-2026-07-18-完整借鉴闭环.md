# PROP-004 · Complete Borrowing Lifecycle

- **Status**: Approved · Completed (implemented 2026-07-19 and hardened in final review 2026-07-22; ADR-039 is current)
- **Date**: 2026-07-18.
- **Responsible roles**: Project PM orchestrates and accepts; Operating System PM governs the framework; the target decision PM assesses; existing responsible PMs and implementation tools are selected according to target-path allowlists.
- **Change level**: L4.
- **Behavior class**: Class B, constrained local implementation and verification. After `content-deleted`, the operation is irreversible. Preserve residual objects whose ownership cannot be proven. Git and publication actions require separate authorization.

## Authorization basis

The user successively requested and confirmed, within the same task chain:

1. Learn from another operating system specified by the user and add borrowing support.
2. Choose option A and produce a plan first.
3. Review the plan and deliver the final version.
4. Set goals and continue driving implementation independently.

These instructions authorize continued local implementation of option A; the proposal is no longer pending approval. This authorization excludes commit, push, tag, release, publication, and external distribution. Any later need for those actions requires explicit authorization under ADR-016 and single-point execution by Test and Release PM.

## Goal

Turn one-off cross-project analysis into repeatable, auditable, instantiable borrowing: freeze a source version, record candidates and adoption decisions, adapt approved material to the current project, close items with verification evidence, and retain rejected, deferred, and historical versions.

This builds an operating system template capability:

- The template contains neutral skeletons, rules, and tools, without concrete historical source cards, item cards, or source code.
- Instance business code must not directly depend on `借鉴区/`, source caches, or external content.
- Adopted material must be copied or adapted into existing target paths and governed by their responsible roles and verification systems.

## Implementation stages

### A. Gate 0: complete with evidence

Freeze the pre-task dirty workspace, establish Windows PowerShell 5.1 encoding/parsing gates, mechanically migrate the formal scope to UTF-8 BOM, and replace heuristic mode detection with explicit template/instance markers. A1 and A3 evidence outside the workspace preserves original bytes, hashes, manifests, and migration reconciliation. Existing changes must not be overwritten, deleted, or cosmetically restored through Git commands.

### B. Core capability: complete

Create one `借鉴区/` root, source capture cards, and borrowing cards, with permissions, safety rules, role routing, a sole skill entry point, a tested machine facade, and a complete workflow. Instantiation copies only an empty skeleton and does not overwrite instance data. The installer uses two-stage no-overwrite moves, physical final-path binding, and an output manifest. On a single-file transaction failure, retain auditable residual objects whose ownership cannot be proven. Do not promise global atomic rollback of the project tree.

### C. P4t and closure: complete

Contract tests implement a read-only offline P4t consistency guard. Temporary-instance dogfood, zero-business-dependency checks, P4s/P4t, and full health checks on both sides are complete. An unchanged source fingerprint returns REUSED; only changed fingerprints create a new capture. Closed-item references and seals remain unchanged. Isolation scanning uses an 8 MiB full-content boundary and 64 KiB prefix-observation boundary. Three rounds of actual reads share one fail-closed resource budget.

The close transaction restores the original active card only when ownership is proven and `content-deleted` has not been reached. `seal-ownership-unproven` preserves the current formal card and staging. After the irreversible `content-deleted` completion point, do not roll back the formal card. Never overwrite or delete later objects or failure residues based on guessed ownership.

## Boundaries and risk controls

- Do not execute, build, install, automatically refresh, or write upstream source content. Verification is offline.
- Do not record credentials, private access parameters, or local absolute paths as current template facts.
- Source capture identity is immutable. An unchanged fingerprint returns REUSED; a changed one creates a new capture. Existing items must not drift.
- A preexisting dirty workspace is existing work. A1/A3 external evidence is its protection baseline. Stop if reconciliation fails.
- Do not delete historical ADR/PROP text. Express current evolution through ADR-039 and top-level overriding pointers.
