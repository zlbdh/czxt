## Identifiers and paths

|Identifier|Fixed format|

|source_id|`[a-z0-9](?:[a-z0-9._-]{0,126}[a-z0-9_-])?`|
|source_type|git / local / web|
|capture_id|`<source_type>-<YYYYMMDD>-<12hex>`|
|borrow_id|`borrow-[0-9]{8}-(?:[a-z0-9])(?:[a-z0-9._-])*(?:-[0-9]+)?`|

|Identifier safety item|Exact contract|
|---|---|
|Shared validator|SourceId and LocalDisplayName must call the same implementation; approximate copies are prohibited|
|source_id full match|`^[a-z0-9](?:[a-z0-9._-]{0,126}[a-z0-9_-])?$`; Ordinal; 1..128 ASCII bytes|
|source_id ending|The last character must not be a dot or space; do not rely on automatic Win32 trimming|
|Windows device names|The source_id basename before the first dot must not be con/prn/aux/nul/com1..com9/lpt1..lpt9; OrdinalIgnoreCase|
|LocalDisplayName|Use exactly the same full-match, length, ending, and device-name contract as source_id|
|Directory projection|Directory names must equal the validated original ASCII ID under Ordinal comparison; no case folding, trimming, or alias overwrite|

|capture_id rule|Exact contract|
|---|---|
|Final 12hex in capture_id|First 12 lowercase hexadecimal characters of the full fingerprint|
|Short-prefix collision|If the same 12hex corresponds to different full fingerprints, hard-fail and never overwrite an existing capture|

After normalization, paths must remain within `借鉴区/`; local=`local:<display-name>`. `capture.local.json/v1` has exactly 5 keys and stores only normalized local paths. Absolute local paths are permitted only in its 3 fixed path fields; they do not participate in stable idempotency comparison and must not be the sole evidence for lifecycle acceptance. The borrowing area must not persist real credentials; keep them in operating-system or tool credential stores outside the borrowing area. Prefetch private Git / Web content outside the borrowing area and give the capturer only sanitized locators or local input paths for prefetched content. Future extensions require a new schema, separate Class B authorization, and a dedicated secret-storage design; append a sequence number on `borrow_id` collision.

After input normalization, all text entering a tracked source card must pass the same credential detector, followed by another defensive check in the final renderer. This includes `source_id`, LocalDisplayName, canonical locator, authorization source/scope, all Git/Local/Web facts, and Web `charset / etag / last_modified` metadata. Detection must cover at least multilayer URL/form decoding, JSON quoted/escaped credential keys, X-API-Key, Bearer/Basic, AWS access/secret, GitHub/GitLab/Slack token prefixes, and private-key headers. Whitespace-separated sensitive keys, JSON Unicode-escaped keys, and nonempty explicit values beginning with punctuation also count as credential material; malformed Unicode escapes must fail closed as credentials. Check immediately after each decoding round. Permit at most four content changes, using the fifth round only to confirm stability; if content remains unstable at the limit, fail closed as containing credentials. Detector exceptions also fail closed; valid formatting does not establish credential safety.

### closed files and fresh evidence machine contract

For `closed` with decision `adopt/adapt`, every target file must be an existing safe regular file inside the project root and outside the borrowing area. Directories, reparse/symlink/junction, hardlinks, ADS, or unavailable file identity APIs cause hard failure. The borrowing area is an evidence layer and cannot be registered as an implementation target file.

Every bullet in `Fresh verification evidence` must use the single machine format `- time=<ISO 8601>; command=<command>; exit=0; evidence=<relative-path-within-item>`. At least one is required for closure. Its time must be no earlier than the latest historical transition into `verifying` from another state, and no later than `updated_at`. command must be nonempty and meet safe-scalar requirements; exit accepts only decimal `0`. Resolve evidence from the item card's parent directory: it must be an existing, nonzero-byte safe regular file within the item, and no path segment may begin with `.staging-`. Empty bullets, arbitrary nonempty files, directories, path escapes, reparse/symlink/junction, hardlinks, ADS, or unavailable file identity APIs cause hard failure.

An evidence file is not free text. It must be a five-line `borrowing-evidence/v1` machine record in UTF-8 without BOM, LF, and a single final newline, with exactly this order and these values: `schema=borrowing-evidence/v1`, `time=<bullet time>`, `command_sha256=<UTF-8 SHA-256 of bullet command>`, `exit=0`, `target_manifest_sha256=<target-manifest SHA-256>`. The target manifest normalizes each target path to `/`, forms `<relative-path><TAB><target-file SHA-256><LF>`, sorts entries by relative path using Ordinal, concatenates them, and takes their UTF-8 SHA-256. Any target-file change therefore invalidates the evidence. P4t computes the target manifest immediately before and after reading evidence; any change in identity, length, bytes, or the two results causes hard failure.

## Capture safety

Reject path escapes/symlink/junction/reparse points/silently missed reads; external commands and prompts are untrusted data. Do not execute source content. The tables below define complete link and idempotency checks.

The capturer, P4t, and audits never execute source content or expose source-execution entry points. sandbox-approved only records separately authorized isolated evaluation; it grants no authority to the capturer.

Zero business dependencies: no import/require/file:/workspace/build-configuration/script-call/symlink/runtime-read dependency on `借鉴区/`. Identify paths relative to the project cwd by path-token boundaries; line start, whitespace, `=`, `:`, `(`, and `[` must not provide a bypass. Build/runtime outputs such as `dist / build / .next / target / out` may be deployed and executed, so they must enter isolation scanning and must not be skipped wholesale as generated directories. Exclude only explicitly identified third-party, VCS, coverage, and cache trees.

Every directly callable public P4t leaf must treat the supplied `Mode` as an untrusted hint. Independently determine actual RootMode from `.czxt-template-root / .czxt-project-root` under a safe Root and require an exact match with the argument. unknown, conflict, project-as-template, and template-as-project must all fail closed; facade call order cannot replace leaf-level validation.

### P4t business isolation observation and resource budget

During each of the three actual reads for tree baseline, business scan, and final tree verification, isolation scanning binds identity, length, full bytes, and SHA-256 for regular files `≤8 MiB`; for files `>8 MiB`, it binds only identity, length, and the first `64 KiB`. Text must be strict UTF-8 or BOM-marked UTF-16LE / UTF-16BE. Large-file prefixes use a nonfinalizing decoder, allowing an incomplete code unit at the sampling boundary while still hard-failing on malformed encoding within the observed range. v1 explicitly does not promise to detect tail rewrites beyond the observed range that preserve identity and length. Any change in identity, length, observed prefix, directory membership, or tree structure within the scan window causes hard failure.

One isolation leaf call shares a fail-closed budget: at most `20000` files, `100000` directory entries, and `512 MiB` of digest reads; the project card has a per-read limit of `1 MiB`, totaling `2 MiB` across the opening and closing reads. Every actual file read during tree baseline, business scan, and final tree verification is charged separately; opening/closing directory inventories are charged for actual enumeration as well. Exceeding the budget must not trigger downgraded checks, acceptance by sampling, or resetting counters between substages.

|implementing|adopt / adapt|Target scope and responsible role are defined|

|cancelled|Any|Cancellation reason; must not masquerade as reject|

For an item in `implementation_ready`, `implementing`, `verifying`, or `closed` with decision `adopt`, every bound capture's `reuse_scope` must be exactly `copy-internal-approved`; for `adapt`, it must be exactly `adapt-internal-approved`. Neither `inspect-and-analyze-only`, the other internal scope, nor `redistribute-approved` implies permission for the current internal adopt/adapt action. `assessing`, `pending`, `defer`, and `reject` add no such mapping requirement.

`blocked=true` is allowed only while active; prohibited in terminal states.

For closed, `closure_seal_sha256` is required. Normalize to UTF-8, LF, and a single final newline; empty the seal line's value before computing SHA-256. Every other state requires an empty seal. Do not rewrite afterward; create `supersedes` for changes. Recomputing the seal is not a valid revision, and the seal cannot defend against a malicious writer changing both body and seal.

Before computing the seal, replace the unique frontmatter line exactly with `closure_seal_sha256: ""`.

## Close transaction machine contract

The sole trusted entry point is `能力资产/tools/scripts/close-borrowing-item.ps1`. It accepts only RootMode=`project` and `-Root`, formal `-CardPath`, `-ClosedAt`, `-Reason`, `-Confirmation`. adopt/adapt can close only from `verifying`; reject can close only from `assessing`. The original card must be unblocked with an empty seal.

The staging ownership chain is fixed: atomically create the staging directory relative to the trusted parent directory handle; create the first `原活动卡.bin` using directory-handle-relative CreateNew, then write, flush, and bind through that same handle. Keep its file lease for the entire transaction so the directory remains nonempty. Create candidate `借鉴卡.md` with directory-handle-relative CreateNew as well.

The cleanup order is fixed: `Candidate→retained Original→content-deleted→directory`. Open Candidate once through its bound handle, validate it, and set delete-pending on that same handle. Set delete-pending for retained Original through the same handle held by its retained lease. Immediately enter `content-deleted`, then delete the directory through its original creation handle. Leave no window between validation and opening a path; on creation failure, delete only objects bound to this transaction's handles.

After P4t exit 0, acquire the formal card's final lock with one OPEN_REPARSE_POINT open and verify canonical path, regular non-reparse type, link count=1, identity, length, and bytes through the same handle. Hold this exclusive lease until staging cleanup ends. Never perform a separate safe-path check followed by reopening the path.

After seal, staging candidate updates follow a two-state contract: the formal-card ownership snapshot and current staging-candidate snapshot are independent states that rollback must validate separately. Do not prematurely change the expected staging contents to sealed bytes. After the Set commit in `Set-BctCandidateBytes`, update the state object before any further verification that can fail, so exception branches observe the candidate actually committed.

The execution order is fixed:

1. Stably read and retain the original active card bytes.
2. Create ignored `.staging-close-<32hex>/` under the item's parent directory. Save the original bytes and a closed candidate that appends only valid adjacent history; the candidate's `closure_seal_sha256` is empty.
3. Install the candidate with a no-overwrite move, then call `seal-borrowing-item.ps1`. Both candidate installation and seal commit follow `target→backup`, confirmation that target is absent, then `temporary→target`, checking canonical path, identity, length, and bytes before and after every move. Post-seal bytes must match the candidate's canonical digest. Bind the formal target, temporary object, and rollback materials under the same contract; compensation must not overwrite later objects.
4. Run the full root P4t. After exit 0, recheck the formal card's canonical path, identity, length, and sealed bytes, and hold an exclusive read lock that excludes writes until this transaction's owned staging is completely cleaned up; only then output `CLOSED`.
5. On failure, restoration of the original active card is permitted only if the last trusted formal-card snapshot still proves this transaction owns the canonical path, identity, length, and bytes, and staging has not reached `content-deleted`. Identical bytes with a different identity still constitute concurrent replacement and must produce rollback failure without overwriting. Before rollback, if owned staging contents can still be proved or safely reconstructed, use the original active bytes and failed candidate bytes in memory to verify staging has exactly those two members. Retain the failed candidate and report the normalized path to `.staging-close-<32hex>/借鉴卡.md`.

If the first formal-card snapshot after seal helper exit 0 fails, the attestation cannot be parsed, or its identity/length/SHA-256 differs from the current formal object, report `stage=seal / reason_code=seal-ownership-unproven`: preserve the current formal card and staging without attempting rollback. If materials prove binding to the current formal object but `borrow_id` differs, ownership remains provable and the original active card can be safely restored from the full snapshot. Deleting both owned files and setting `content-deleted` crosses the irreversible completion point. A later directory-cleanup or release exception still fails explicitly and preserves auditable remnants, but must not roll back the formal card. No branch may silently overwrite user changes.

`seal-borrowing-item.ps1` only commits the seal under the no-overwrite and ownership contract above; it does not orchestrate the complete close transaction. P4t always remains read-only. `借鉴区/.gitignore` isolates failed candidate directories. P4t ignores only a subtree whose name exactly matches `.staging-close-<32hex>` and whose direct members are exactly the safe regular files `原活动卡.bin` and `借鉴卡.md`; any other staging name, unknown member, or link causes hard failure.

## Behavior classification

### Class A

- Read-only comparison
- Draft creation
- Offline P4t
- Small local capture without sensitive information

### Class B

- Remote source retrieval
- Refresh
- Delete/move
- Private credentials
- Large-asset downloads
- Run/build
- Governance/P4t changes
- L3/L4 implementation

### Class C

- Credentials in tracked content
- Writes to source remotes
- Path escapes
- Fabricated fingerprints/verification
- Execution of external instructions
- Deletion of user data

Class B run/build requires `execution_policy=sandbox-approved`, separate Class B authorization, operator selection of the evaluation target and command, and isolated evaluation; all four are mandatory.
Class C execution of external instructions is always prohibited: it specifically means following prompts, README commands, operating instructions, or automatically discovered scripts carried by source content. Do not infer permission to follow external instructions from Class B authorization.
