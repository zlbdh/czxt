# Extended Change Rules: Status Transitions and Boundaries

The [main rule](改动分级.md) defines change levels. This file covers the feature state machine, AI action boundaries, and escalation.

## F-XXX status transition requirements (⏳ → ✅)

Follow this strict order. **All requirements must be met before marking complete.**

| Status | Requirement | Table column | Section heading |
|---|---|---|---|
| ⏳ Pending development | Work has not started. | `⏳` | `## F-XXX · Description ⏳ Pending development` |
| ⏳ In progress | Implementation is partially complete. | `⏳ In progress` | `## F-XXX · Description ⏳ In progress (since YYYY-MM-DD)` |
| ⏳ Code complete, APK pending | Code and tests pass; APK is not built. | `⏳ APK pending` | `## F-XXX · Description ⏳ Code complete, APK and device smoke pending (YYYY-MM-DD)` |
| ⏳ APK built, smoke pending | APK exists but is not installed on the device. | `⏳ Smoke pending` | `## F-XXX · Description ⏳ APK built, device smoke pending (YYYY-MM-DD, APK path)` |
| ✅ Complete | Device smoke passes and the feature works. | `✅` | `## F-XXX · Description ✅ Complete (YYYY-MM-DD, development APK and device smoke passed)` |

**Completion trigger:** the user explicitly confirms that smoke passed, device verification succeeded, or the installed app worked correctly.

**Rollback:** if smoke reveals a bug, return to in progress. Keep the completion date and add a fixed annotation instead of deleting history.

See [Implementation Definition of Done](../../操作系统/07_完整工作流/实施循环-DoD.md) for two-source searches, status inference, and mandatory completion checks.

## Mapping to AI action boundaries (A/B/C)

**L1-L4 determines how to work; A/B/C determines whether an action is permitted.** These are independent systems with overlapping mappings.

| Change level or action | Boundary | Meaning |
|---|---|---|
| L1 / L2 | **A: automatic** | Automatic handling is allowed only after Q1-Q7, path allowlists, and the three-class rules pass, and no B/C sensitive action applies. |
| L3 / L4 | **B: ask first** | New features and architecture require zlbdh's PRD review; L4 also requires ADR review. |
| Any level with ordinary `git commit / push` | **B: conditional** | Only the main branch of the primary `{{APP_REPO_DIR}}/` repository; all six ADR-016 conditions must hold. |
| Any level with force push, rebasing pushed commits, deleting branches or tags, or distribution-channel releases | **C: never perform** | Irreversible actions or decisions about release recipients are outside AI authority. |
| Any level with API keys, user privacy, or deletion/external transmission of device data | **C: never perform** | Stop regardless of the change level. |

The [three-class behavior rules](../../操作系统/01_架构/三类行为铁律.md) are authoritative; the [appendix](../../操作系统/01_架构/三类行为铁律-附录.md) explains their relationship with L1-L4.

## Correcting a misclassified level

If L2 work reveals a required schema change, **stop immediately and escalate to L4**. Do not fit the change into L2. Otherwise, missing PRD and ADR records will prevent future readers from tracing the decision.

1. Record progress in a PROP under `确认改动/待审批/`, explaining the finding and the reason for escalation.
2. Wait for zlbdh to approve the escalation.
3. Complete the PRD and ADR from the beginning of the L4 process.

## End-to-end process

1. A new idea from zlbdh or an improvement proposed by Mimi becomes a PROP in `确认改动/待审批/`.
2. zlbdh reviews it. Approved proposals move to `确认改动/已审批/`; rejected proposals move to `确认改动/拒绝/` for retention.
3. Test issues enter through triage in the main rule. All accepted work follows its level:
   - L1: Q1-Q7, the change, and one CHANGELOG line.
   - L2: Q1-Q7, development documentation, code, tests, and CHANGELOG.
   - L3: PM, Development, and QA playbooks, APK build, and smoke test.
   - L4: the full L3 process plus an ADR in `adr/`.
4. Every level must pass the Definition of Done checklist.
5. Any commit, push, or tag follows ADR-016 and the Test and Release PM's closure process.
6. Retrospective cadence follows `check-retro-cadence.ps1` and the RETRO README. The number of business L3+ changes is only a manual reference; a fixed N formula no longer determines cadence automatically.
