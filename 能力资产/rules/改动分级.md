# Rule: Change Levels (L1-L4)

Expand the existing small/large distinction into four levels and include **test issue triage**. Before each change, Mimi determines its level and records it in the task description so zlbdh can immediately see whether review is required.

## Four-level reference

| Level | Description | Examples | Process | Decision authority |
|---|---|---|---|---|
| **L1** | Copy or a small localized change | Subtitle, typo, one color parameter, unused console.log | After Q1-Q7, the path allowlist, and the three-class behavior rules pass, the responsible PM makes the change and adds one CHANGELOG line. | Responsible PM if no B/C restriction applies; Project PM accepts the work. |
| **L2** | Small behavior adjustment or localized bug | Adjust existing behavior, fix a specific bug, add an error message | After Q1-Q7, the path allowlist, and the three-class behavior rules pass, update the relevant `Docs/3-开发文档/` section, code, tests, and CHANGELOG. | Responsible PM if no B/C restriction applies; commits and releases still follow ADR-016. |
| **L3** | New feature or module | Any new `F-XXX` feature, changes spanning multiple files, UI entry changes | Full process: Product PM writes PRD → Development PM implements → Test PM / Test and Release PM verifies → APK → smoke test. | **zlbdh must review the PRD.** |
| **L4** | Architecture or data schema change | New table, schema field, tab, module split, router replacement, native plugin | Full L3 process plus ADR in `Docs/3-开发文档/adr/`. | **zlbdh must review the PRD and ADR.** |

## Triage incoming test issues

For a bug, exception, or unexpected result, **triage before fixing**:

- A localized logic or boundary fix with no product behavior change: L2.
- A fix requiring product behavior changes visible to users: L3; follow the requirements process and write a new PRD.
- A fix involving architecture or data schema changes: L4; an ADR is required.

Triage prevents introducing new features under the label of a bug fix and leaving the PRD inconsistent with the code.

## Existing terminology

| Existing term | Levels |
|---|---|
| Small change | L1 + L2 |
| Large change | L3 + L4 |

The two-way distinction remains valid; L1-L4 adds detail. A Sprint describes **time or a batch**, independently of change level. A Sprint commonly contains several L3 and L2 changes.

## Task labels

Put the level in square brackets at the beginning of each new task title:

```text
[L1] Change Mimi's subtitle to “Personal Growth Plan”
[L2] Fix overlapping X-axis labels in the Health calendar
[L3] F-001 Tap a calendar date to view that day's details
[L4] F-XXX Add custom tasks (new customTasks table)
```

L3/L4 means work **must wait for zlbdh's review**. L1/L2 means the responsible PM may proceed within the allowlist and applicable gates.

## Extended rules (split under PROP-008 / ADR-011)

The [extended rules](改动分级-扩展规则.md) cover:

- F-XXX status transitions: pending development → in progress → pending APK → pending smoke → complete.
- Mapping L1-L4 to AI action boundaries A/B/C.
- Misclassification and escalation, such as discovering a schema change during L2 work.
- The end-to-end process from proposals and test triage through Definition of Done.
