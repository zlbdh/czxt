# Brand Dictionary: Project Instance Template

Project, Operations, and other PMs must consult this dictionary before writing public content, documentation, commit descriptions, or replies. During initialization, fill it from the project card, application repository, and local untracked configuration. Keep unverified fields “Pending confirmation”; never inherit source-project facts.

### 2.1 Protocol layer and model layer are distinct

Application code sends a `<protocol>` request to `<service-base-url>` or a gateway. The service routes according to the actual `<model-id>` to a `<model-provider>` model or downstream service, then returns a `<protocol>` response.

- The **protocol layer** describes request, authentication, and response formats.
- The **service layer** identifies the first provider or gateway receiving the request.
- The **model layer** identifies the actual model and provider performing inference.
- Protocol compatibility establishes interface compatibility only. **It cannot independently establish model identity, service-provider identity, or data location.**
- Brand names in variables, SDKs, or URL paths still require verification against actual configuration, consoles/contracts, and request evidence.

### 2.2 Verification order

1. Read the current project card for registered product claims and local configuration locations.
2. Inspect `model`, `baseUrl`, protocol, and gateway settings in local untracked configuration. Never copy real keys into tracked files.
3. Compare the service console, contracts, billing, or official provider material to establish service and model ownership.
4. If needed, verify actual routing with nonsensitive request logs or response metadata.
5. Data residency, cross-border transfers, compliance, and commercial licensing remain “Pending confirmation” without written evidence.

## 3. Public communication

### Acceptable statements

- All facts confirmed: “{{PROJECT_NAME}} currently uses <public-model-name> from <model-provider>, called through <protocol>.”
- Only service layer confirmed: “Requests currently reach <service-provider-or-gateway>; the final model identity is still being verified.”
- Residency unconfirmed: “Data residency and cross-border transfer status await written confirmation; no public commitment is made yet.”

### Prohibited claims

- Claiming a protocol owner's model is used solely because its protocol is supported.
- Treating a brand in a model string or URL as proof of the final model provider.
- Presenting domestic/overseas, official/third-party, or compliant/noncompliant status as fact without current project evidence.
- Exposing API keys, tokens, or credentials in this dictionary, commit descriptions, screenshots, or chat.
- Filling missing current-instance fields from old projects, template examples, or memory.

### Response templates

| Question | Response |
|---|---|
| Which model do you use? | “The confirmed fact is <confirmed-fact>. We will not guess about the model ID/provider details still awaiting <evidence>.” |
| Is it the protocol owner's model? | “<protocol> is an interface protocol. The protocol layer is distinct from the model layer. Actual configuration and provider evidence determine the final model.” |
| Does the request pass through a third party? | “The confirmed service chain is <confirmed-service-chain>. Unverified gateways or downstream services remain unconfirmed.” |
| Does data cross borders? | “Data residency / transfer status is <confirmed-or-pending>. Without written evidence, the public status is pending confirmation.” |
