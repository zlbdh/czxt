### 2.1 协议层不等于模型层

```
应用代码
  ↓ 使用 <protocol> 请求格式
<service-base-url> / 网关
  ↓ 按实际请求中的 <model-id> 路由
<model-provider> 的模型或下游服务
  ↓
按 <protocol> 格式返回响应
```

- **协议层**只描述请求、认证和响应格式。
- **服务层**描述请求先到哪个提供商或网关。
- **模型层**描述最终执行推理的具体模型和提供商。
- 协议兼容只能证明接口形状兼容，**不能单独证明模型身份、服务商身份或数据驻留地点**。
- 即使变量名、SDK 名或 URL 路径含某品牌词，也必须结合实际配置、控制台 / 合同和可核验请求证据确认事实。

### 2.2 AI 事实确认顺序

1. 读取当前项目卡，确认已登记的产品口径和本机配置位置。
2. 读取本机未跟踪配置中的 `model`、`baseUrl`、协议和网关设置；绝不复制真实 key 到 tracked 文件。
3. 对照服务控制台、合同、账单或提供商正式资料，确认服务商与模型归属。
4. 必要时用不含敏感信息的请求日志或响应元数据核验实际路由。
5. 数据驻留、跨境、合规、商用授权等没有书面证据时一律保留“待确认”。

## 三、对外沟通规则

### 可以这样说

- 已确认全部事实：`“{{PROJECT_NAME}} 当前接入 <model-provider> 的 <public-model-name>，通过 <protocol> 协议调用。”`
- 只确认服务层：`“当前请求接入 <service-provider-or-gateway>；最终模型身份仍在核验，不作确定性承诺。”`
- 数据驻留未确认：`“数据驻留与是否跨境待书面确认，当前公开口径不作承诺。”`

### 不能这样说

- 不能因为兼容某协议，就宣称使用该协议所属公司的模型。
- 不能因为 model 字符串或 URL 含品牌词，就直接宣称该公司是最终模型提供商。
- 不能把“国内 / 海外”“官方 / 第三方”“合规 / 不合规”写成事实，除非有当前项目证据。
- 不能在品牌词典、提交说明、截图或 chat 中暴露 API key、token 或其他凭证。
- 不能用旧项目、模板示例或记忆补齐当前实例的空字段。

### 常见问答模板

| 用户可能问 | 标准回答模板 |
|---|---|
| 你们用的是什么模型？ | 当前已确认的是 `<confirmed-fact>`；模型 ID / 提供商仍待 `<evidence>` 确认的部分不作猜测。 |
| 用的是某协议所属公司的模型吗？ | `<protocol>` 是接口协议；协议层不等于模型层。最终模型以本机实际配置和提供商证据为准。 |
| 请求是否经过第三方？ | 当前服务链路为 `<confirmed-service-chain>`；未确认的网关或下游不作承诺。 |
| 数据会出境吗？ | 数据驻留 / 跨境状态为 `<confirmed-or-pending>`；没有书面证据前公开口径为“待确认”。 |
