# Skill: Borrowing

This skill is the sole operator entry point for the borrowing lifecycle. Follow the [borrowing governance rules](../rules/借鉴治理.md) for decision boundaries and the [complete borrowing workflow](../../操作系统/07_完整工作流/借鉴闭环.md) for roles and state transitions; see the [command appendix](借鉴-命令附录.md) for trusted executor calls.

## Triggers and modes

Enter this skill when a request involves borrowing, referencing, benchmarking, incorporating ideas, learning from another project, adding a reference source, updating a reference source, or auditing a reference source.

There are exactly four modes:

- **Intake**: Freeze and register one source version.
- **Assessment**: Compare existing capabilities and record an adoption decision.
- **Adoption**: Adapt approved content to the responsible target paths and verify it.
- **Audit**: Check existing sources, items, and evidence without writing.

## Common prerequisites

First settle the **target problem**, then confirm the **source**, and finally specify the **permitted actions**; apply **A/B/C** to determine whether to proceed and whether separate confirmation is required.

Dot-source the fixed trusted path `能力资产/tools/scripts/check-os/framework-scope.ps1` before calling `Get-CzxtRootMode`; operators must not substitute another loading path.

Call `Get-CzxtRootMode` **before any write**. Map its `project` return value to the human label `project-only`; only this result permits a write branch. Map `template` to `template-only`, which permits only offline, read-only auditing. For `unknown` or `conflict`, **reject all modes without writing**. A non-project root must not create `staging`, cards, or `local state`. Implementations must compare the actual function return values, not the human labels.

| RootMode | Modes permitted by the skill | Write boundary |
|---|---|---|
| project | Intake / Assessment / Adoption / Audit | Only project permits writes |
| template | Offline, read-only P4t audit only | Writes prohibited |
| unknown / conflict | None | Hard failure with zero writes in every mode |

## Intake

Intake also requires RootMode=project; reject template, unknown, and conflict during preflight.

1. Complete the [common prerequisites](#common-prerequisites); reject `template-only / unknown / conflict` during preflight in all cases.
2. Have the skill call `能力资产/tools/scripts/capture-borrowing-source.ps1`; operators must not assemble the underlying capture steps themselves.
3. Read the executor's `P4t` gate result; output `ready` only for `exit 0`.

## Assessment

1. Inventory **current capabilities** first to avoid introducing an existing capability again.
2. Fill in the **candidate matrix**, recording each potential borrowing point, conflict, rationale, and evidence.
3. State separately what is **explicitly adopted** and **explicitly not adopted**.
4. Update `decision` from these records; the existence of a source is not an assessment conclusion.

## Adoption

Run `Q1-Q7` again, determine `L1-L4`, and obtain the required approvals. Then use the target path allowlist to identify the target paths and responsible PM before implementation. Before entering `implementation_ready`, check each source binding: `adopt` accepts only `copy-internal-approved`, and `adapt` accepts only `adapt-internal-approved`. Do not infer implementation permission from any other `reuse_scope`. Record `fresh verification evidence` after completion. A borrowing item must not expand source permissions or any role's write permissions.

## Audit

Keep the entire audit read-only and offline while checking cards, references, and evidence. Do not access the network, execute source content, refresh sources, or write cards. Run `P4t` at the end.

## Closure and failure

Check the closure conditions first; never fill in or recompute `closure_seal_sha256` manually. Close through the trusted entry point `能力资产/tools/scripts/close-borrowing-item.ps1`. It internally calls `seal-borrowing-item.ps1` and runs the full root `P4t`. After exit 0, it must still hold the final lock while rechecking the formal card's identity, length, and sealed bytes and cleaning up this transaction's staging. Output closed only after every step succeeds. See the [command appendix](借鉴-命令附录.md) for parameters and machine output; the borrowing governance rules above remain the sole authority for fields and transaction invariants.

Both candidate installation and seal commit use no-overwrite and must not overwrite any later object. If the materials returned by seal are bound to the current formal object and only `borrow_id` differs, ownership is still provable, and the original active card can be safely restored from the full snapshot. Other `seal-ownership-unproven` branches must preserve the current formal card and staging. Do not roll back the formal card after reaching the irreversible `content-deleted` completion point.

### Close transaction

| Closing order | Exact action | Failure boundary |
|---|---|---|
| 1 | Retain the original active card bytes | The externally visible state remains the original active state |
| 2 | Construct the closed candidate | Set state and history to closed; leave closure_seal_sha256 empty |
| 3 | Install the candidate with no-overwrite and call seal-borrowing-item.ps1 | A seal helper failure must not be reported as closed; never overwrite later objects |
| 4 | Run root P4t | Exit 0 only permits final-lock verification; do not output closed yet |
| 5 | Hold the final lock while verifying and cleaning up staging | Identity, length, and sealed bytes must remain stable; deleting both owned contents reaches the irreversible content-deleted completion point; output closed only after directory cleanup succeeds |
| Provable failure | Restore the original active card only if ownership is provable and content-deleted has not been reached; retain the failed candidate in ignored staging | Explicitly report the failed stage and normalized paths; never claim closed |
| Unproven ownership or irreversible completion | For seal-ownership-unproven, preserve the current formal card and staging; after content-deleted, do not roll back the formal card | Preserve auditable remnants and fail explicitly; overwriting or speculative recovery is prohibited |

This transaction applies to both adopt/adapt and reject. Roll back only while the transaction can still prove ownership of the formal object and has not reached content-deleted. For seal-ownership-unproven or a failure after irreversible completion, preserve evidence and do not roll back the formal card.

On failure, report the failed stage, reason, `staging path`, and recovery advice. Never claim ready or closed, reset, delete user changes, overwrite later objects, or attempt speculative rollback. For `seal-ownership-unproven` or failures after `content-deleted`, preserve the current formal card and staging/auditable remnants unchanged for manual review.

For zero-write preflight failures, the fixed staging output is `none(not-created)`.
Output its normalized path only when staging already exists.
