# 依赖矩阵（项目实例填写模板）

> **项目实例真值**：本文件不预置任何语言、框架、包管理器或版本。实例化后先读取项目卡，再以业务仓库当前的 manifest、lockfile、版本文件、脚本和 CI 配置回填；模板示例不得覆盖仓库真值。

---

## 一、真值来源与读取顺序

| 优先级 | 真值来源 | 读取要求 |
|---|---|---|
| 1 | 当前项目卡（`项目配置/*.project.json` 或项目实例登记路径） | 确认 `{{APP_REPO_DIR}}`、当前版本、仓库边界和项目特别约束 |
| 2 | 真实 manifest | 在 `{{APP_REPO_DIR}}/` 内识别实际存在的依赖声明文件；不得默认文件名或生态 |
| 3 | 真实 lockfile | 读取实际锁定版本、解析结果和包管理器；没有 lockfile 时如实标为“未发现” |
| 4 | 仓库命令与环境声明 | 从 scripts、任务文件、版本文件、容器配置和 CI 工作流读取安装、测试、构建及运行命令 |
| 5 | 当前交接卡与验证记录 | 只用于确认本次改动和验证结果，不能反向覆盖 manifest / lockfile |

发生冲突时，先以当前仓库可执行状态为证据，并在交接卡记录项目卡或文档漂移；不要凭模板记忆修正业务仓库。

## 三、依赖清单

### 运行时依赖

| 依赖 | 声明约束 | 锁定版本 | 用途 | 兼容约束 | 证据 |
|---|---|---|---|---|---|
| `<dependency-name>` | `<declared-range>` | `<locked-version>` | `<purpose>` | `<runtime-or-peer-constraint>` | `<manifest-and-lockfile>` |

### 开发 / 构建 / 测试依赖

| 依赖 | 声明约束 | 锁定版本 | 用途 | 兼容约束 | 证据 |
|---|---|---|---|---|---|
| `<dev-dependency-name>` | `<declared-range>` | `<locked-version>` | `<purpose>` | `<toolchain-constraint>` | `<manifest-and-lockfile>` |

填写规则：

- “声明约束”来自 manifest，“锁定版本”来自 lockfile；两列不得互相替代。
- 工作区、多模块或多语言仓库按 manifest 分组，不把不同依赖图混成一张无来源清单。
- 伴生包、插件与运行时需要同版本族时，写明约束和证据，不从包名猜测兼容关系。
- 仓库没有某类依赖时写“无 / 未发现”，不要保留模板占位行冒充现状。

## 四、不在依赖清单里的关键工具

| 工具 / 外部服务 | 当前版本或身份 | 用途 | 配置来源 | 验证命令或证据 |
|---|---|---|---|---|
| `<runtime-or-build-tool>` | `<version>` | `<purpose>` | `<version-file-or-environment>` | `<version-command>` |
| `<external-service>` | `<provider-or-service-id>` | `<purpose>` | `<local-untracked-config-or-project-card>` | `<non-secret-evidence>` |

规则：

- 本机 SDK、编译器、容器、数据库、外部 API 等只从真实环境和仓库配置读取。
- 密钥只允许存在于本机未跟踪配置或受控密钥系统；本文件只记配置位置和非敏感身份，不写真实密钥。
- AI 服务的提供商、模型、协议与地址口径见 [品牌词典.md](../shared/品牌词典.md)，四者不得互相推定。

## 五、依赖升级策略

1. 不为“追新”主动升级；先写清业务收益、受影响面和不升级风险。
2. 从真实 manifest / lockfile 确认当前基线，再查运行时、伴生包、插件、构建链和部署环境兼容性。
3. 升级前必须给出回滚点、数据 / 配置迁移影响、许可证变化和已知安全风险。
4. 按 [`../rules/改动分级.md`](../rules/改动分级.md) 与 [`../../操作系统/01_架构/三类行为铁律.md`](../../操作系统/01_架构/三类行为铁律.md) 判级；触及产品方向、数据迁移、发布链或 framework 时升级治理，不按版本号大小机械判定。
5. 实施后同步 manifest 与 lockfile，执行项目实例定义的 `<test-command>`、`<build-command>` 和必要 smoke，并在交接卡记录结果。

### lockfile 规则

- lockfile 路径和类型以业务仓库实际文件为准，不默认某一种包管理器。
- 已有 lockfile 时，依赖变更必须解释对应 diff；不得只改 manifest 后漏交 lockfile。
- lockfile 缺失、冲突或由不同工具重写时先停手查明原因，不手工伪造锁定结果。

## 六、添加新依赖流程

新增依赖默认是 **B 类行为**，必须先确认再实施：

1. **产品 PM** 明示所需能力和验收标准，确认不是“为了方便”无边界引包。
2. **开发 / 技术侧读取真值**：确认当前语言、依赖工具、manifest、lockfile、运行时和仓库命令。
3. **技术 PM 评估**：至少覆盖替代方案、版本兼容、维护活跃度、包体 / 性能影响、回滚方案、许可证和安全风险。
4. **项目 Owner / 当前项目授权人明确批准 B 类**（具体身份以项目卡为准）；未批准不得执行安装命令或改 manifest / lockfile。
5. 按改动等级决定是否需要 PROP / ADR，并在批准范围内由开发 PM 实施。
6. 执行项目实例定义的测试、构建和 smoke；同步 lockfile、依赖矩阵及交接卡证据。
7. 测试发布 PM 按项目实例发布门禁复核；git 动作仍受 ADR-016 六条件约束。

## 七、体检与维护

- 首次实例化、依赖新增 / 升级、运行时变化、构建链变化时复核本文件。
- 每次复核都重新读取项目卡、manifest、lockfile 和仓库脚本；不得复制上一个项目的版本清单。
- 发现本文件与仓库不一致时标记漂移并按证据修正，不能把文档声明当作安装结果。
- 维护责任：操作系统 PM 维护模板结构；项目实例的依赖真值由项目 PM 协调相关 PM 验证。
