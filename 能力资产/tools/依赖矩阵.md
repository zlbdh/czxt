# Dependency Matrix: Project Instance Template

**Project instance source of truth:** this template prescribes no language, framework, package manager, or version. After initialization, read the project card and fill it from the application repository's current manifests, lockfiles, version files, scripts, and CI configuration. Template examples must never override actual repository facts.

## 1. Evidence and reading order

| Priority | Source | Requirement |
|---|---|---|
| 1 | Current project card, `项目配置/*.project.json` or registered instance location | Confirm `{{APP_REPO_DIR}}`, version, repository boundaries, and project-specific constraints. |
| 2 | Actual manifest | Identify existing dependency declarations inside `{{APP_REPO_DIR}}/`; assume no filename or ecosystem. |
| 3 | Actual lockfile | Read locked versions, resolved packages, and package manager. Report “Not found” if absent. |
| 4 | Repository commands and environment declarations | Read install, test, build, and runtime commands from scripts, task/version files, containers, and CI workflows. |
| 5 | Current handoff and verification records | Confirm this change and its results; never override the manifest or lockfile. |

When sources disagree, use the repository's current executable state as evidence and record project-card or documentation drift in the handoff. Never correct application code from template memory.

## 5. Upgrade policy

1. Do not upgrade merely to stay current. Explain business benefit, affected areas, and the risk of not upgrading.
2. Establish the baseline from manifests/lockfiles, then check runtime, companion package, plugin, build-chain, and deployment compatibility.
3. Before upgrading, identify a rollback point, data/configuration migration impact, license changes, and known security risks.
4. Classify under the [change-level rule](../rules/改动分级.md) and [three-class boundaries](../../操作系统/01_架构/三类行为铁律.md). Escalate product direction, data migration, release-chain, or framework changes; do not classify mechanically by version number.
5. Update manifests and lockfiles together. Run the instance's `<test-command>`, `<build-command>`, and required smoke tests, recording results in the handoff.

### Lockfiles

- Paths and types follow actual application-repository files, not an assumed package manager.
- Explain lockfile diffs with dependency changes; never update only the manifest and omit the lockfile.
- Stop and investigate missing, conflicting, or differently rewritten lockfiles. Never fabricate locked results manually.

## 6. Adding dependencies

A new dependency is **Class B by default** and requires confirmation before implementation.

1. Product PM states the capability and acceptance criteria; convenience alone does not justify an unbounded dependency.
2. Development/Technical roles inspect the actual language, tooling, manifests, lockfiles, runtime, and repository commands.
3. Technical PM evaluates alternatives, version compatibility, maintenance activity, package size/performance, rollback, licensing, and security.
4. The project Owner or authorized approver named by the project card explicitly approves Class B. Without approval, do not install or modify manifests/lockfiles.
5. Determine whether a PROP/ADR is required by the change level; Development PM implements within the approved scope.
6. Run the instance's tests, build, and smoke checks; synchronize the lockfile, dependency matrix, and handoff evidence.
7. Test and Release PM verifies the instance's release gates. Git actions still require all six ADR-016 conditions.

## 7. Health checks and maintenance

- Review on first initialization, dependency additions/upgrades, runtime changes, and build-chain changes.
- Reread project cards, manifests, lockfiles, and scripts each time; never copy the preceding project's version inventory.
- Mark and correct drift using evidence. A written declaration is not an installation result.
- Operating System PM maintains template structure; Project PM coordinates verification of the instance's actual dependencies.
